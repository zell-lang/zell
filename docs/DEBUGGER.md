# Отладчик

Цель: отладка уровня Delve/dlv и VS Code-интеграции, но быстрее там, где
Delve интерпретирует: условные точки останова, вычисление выражений,
перечисление задач. Преимущество Zell — компилятор на LLVM (DWARF
бесплатно) и компилятор как библиотека (отладчик компилирует условия и
выражения в нативный код).

## Этап 1: DWARF + lldb/gdb + DAP

- Кодогенерация пишет DWARF 5 через LLVM `DIBuilder`: compile unit на файл,
  функции (включая мономорфизированные generics с читаемыми именами
  `Max<int>`), параметры и локальные переменные с местоположениями, строки,
  инлайн; типы: примитивы, структуры с полями, указатели, `weak`, срезы,
  строки, map, кортежи, enum (простые и с данными как tagged union),
  интерфейсы (fat pointer), `T!` (как union {value, error}), `Task<T>`,
  замыкания, фреймы корутин (локальные переменные видны после `await`).
- Включено по умолчанию в debug-сборке; `zell build --release -g` для
  release с отладочной информацией; `--strip` убирает.
- **Форматтеры типов**: `tools/lldb/zell_formatters.py` (string → текст,
  slice → массив, map → пары, `T!` → значение или `error: ...`, enum →
  имя варианта с полями, interface → динамический тип и значение, Task →
  состояние) и `tools/gdb/zell_printers.py`. Подключаются автоматически
  через `zell debug --lldb` или вручную.
- **DAP**: `lldb-dap` с форматтерами; клиент в `editors/vscode`
  (конфигурация `type: "zell"`, запуск `zell build` перед отладкой,
  `program`/`args`/`env`/`cwd`, attach по pid). Работают точки останова,
  условия (вычисляются lldb — медленно, см. этап 2), шаги, стек,
  переменные, watch, REPL-выражения в синтаксисе lldb.
- Паника останавливает отладчик в месте паники (точка на `zell_panic`).

### Статус этапа 1 (сделано)

- **DWARF** (`compiler/src/codegen/debug.rs`): DWARF 5, `DW_LANG_C11`,
  compile unit на исходный файл; `DISubprogram` на функцию с полным
  именем (`app.Max<int>`, `app.Point.Length`, `app.main$lambda1`);
  параметры и локальные переменные через `llvm.dbg.declare` на alloca
  (ячейки захваченных переменных — `DW_OP_deref, +16`), лексические блоки,
  результат функции как переменная `~r0` (как у Delve), глобальные
  переменные; локация на каждом операторе, вызове и `await`; пролог без
  локации, поэтому точка на функции встаёт после записи параметров.
  Типы: примитивы (typedef `int` → `int64_t` и т. п.), структуры, `*T`,
  `weak *T`, `[]T` (struct `[]T {data, len, cap, backing}`), `[N]T`;
  `string`, `error`, `map[K]V` (таблица map.c с типизированными слотами),
  `Task<T>`, `weak *T` — 8-байтные «ручки» `{T *ptr}`; кортежи
  `(A, B) {_0, _1}`, простые enum (enumeration), enum с данными
  (`{tag, union payload}`), интерфейсы и `any`, `T!` (`{value, err}`),
  `func(..)` (`{fn, env}`).
- **Корутины**: CoroSplit переносит `dbg.declare` во фрейм; в
  неоптимизированной сборке выход async-функции читает (volatile) все
  описанные локальные переменные, чтобы они жили во фрейме и были видны
  после любого `await`; дубликаты `dbg.declare`, которые LLVM 18 вешает на
  слоты пролитых SSA-копий, удаляются после оптимизации
  (`codegen::dedup_declares`). Async-функция получает свою задачу только
  при первой приостановке (runtime/ABI.md 10.3): пока она не
  приостанавливалась, её кадр — обычный кадр вызова в составе задачи
  вызывающего (так его и показывают `bt`, `tasks` и агент: записи задачи
  для вызова, завершившегося синхронно, нет), а у функции без точек
  приостановки нет и кадра корутины — LLVM убирает его целиком. Шаг
  `next` через первый `await`, на котором функция действительно
  приостановилась, заканчивается уже в её собственной задаче — событие
  `stopped` приходит с новым `threadId` (как в отладчиках C#, где
  продолжение async-метода после первого `await` идёт в другом потоке).
- Флаги: debug-сборка — с DWARF; `--release` — без (код идентичен: тест
  сравнивает дизассемблер `--release` и `--release -g`); `--release -g` —
  с DWARF и без `-s`; `--strip` — без DWARF и с `-s`.
- **Форматтеры**: `tools/lldb/zell_formatters.py` (summary + synthetic
  children: string, срезы, map, error, `T!`, enum с данными, интерфейсы/
  `any` с динамическим типом по `vtable[0]`, замыкания по имени функции,
  `Task<T>` через `zell_debug_task_layout` (ABI.md §20), `weak`, `char`;
  точка останова `ZellPanic` на `zell_panic*`; команды `zell-next` и
  `zell-rc <выражение>` — счётчик ссылок объекта, на который указывает
  значение, с разбором слова: неразделённый, смещённый к слоту потока
  (B + S), циклический с флагами сборщика, бессмертный, арена, вид строки;
  ABI.md §3.1) и `tools/gdb/zell_printers.py` (те же `zell-rc`). `zell debug --lldb|--gdb file.zl`
  собирает и запускает отладчик с форматтерами (`--source f --batch` для
  скриптов); `zell debug --formatters lldb` печатает путь к скрипту.
- **DAP**: `editors/vscode` — тип `zell` (`launch`: `program`/`source`/
  `args`/`env`/`cwd`/`stopOnEntry`; `attach`: `pid`), адаптер — `lldb-dap`
  с `initCommands: command script import ...`, задача `zell: build` для
  `preLaunchTask`.
- **Тесты** `compiler/tests/debug.rs`: скрипты `lldb --batch` на фикстурах
  `tests/fixtures/debug/*.zl` и на examples, `llvm-dwarfdump --verify` на
  каждом примере, gdb-принтеры, сессия DAP через `lldb-dap`; отсутствующие
  инструменты — тест пропускается.

Ограничения этапа 1:

- `next` в lldb через `await`, который приостанавливает корутину, идёт по
  нативному стеку и останавливается в вызывающей функции. Обходной путь —
  `zell-next`: точка на следующей строке корутины и `continue` (поток
  возобновления — любой worker). Полноценный `await`-aware шаг — дело
  собственного отладчика.
- Выражения `p`/`expr` — в синтаксисе C (lldb/clang): `v nums[1]`
  работает через synthetic children, `p nums[1]` — нет; ключи map в путях
  `frame variable` не поддерживаются (раскрывайте map целиком).
- Типизированные ошибки показываются как тип + поля, не через `Message()`
  (форматтеры не вызывают код в процессе).
- Имена типов — полные (`app.Point`), как в `type_info`.
- В оптимизированном коде (`--release -g`) часть переменных
  «optimized out».

## Этап 2: `zell debug` — отладочный агент внутри процесса (без ptrace)

Основной отладчик — не внешний процесс, а **агент внутри отлаживаемой
программы**, как в Java (JDWP), .NET, Python и JavaScript. Debug-сборка
линкует агент (`runtime/src/debug/`), который слушает DAP по сокету
(`ZELL_DEBUG=:2345` или `zell debug run app.zl`); редактор подключается
напрямую. Внешний ptrace-отладчик не нужен.

### Механика

- **Точки останова и шаги**: компилятор в debug-сборке ставит на границе
  каждого оператора хук `if (zell_dbg_on) zell_dbg_stmt(id)` — один
  предсказуемый branch, при выключенном агенте стоимость около нуля.
  Агент держит таблицу активных точек; `next`/`step`/`step out` — те же
  хуки плюс глубина стека и id задачи, поэтому шаги `await`-aware по
  построению (следующая строка *в этой задаче*).
- **Переменные и стек**: агент читает DWARF своего бинарника (встроенный
  парсер на C/Rust) и память своего процесса обычными указателями;
  раскрутка по frame pointers (включены всегда).
- **Условия, логпоинты, выражения**: компилируются компилятором Zell
  (как библиотека в dev-сборке или через сокет к `zell`) против типов
  DWARF и вызываются как обычные функции в том же процессе. Ноль
  переключений контекста — главный источник скорости относительно Delve.
- **Задачи**: прямой доступ к списку задач планировщика; остановка одной
  задачи при работе остальных или заморозка всех; стек и точка `await`
  каждой задачи.
- **Паники и ошибки**: перехват в `zell_panic` и в местах создания
  ошибок (`break on error NotFound`) до раскрутки.
- **Память**: счётчик ссылок, владельцы, циклы — через рантайм.
  Детектор утечек (`--leak-check`) уже различает циклы, которые
  освободил бы сборщик циклов (`ZELL_CYCLES=manual`: строка «M of them in
  unreachable reference cycles…»), и настоящие утечки; в режиме `auto`
  он сначала собирает циклы, и в отчёте остаются только последние.
  Живые объекты по типам без `--leak-check` — `ZELL_DIAG_HEAP=1` и
  `/debug/heap` (docs/FRAMEWORK.md §5).
- **Горячая замена функций** в dev-сборке тем же агентом.

### Чем быстрее Delve

| Delve | `zell debug` |
|---|---|
| Условная точка: остановка через ptrace на каждом попадании, условие вычисляет отладчик | Условие — скомпилированная функция в процессе; остановка только когда истинно |
| Выражения: интерпретатор подмножества Go | Полный язык, компилируется и выполняется в процессе |
| Логпоинты через остановку | Внедрённый код пишет в канал агента без остановки |
| Горутины: чтение структур рантайма через ptrace, секунды | Список задач в памяти агента, миллисекунды |
| Шаг через канал уводит в планировщик | Шаги по id задачи |
| Каждая операция — syscalls ptrace и переключения контекста | Всё в одном процессе |

### Что даёт отказ от ptrace

Переносимость без усилий: Linux, macOS без entitlements и подписи,
Windows, wasm в браузере, контейнеры без `CAP_SYS_PTRACE`; удалённая
отладка из коробки (сокет); один код агента для всех платформ; отладка в
проде по флагу без перезапуска.

### Чего агент не покрывает — и чем это закрыто

Подключение к процессу без агента, зависший агент, крэши, core-dumps —
внешний режим на базе lldb (этап 1): `zell debug core`, `attach --lldb`,
посмертный анализ с теми же форматтерами.

### Агент написан на Zell

`debug` — обычный модуль стандартной библиотеки на Zell: DAP-сервер
на `net` + `encoding.json`, парсер DWARF на `encoding.binary`
(секции собственного бинарника через `debug.elf/macho/pe`), таблица
точек, шаги, стек по frame pointers, список задач через `task`,
форматирование значений по типам DWARF. Это первая большая программа на
языке и его нагрузочный тест.

На C остаётся минимум (`runtime/src/debug.c`, ~300 строк):

- хук `zell_dbg_stmt(id)`, вызывающий зарегистрированную Zell-функцию;
- `thread.Spawn(fn)` — выделенный поток агента вне пула задач, чтобы он
  отвечал, когда все задачи остановлены (входит в `sync`);
- `unsafe`: чтение/запись памяти по адресу, адрес объекта, вызов по
  адресу — capability, доступная только пакетам с разрешением в манифесте;
- `plugin`: `dlopen`/`dlsym` для загрузки скомпилированных выражений.

Выражения и условия компилирует не агент, а процесс `zell serve`
(компилятор как сервер): агент отправляет выражение и описание типов
текущего кадра, получает объектный файл, загружает его через `plugin`
и вызывает. Бинарник не тянет компилятор, а `zell` и так есть там, где
отлаживают.

### Архитектура

```
editors (VS Code, IDEA) ──DAP/сокет──▶ агент в процессе (debug, на Zell)
                                       ├─ hooks (C): zell_dbg_stmt → Zell
                                       ├─ dwarf (Zell): типы, локации
                                       ├─ expr: `zell serve` → объект → plugin
                                       ├─ tasks: планировщик напрямую
                                       ├─ unsafe/thread (C): память, поток агента
                                       └─ cli: `zell debug` — тонкий клиент
```

### Статус этапа 2 (сделано)

- **Хуки** (`compiler/src/codegen/debug_agent.rs`, флаг `--debug-agent`;
  включён по умолчанию в debug-сборке, в `--release` только явно,
  `--no-debug-agent` выключает): в каждой функции пользовательского кода
  (не стандартной библиотеки) запись кадра `zell_dbg_frame` (32 байта в кадре функции или
  корутины) и одна загрузка `zell_dbg_on` на входе; за `if (on)` —
  `zell_dbg_enter` после записи параметров, `zell_dbg_stmt(id)` перед
  каждым оператором и на закрывающей скобке, `zell_dbg_leave` на выходе,
  `zell_dbg_suspend`/`resume` вокруг `await`. Таблицы операторов
  `{file, line, col, func, kind}`, функций `{name, file, line, locals}` и
  локальных `{name, TypeInfo*, slot, cell?, видимость по строкам}`, байты
  точек останова — runtime/ABI.md §22. Типы локальных — полные таблицы
  `reflect.TypeInfo` (рефлексия включается вместе с агентом).
- **Release без потерь**: в оптимизированной сборке с агентом каждая
  функция (кроме async) есть в двух копиях — с хуками (`sym.dbg`) и без
  (`sym`, на входе `if (zell_dbg_on) return sym.dbg(...)`); прямые вызовы
  из `.dbg` идут в `.dbg`, а у простой копии, которую вызывают только
  простые копии, проверка убирается совсем. С выключенным агентом код
  равен коду сборки без агента: `Fib(35)` 31.4 мс без агента против
  29.6–30.9 мс с агентом (в пределах шума, тест `overhead_with_agent_off`).
  Переменные в release-сборке не описываются (только стек и строки).
  В debug-сборке (`-O0`, одна копия) хуки стоят дороже: `Fib(35)` +56%
  с выключенным агентом и ~7× с включённым агентом без точек (каждый
  оператор — вызов `zell_dbg_stmt`).
- **Рантайм** (`runtime/src/debug.c`): цепочка кадров на поток (теневой
  стек), записи задач (`zell_task.dbg_id`), шаги по задаче
  (`next`/`step in`/`step out` по кадру, родителю и глубине; `await`, на
  котором корутина приостановилась, не завершает шаг — он продолжается,
  когда она возобновится, в той же логической задаче с тем же id, см.
  «Задачи и их id»), заморозка всех задач при остановке,
  остановка одной задачи (`singleThread`), перехват паники и создания
  ошибок, `stopOnEntry`, ожидание `configurationDone`; `unsafe`,
  `thread` (поток вне планировщика), `plugin` (`dlopen`).
- **Агент на Zell** (`debug`, `sema/stdlib_src/debug.zl`,
  `debug_dap.zl`, `debug_vars.zl`, ~2000 строк): DAP-сервер на выделенном
  потоке с блокирующим сокетом (не через `net`: асинхронный `net`
  нуждается в worker'ах планировщика, а они стоят в остановленных
  задачах), `Content-Length`-фрейминг, разбор через
  `encoding.json.ParseValue`. Запросы: `initialize`, `launch`/`attach`
  (программа уже запущена), `setBreakpoints` (строка → операторы всех
  инстансов generic-функции; `condition`, `hitCondition` — `N` (= `== N`,
  как в VS Code), `== N`, `>= N`, `> N`, `< N`, `<= N`, `% N` (каждое N-е
  попадание), неразборчивое условие игнорируется с `message`; `logMessage` с
  `{expr}`; путь сравнивает агент: канонизирует путь клиента (симлинки,
  `realpath`; на Windows `GetFinalPathNameByHandleW` без `\\?\`) и
  сравнивает с таблицей файлов на Windows без учёта регистра и с `\` =
  `/`, затем хвост пути по границе `/`, затем имя файла —
  `runtime/src/debug.c`, правила платформы в `runtime/src/platform/`),
  `setFunctionBreakpoints`, `setExceptionBreakpoints` (`panic`;
  `error` с фильтром по имени типа ошибки), `configurationDone`, `threads`
  (задачи), `stackTrace`, `scopes`, `variables` (с пейджингом
  `start`/`count` для срезов, массивов и map), `setVariable` (локальные,
  поля и элементы скалярных типов: целые с проверкой диапазона, `float`,
  `bool`, `char`, `string` — в кавычках или как есть; новая строка
  создаётся в рантайме, старая освобождается; в клиенте `zell debug` —
  `set x.f[1] = v`), `evaluate`, `continue`,
  `next`, `stepIn`, `stepOut`, `pause`, `disconnect`/`terminate`; события
  `initialized`, `stopped`, `continued` (после каждого `continue`/шага:
  задача снова работает), `output` (логпоинты), `exited` и `terminated`
  (также когда программу завершает паника — после `continue` с
  остановки на ней, код 2).
  Форматирование как в `tools/lldb/zell_formatters.py`: строки, срезы
  (`len 3, cap 4: [1 2 3]`), массивы, map, простые enum (`Color.Green`) и
  с данными (`Fail(code: 2, reason: "bad")`), интерфейсы и `any` с
  динамическим типом, `*T`, `weak *T`, `T!` (`error: ...`), ошибки (тип и
  `Message()`), `Task<T>` (состояние и результат), замыкания (имя функции),
  кортежи (`(3, "rem")`, элементы `_0`, `_1`, … раскрываются и доступны в
  выражениях: `pair._1`). В лямбде видны и захваченные ею переменные
  внешней функции (по ссылке: текущее значение ячейки).
- **Выражения (v1)**: пути к переменным `a.b[2].c`, `m["key"]`, `m[3]`,
  `len(x)`, литералы, сравнения `== != < <= > >=`, `&& || !`, `nil`,
  варианты enum (`c == Green`, `c == Color.Green`); они же — условия точек
  и `{...}` в логпоинтах, вычисляются в процессе без остановки. Арифметики
  и вызовов нет; компиляция произвольных выражений через `zell serve` +
  `plugin` — следующий шаг (рантайм для неё готов, сервера нет).
- **Запуск**: `ZELL_DEBUG=[host]:port[,wait]` (`:0` — свободный порт,
  объявляется в stderr строкой `zell-debug: listening on 127.0.0.1:PORT`;
  `,wait` держит `main` до `configurationDone`). `zell debug run file.zl
  [--port N]` собирает с агентом и открывает тонкий клиент (`zell::dap`)
  с командами gdb: `b file:line [if cond]`, `b func`, `log file:line msg`,
  `c`, `n`, `s`, `o`, `p expr`, `locals`, `bt`, `up`/`down`, `tasks`,
  `task N`, `catch panic|error [T]`, `q`; `--headless [--wait]` — только
  агент, для редактора; `zell debug attach [host:]port` — клиент к уже
  запущенной программе.
- **Задачи и их id** (`threadId` в DAP). «Поток» DAP — это задача, точнее
  логическая цепочка `await`: id даётся записи агента при первой
  остановке кода или при первой приостановке задачи на `await` (хуки
  операторов записей не создают) и хранится в `zell_task.dbg_id`, то есть
  не меняется при всех последующих `await` этой задачи. Код без текущей
  задачи (главный поток) — запись 1. Async-функция до первой приостановки
  выполняется в задаче вызывающего (ABI.md 10.3) и видна под его id; когда
  она приостанавливается впервые и получает свою задачу, то: (1) если в её
  кадре идёт шаг (`next`/`step in`/`step out` начат в ней), её задача
  **забирает** id, под которым её видел клиент, — `next` через `await`
  останавливается в той же функции с тем же `threadId`, а вызывающий,
  который просто продолжает после возврата из рампы, получит новый id,
  только если сам остановится; (2) иначе (никто в ней не шагал, например
  `var t = Half(3)`) — её задача получает новый id и видна в `threads`
  отдельной задачей. Забранный id после завершения задачи переходит к
  **ожидающему** её (задаче, зарегистрировавшей продолжение): `main`,
  ждущий `Work`, после `await` снова останавливается под тем же id; своя
  запись ожидающего, сделанная при его приостановке, при этом снимается,
  если она ни разу не останавливалась. Шаг `step in` в вызываемую
  функцию останавливается в её первом операторе ещё в задаче вызывающего
  (тот же id); если она потом приостанавливается, действует правило (1).
  Имя потока — функция на дне цепочки (`main` или `task N Work`) и
  меняется вместе с переходом записи. Тесты: `next_over_await_stays_in_task`,
  `task_id_stable_across_awaits`.
- **Отладка тестов**: `zell test --debug [--port N] [--wait] [--filter F]`
  выполняет выбранные тесты в одном процессе под одним агентом (каждый
  тест — своя задача; паника, `t.Fatal`, `t.Skip` завершают только её),
  порт и `,wait` — как у `zell debug run --headless`; docs/TOOLING.md,
  «Тесты»; тест `debug_runs_tests_in_one_process_under_the_agent`.
- **Capability**: `unsafe` и `plugin` импортирует только
  стандартная библиотека и пакеты с `[capabilities] unsafe = true` /
  `plugin = true` в манифесте; обычный файл без манифеста — нет. Обращение
  по полному пути без импорта (`unsafe.ReadInt(...)`) проверяется так же.
- **VS Code**: `"adapter": "agent"` (по умолчанию) — `launch` запускает
  программу с `ZELL_DEBUG=127.0.0.1:0,wait`, читает порт и подключается
  через `DebugAdapterServer` (вывод программы — в debug console);
  `attach` с `address` (`":2345"`) или `host`/`port`; `"adapter": "lldb"`
  — прежний режим этапа 1.
- **Тесты** `compiler/tests/debug_agent.rs`: DAP по сокету против
  собранных фикстур — переменные всех видов на точке останова, generic,
  ошибки и `stepOut`, `next` через `await` в той же задаче (и тот же id
  задачи при всех `await`, возврат id ожидающему), `setVariable`,
  все формы `hitCondition`, пути точек через симлинк и хвост пути (C-матчер
  с правилами Windows — `runtime/tests/test_debug.c`, также под wine),
  логпоинты без
  остановки, условные точки, точка на функцию и `stepIn`, `pause`/
  `continue`, паника и создание ошибки как exception breakpoints (с
  `continued`/`exited` после паники), захваченные переменные и кортежи, две
  задачи с независимыми шагами, release-сборка с агентом, capability,
  накладные расходы.

Ограничения этапа 2:

- `evaluate` — только v1 (пути и сравнения); `zell serve` не сделан
  (замечание IDE-плагина о полном `evaluate` оставлено этому плану).
- `setVariable` — только скалярные типы; составные значения, указатели и
  map не присваиваются.
- Переменные не видны в оптимизированной сборке (стек и шаги работают).
- Задача получает запись (и попадает в `threads`) при первой остановке
  или первой приостановке на `await`; номера задач не равны порядку
  запуска. Если ожидающий начинает ждать задачу уже после её завершения
  или ждёт не её первой, забранный id завершается вместе с задачей.
- `pause` останавливает задачи на ближайшем операторе; задача, ждущая
  ввода-вывода или таймера, видна как остановленная на своём `await`.
- Шаг `step out` и `next` с последней строки сначала останавливаются на
  закрывающей скобке; возврат в вызывающую функцию — на следующем
  операторе после вызова.

## Этапы

1. DWARF в кодогенерации (все типы, локальные переменные, корутины),
   форматтеры lldb/gdb, `lldb-dap` в VS Code, тесты: скрипты lldb,
   проверяющие значения на точках останова в examples/.
2. In-process агент на Zell (`debug`): хуки операторов в кодогенерации, `unsafe`/`thread`/`plugin` в рантайме, таблица точек,
   шаги, стек и переменные по DWARF, DAP по сокету, тонкий клиент
   `zell debug`; замена `lldb-dap` в VS Code.
3. Компилируемые условия и выражения, логпоинты, список задач и шаги по
   задаче, остановка на паниках и ошибках.
4. Память и ошибки как объекты отладки, горячая замена, remote в проде.
5. Внешний режим (lldb) для крэшей и core-dumps; wasm.
