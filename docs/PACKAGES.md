# Менеджер пакетов Zell

Собственный менеджер пакетов, встроенный в CLI `zell`. Берёт у Go
воспроизводимость (minimal version selection, журнал контрольных сумм),
у Cargo — манифест, lock-файл, реестр, features и workspace, и добавляет
то, что возможно только при своём компиляторе: кэш собранных пакетов и
анализ capabilities.

## Модель: как у Go, с улучшениями

Идентичность пакета — путь репозитория (`github.com/org/router`), без
центрального реестра с публикацией. Это снимает захват имён, исчезающие
пакеты и необходимость содержать сервер; приватные репозитории работают
без настройки; исходники всегда лежат на диске и видны IDE.

| Компонент | Как у Go | У нас |
|---|---|---|
| Имя пакета | путь модуля (URL) | то же; версии — git-теги `v1.2.3` |
| Пространство имён в коде | путь импорта целиком | модуль объявляет корень (`router`); `import github.com/org/router` даёт `router.X`; конфликт корней решается `as` |
| Манифест | `go.mod` | `zell.toml/json/yaml`: `[dependencies]`, `[dev-dependencies]`, `[features]`, `[workspace]` |
| Выбор версий | MVS | MVS |
| Целостность | `go.sum` + sum.golang.org | `zell.lock` (хэши) + публичный журнал контрольных сумм |
| Доступность | proxy.golang.org | публичный прокси-кэш модулей; `ZELL_PROXY`, `ZELL_NOPROXY`, `ZELL_PRIVATE` |
| Поиск и документация | pkg.go.dev, наполняется из прокси | индекс, наполняется из прокси; `zell doc <path>` офлайн из кэша |
| Кэш на диске | `$GOPATH/pkg/mod` | контентно-адресуемое хранилище с жёсткими ссылками (pnpm), один экземпляр на все проекты |
| v2+ | `/v2` в пути импорта | путь не меняется; одна мажорная версия в графе, иначе ошибка с объяснением |
| Безопасность | govulncheck | capabilities пакета (сеть, файлы, процессы, unsafe) видны при `zell add` и в lock; `zell audit` |
| Сборка зависимостей | кэш сборки | кэш собранных пакетов по (версия, features, профиль, компилятор) |

Короткое имя — просто псевдоним в манифесте:
`router = { git = "github.com/org/router", version = "^1.2" }`.

## Принципы

1. **Воспроизводимость.** Minimal Version Selection; новый релиз
   зависимости ничего не меняет до `zell update`.
2. **Одна мажорная версия пакета в графе.** Конфликт — ошибка с объяснением.
3. **Пакет объявляет корневое пространство имён.** Изоляция: пакет видит
   только объявленные зависимости и стандартную библиотеку; корни stdlib
   (`io`, `net`, …) пакету не принадлежат.
4. **Целостность.** Хэш каждого пакета в `zell.lock`; публичный журнал
   контрольных сумм; клиент сверяет.
5. **Без центрального реестра.** Git-репозиторий или локальный путь —
   источник; прокси и индекс — необязательные ускорители и зеркала, любой
   HTTP-сервер со статической раскладкой может быть прокси.

## Манифест: `zell.toml`, `zell.json` или `zell.yaml`

Формат манифеста выбирает автор проекта, по имени файла. Все три формата
описывают одну и ту же схему; `zell init --format json|yaml|toml` создаёт
нужный, `zell manifest convert yaml` переводит между ними. В корне проекта
допускается только один манифест. Схема публикуется как JSON Schema
(`zell manifest schema`), поэтому редакторы дают автодополнение и проверку
во всех трёх форматах.

```toml
[package]
name = "shop"
version = "0.3.1"
namespace = "shop"          # корневое пространство имён пакета
entry = "src/main.zl"       # точка входа для бинарника (опционально)
license = "MIT"
description = "Example service"

[dependencies]
"github.com/org/router" = "^1.2"
"github.com/org/crypto-extra" = { version = ">=0.5, <1", features = ["argon2"] }
router2 = { git = "github.com/other/router", version = "^3" }   # псевдоним при конфликте
internal-lib = { path = "../internal-lib" }
experimental = { git = "https://github.com/org/exp", tag = "v0.4.0" }

[dev-dependencies]
testkit = "^1"

[features]
default = ["tls"]
tls = ["http-router/tls"]
metrics = []

[workspace]
members = ["services/*", "libs/*"]
```

Тот же манифест в YAML:

```yaml
package:
  name: shop
  version: 0.3.1
  namespace: shop
dependencies:
  github.com/org/router: ^1.2
  github.com/org/crypto-extra: { version: ">=0.5, <1", features: [argon2] }
  internal-lib: { path: ../internal-lib }
dev-dependencies:
  testkit: ^1
features:
  default: [tls]
  tls: [http-router/tls]
```

- Ограничения версий: `^1.2` (>=1.2, <2), `~1.2.3` (>=1.2.3, <1.3),
  `>=1, <2`, `=1.4.0`.
- `features` — условная компиляция через `@cfg(feature: "tls")` на
  объявлениях.
- `[capabilities]` — низкоуровневые модули стандартной библиотеки, которые
  пакету разрешено импортировать: `unsafe = true` (`unsafe`: память по
  адресу, вызов по адресу) и `plugin = true` (`plugin`: `dlopen`). Без
  разрешения (и в сборке без манифеста) `import unsafe` — ошибка
  компиляции; сама стандартная библиотека (отладочный агент `debug`)
  ими пользуется. См. docs/DEBUGGER.md, runtime/ABI.md §22.

## Lock-файл `zell.lock`

Всегда один формат независимо от формата манифеста: детерминированный
YAML с отсортированными ключами (читается человеком, хорошо сливается в
git). Генерируется автоматически, коммитится в репозиторий. Содержит точную
версию, источник и хэш каждого пакета в графе, включая транзитивные.
Читается не только сборкой, но и LSP (навигация внутри зависимостей) и
`zell doc`.

## Команды

| Команда | Действие |
|---|---|
| `zell init [name]` | создать `zell.toml` и `src/main.zl` |
| `zell add github.com/org/pkg[@constraint] [--dev] [--features a,b]` | добавить зависимость, обновить lock |
| `zell remove pkg` | удалить зависимость |
| `zell update [pkg]` | поднять версии в рамках ограничений |
| `zell build` / `run` / `test` | сами скачивают и собирают зависимости |
| `zell release v1.2.3` | проверить манифест и тесты, создать подписанный git-тег; прокси и индекс подхватят сами |
| `zell audit` | сверить граф с базой уязвимостей |
| `zell vendor` | скопировать все зависимости в `vendor/` |
| `zell install [--offline]` | привести `.zell/deps` в соответствие с lock-файлом |
| `zell store verify / prune / path` | проверить, очистить, показать хранилище |
| `zell manifest convert <fmt> / schema` | сменить формат манифеста, вывести JSON Schema |
| `zell tree` | показать граф зависимостей |
| `zell why pkg` | объяснить, кто требует пакет |

## Хранилище и кэш (модель pnpm)

Одно глобальное **контентно-адресуемое хранилище** `~/.zell/store/`:

- Каждый файл каждого пакета лежит там один раз, под именем своего хэша
  (`store/files/<sha256>`); версия пакета — это индекс «путь → хэш»
  (`store/packages/<name>/<version>/index.yaml`). Десять проектов с одной
  и той же зависимостью занимают место один раз.
- В проект пакеты не копируются. Каталог `.zell/deps/<name>@<version>/`
  заполняется **жёсткими ссылками** на файлы хранилища (на той же файловой
  системе), иначе reflink/копия. Установка — это создание ссылок, поэтому
  она занимает миллисекунды и не зависит от размера пакетов.
- Исходники зависимостей видны IDE через `.zell/deps/` и `zell.lock`
  (см. `docs/TOOLING.md`), как `$GOPATH/pkg/mod` у Go.
- Целостность: хэш каждого файла проверяется при добавлении в хранилище
  и при `zell store verify`. Повреждённый или подменённый файл
  обнаруживается, а не тихо компилируется.
- **Строгая изоляция зависимостей**: пакет видит только то, что объявил в
  своём манифесте. «Фантомные» зависимости невозможны: компилятор разрешает
  `import` только по графу из lock-файла.
- `zell install --offline` собирает из хранилища без сети; `zell store
  prune` удаляет версии, на которые не ссылается ни один проект;
  `zell store path` показывает расположение. Хранилище можно вынести на
  общий диск (`ZELL_STORE`) для CI.

**Кэш сборки** живёт рядом: `~/.zell/store/build/<pkg>/<hash>/`, где хэш
учитывает версию пакета, набор features, профиль, версию компилятора и
целевую платформу. Внутри — объектный файл и сериализованный HIR с
сигнатурами. Все проекты на машине переиспользуют его; после первой
сборки зависимости не перекомпилируются. Генерики мономорфизируются на
стороне использующего пакета по сериализованному HIR. Кэш сборки — просто
директория, его можно выгружать в CI-артефакт или удалённый кэш
(`ZELL_BUILD_CACHE=https://...`, как у sccache).

## Безопасность

- **Подпись релизов** ключом издателя; реестр проверяет при публикации,
  клиент — при скачивании.
- **Capabilities.** Стандартная библиотека помечает «опасные» точки:
  сеть (`net`), файлы (`fs`, `io` файловые функции), процессы
  (`process`, `os`), FFI/unsafe. Компилятор вычисляет, какие из них
  достижимы из пакета, и пишет в метаданные. `zell add` показывает:
  `http-router: network`, `left-pad: none`. Пакет, который внезапно
  начинает использовать процессы в новой версии, подсвечивается при
  `zell update`.
- **`zell audit`** — база уязвимостей в реестре, проверка по lock-файлу,
  в CI через `zell audit --deny`.
- Скрипты сборки в пакетах запрещены. Нет `build.rs` и post-install hooks,
  нечему выполняться при установке.

## Прокси, журнал контрольных сумм, индекс

- **Прокси** (`ZELL_PROXY=https://proxy.zell-lang.org,direct`): кэширует
  архивы модулей по пути и версии; делает пакеты доступными, даже если
  репозиторий удалён; статическая раскладка `/<path>/@v/list`,
  `/<path>/@v/v1.2.3.zip|.info|.manifest`, поэтому зеркало — любой HTTP-сервер.
- **Журнал контрольных сумм** (append-only, с доказательствами включения,
  как sum.golang.org): клиент сверяет хэш модуля при первой загрузке;
  `ZELL_NOSUMDB` для приватных путей.
- **Индекс** (`index.zell-lang.org`): поиск, документация, версии,
  capabilities, уязвимости; наполняется из прокси автоматически.
- **Приватное**: `ZELL_PRIVATE=github.com/mycorp/*` — напрямую по git с
  учётными данными системы, без прокси и журнала; корпоративный прокси —
  тот же статический формат.

## Чего не будет

- Нескольких версий одной мажорной ветки в одном бинарнике.
- Скриптов, выполняющихся при установке пакета.
- Версии в пути импорта (`pkg/v2`).
- Центрального реестра с публикацией и короткими глобальными именами.

## Этапы

1. ✅ **Готово.** Манифест (TOML/JSON/YAML, общая схема), `path`-зависимости, workspace, компиляция многопакетного
   проекта (нужно для разбиения стандартной библиотеки на пакеты).
   Что реализовано (`compiler/src/package/`, `compiler/src/build.rs`):
   - манифест `zell.toml` / `zell.json` / `zell.yaml` (ровно один в
     директории, иначе ошибка со списком), одна serde-модель;
     `zell manifest schema` (JSON Schema через `schemars`),
     `zell manifest convert <fmt>` (с проверкой round trip);
   - поиск проекта вверх от текущей директории; enclosing `[workspace]`,
     в котором директория перечислена как member, становится корнем;
     `zell build/run/check/test` без пути, `--workspace`, `-p name`;
     путь к файлу или к директории без манифеста — прежняя сборка без пакетов;
   - исходники `src/**/*.zl`; `entry` — бинарник, без `entry` — библиотека;
     `zell init [dir] [--format toml|json|yaml] [--lib]`;
   - граф `path`-зависимостей: дедупликация по каноническому пути, поиск
     циклов (`a -> b -> a`), проверка имён и features зависимостей;
   - корень пространства имён (`namespace`, по умолчанию имя с `-` → `_`) —
     один идентификатор, уникальный в графе; все файлы пакета объявляют
     `namespace <root>` или `<root>.<sub>`;
   - **строгая изоляция**: файл видит только стандартную библиотеку, свой пакет и прямые
     зависимости своего пакета — и в `import`, и в полном пути без импорта.
     Реализовано хуком `sema::ImportPolicy` (проверка первого сегмента
     пути); ошибка называет пакет, который надо добавить в `[dependencies]`,
     и через какую зависимость он доступен транзитивно;
   - каждый пакет компилируется в свой объектный файл
     `target/zell/<pkg>-<hash>.o` (хэш от IR пакета, флагов и компилятора;
     неизменённый пакет не перекомпилируется), затем всё линкуется;
     у каждой функции и глобала своя секция, `--release` линкует с
     `--gc-sections` и `-s`, `--static` — полностью статический бинарник.
   - Ограничения этапа: `dev-dependencies` разрешаются и попадают в lock,
     но видны только в `zell test`, который пока только проверяет типы;
     `features` проверяются и включают `@cfg(feature: "...")`: у пакета
     включены `default`, features, запрошенные зависимыми пакетами
     (`features = [...]`), и то, что включают включённые (`name`,
     `dep/name`); флага `--features` у CLI пока нет.
2. ✅ **Готово.** `zell.lock`, git-зависимости, MVS (`compiler/src/package/`:
   `resolve.rs`, `semver.rs`, `git.rs`, `lock.rs`).
   - Зависимость по пути модуля: `"github.com/org/pkg" = "^1.2"` (ключ с
     `/` или точкой в первом сегменте — путь модуля, иначе — псевдоним);
     `{ git = "...", tag | branch | rev = "..." }` — закрепление коммита;
     псевдоним `name = { git = "...", version = "^1" }`. URL клонирования:
     `https://<путь>` (или `git` как есть); учётные данные и
     `url.<base>.insteadOf` — из конфигурации системного `git`.
   - Версии — semver-теги (`v1.2.3`, `git ls-remote --tags`), скачивание —
     `git clone --depth 1 --branch <тег>`; `branch`/`rev` и не-semver теги
     получают псевдоверсию `v0.0.0-<UTC время коммита>-<12 hex>`.
   - **MVS** по всему графу (транзитивные манифесты): минимум требования —
     наименьшая версия, подходящая под ограничение; выбирается максимум
     минимумов (как в Go — включая требования вытесненных версий); версия
     из `zell.lock` сохраняется, пока подходит под все ограничения (новый
     релиз ничего не меняет до `zell update`); затем проверяются верхние
     границы итогового графа. Одна мажорная версия модуля в графе, иначе
     ошибка с обоими требованиями.
   - `zell.lock`: у модулей `module`, `version: v1.2.0`, `source: module`
     или `git+<url>?tag=|branch=|rev=<ref>#<commit>`, `checksum: h1:...`,
     `dependencies`; детерминированный (не зависит от машины, прокси и
     порядка сборки). Скачанное сверяется с `checksum` до записи в
     хранилище: несовпадение — `SECURITY ERROR`.
   - `zell update [module|name ...]` (новейшие версии в рамках
     ограничений), `zell tree`, `zell why <module|name>`, `--locked`,
     `--offline` у `build/run/check/test/install`.
   - **Хэш `h1:`** (`sum.rs`): `h1:` + base64(sha256(summary)), где
     summary — для каждого файла дерева модуля (без `.git/`, отсортировано
     побайтово по пути `a/b.zl`) строка `hex(sha256(содержимое)) + "  " +
     путь + "\n"`. Это `dirhash.Hash1` Go без префикса `module@version/`.
     Манифест отдельно: тот же хэш от одного файла.
3. ✅ **Готово.** Контентно-адресуемое хранилище (`store.rs`):
   `$ZELL_STORE` (по умолчанию `$ZELL_HOME/store`, `$ZELL_HOME` =
   `~/.zell`), `files/<sha256>` (только чтение), `packages/<путь>/<версия>/index.yaml`
   (путь → хэш, размер; `h1`, источник), `projects.txt` (для `prune`).
   Проект получает `.zell/deps/<путь модуля>@<версия>/` из жёстких
   ссылок (копия, если ссылка невозможна); заглавные буквы пути
   кодируются как в Go (`!x`). Компилятор читает зависимости оттуда.
   `zell install [--offline] [--locked]` (заодно удаляет устаревшие
   каталоги), `zell store verify | prune | path`, `zell vendor`
   (`vendor/<путь>@<версия>/` + `vendor/modules.yaml`; пока он есть,
   сборка берёт модули оттуда, сверяя с lock, без сети и хранилища).
   Кэш сборки по-прежнему только в `target/zell/`.
4. ✅ **Готово (кроме индекса).** Прокси со статической раскладкой,
   журнал контрольных сумм (`fetch.rs`, `http.rs`, `proxy.rs`).
   - Клиент: `ZELL_PROXY=https://host,direct` (по умолчанию `direct`):
     `,` — к следующему при 404/410, `|` — при любой ошибке; `direct` —
     git, `off` — запрет. `GET <proxy>/<путь>/@v/list`,
     `/@v/<версия>.info` (JSON `{"Version","Time","Manifest","Origin"}`),
     `/@v/<версия>.manifest` (файл манифеста как есть),
     `/@v/<версия>.zip` (дерево под `<путь>@<версия>/`, без сжатия —
     архив воспроизводим побайтно). `http://` — встроенный клиент,
     `https://` — системный `curl`, `file://` — каталог-зеркало.
     `ZELL_PRIVATE` (глобы по сегментам пути, `github.com/mycorp/*`) —
     напрямую по git с системными учётными данными, без прокси и журнала;
     `ZELL_NOPROXY`, `ZELL_NOSUMDB` (по умолчанию = `ZELL_PRIVATE`).
   - Сервер: `zell proxy serve --dir <кэш> [--addr host:port]
     [--upstream direct|off|<url>] [--sumdb]` — отдаёт раскладку из
     каталога и наполняет его по запросу из git (или другого прокси);
     всё, что он пишет, — обычные файлы, так что наполненный каталог
     может отдавать любой статический HTTP-сервер (`--upstream off`).
   - Журнал контрольных сумм (`ZELL_SUMDB=<url>`, по умолчанию `off`),
     формат v1 — статические файлы: `/latest` = `zell-sumdb v1\n<N>\n<base64
     sha256 первых N записей>\n`, `/lookup/<путь>@<версия>` = `<номер
     записи>\n<путь> <версия> h1:...\n<путь> <версия>/manifest h1:...\n`,
     `/log` — все записи. Клиент сверяет `h1` при первой загрузке
     (`.manifest` и `.zip`) и что номер записи меньше размера журнала.
     В v1 нет Merkle-доказательств включения и подписей: первая строка
     `/latest` называет формат, v2 добавит корень дерева, подписи и
     `/tile/...`, не меняя lookup. Сервер с `--sumdb` дописывает запись
     при первой выдаче версии.
   - Не сделано: индекс (`index.zell-lang.org`), `zell doc <path>`,
     `zell add`/`remove`, публичный прокси (поэтому по умолчанию
     `direct`), кэш сборки по (версия, features, профиль), dev-зависимости
     модулей не разрешаются (как в Go/Cargo), `path`-зависимости внутри
     опубликованного модуля запрещены.
5. **План: публичный прокси, индекс и сайт пакетов** (решение 2026-10-23,
   малый бюджет). Три слоя на одной машине, как `proxy.golang.org` +
   `pkg.go.dev`, но ужатые:
   - *Прокси* — `zell proxy serve --upstream direct` на VPS за Cloudflare
     (CDN; содержимое версий неизменяемо, кэшируется навсегда). Нет пакета
     в кэше — клонируется из git при первом запросе; у клиента
     `ZELL_PROXY=https://proxy…,direct`, так что пакет скачивается всегда.
     Бэкап каталога и статики — `rclone` в R2; на статику из бакета можно
     переключить DNS без изменений у клиентов.
   - *Индексатор* — фоновый воркер (на Zell, как showcase): очередь «новая
     версия» от прокси и webhook'ов GitHub; скачивает zip из прокси,
     запускает `zell doc --json` и `zell check` в песочнице (контейнер, без
     сети, лимит времени), берёт из манифеста `description`, `license`,
     `keywords`, первый абзац README, пишет в SQLite; рендерит страницы
     документации в статический HTML в бакет. Публикует
     `index.zell-lang.org/latest` («путь версия время») для зеркал.
   - *Поиск* — SQLite FTS5 по имени, описанию, README, тегам и именам
     экспортированных символов; BM25 + число импортирующих пакетов,
     свежесть, наличие документации; фасет по `keywords`; `zell search
     <слова|tag:json|strings.ReplaceAll>`, `zell add` показывает описание,
     лицензию, capabilities и дату перед добавлением.
   - В манифест добавить `keywords`, `repository`, `readme`; зафиксировать
     версию схемы `zell doc --json`.
   Порядок: прокси (день) → индексатор + FTS + статические доки (2–3
   агентские сессии) → `search`/`add` в CLI.
