# Zell — дизайн языка

Zell — компилируемый язык с простой структурой в духе Go, но без шумных
`if err != nil`, с выводом типов через `var`, пространствами имён вместо
пакетов, методами внутри структур и встроенным `async/await`.
Компилируется в нативный код через LLVM.

## Цели

- **Простота Go**: маленький набор конструкций, явный поток управления,
  структуры вместо классов, указатели без арифметики.
- **Меньше шума**: обработка ошибок через `!`, `?` и `try` вместо повторяющихся
  `if err != nil { return err }`.
- **Вывод типов**: `var x = 123` как в C#, без `:=`.
- **Пространства имён**: полный путь `app.services.users.UserService`, как
  namespace в C#, вместо коротких имён пакетов.
- **Методы внутри структур**: тело структуры содержит и поля, и методы.
- **Асинхронность**: `async`/`await` как языковая конструкция.
- **LLVM**: один бэкенд, нативные бинарники, оптимизации бесплатно.

## Не цели

- Наследование классов. Generics есть (мономорфизация, см. «Generics»),
  но без обобщённых интерфейсов, вариантности и специализации.
- Исключения. Ошибки — обычные значения.
- Макросы и метапрограммирование.
- Трассирующий сборщик мусора. Память управляется подсчётом ссылок с
  оптимизациями компилятора (см. «Память»); циклы освобождает
  ограниченный сборщик циклов, который просматривает только объекты
  циклических типов (см. «Циклы»).

## Файлы и пространства имён

Один файл начинается с объявления пространства имён. Имя — полный путь,
точки разделяют уровни.
В файле ровно одно объявление `namespace`, и оно первое: второе
объявление — ошибка компиляции. Пространство имён может занимать
несколько файлов; вложенное пространство (`app.services.users.cache`) —
это отдельный файл.

```zell
namespace app.services.users

import io
import app.models

struct UserService {
    // ...
}
```

### Точки с запятой

`;` между инструкциями не пишут: как в Go, лексер вставляет его в конце
строки, если последний токен строки может завершать инструкцию
(идентификатор, литерал, `return`, `break`, `continue`, `nil`, `true`,
`false`, `this`, `_`, `)`, `]`, `}`, `?`, `!`, `>` закрывающих
аргументов типа). Отличия от Go:

- внутри `( )` и `[ ]` точки с запятой не вставляются — списки аргументов
  и литералы срезов переносятся без запятой в конце строки;
- после `:` точка с запятой не вставляется (как и в Go), поэтому метка
  `outer:` на отдельной строке стоит перед следующей инструкцией;
- строка, первый токен которой — `.`, продолжает предыдущую: `;` перед ней
  не вставляется (комментарии и пустые строки между ними не мешают), так
  что цепочку вызовов можно переносить перед точкой.

```zell
var names = users
    .Where((u) => u.Active)
    .Select((u) => u.Name)
    .ToList()
```

### Правила импорта

`import X` делает содержимое пространства имён `X` доступным по коротким
именам (как `using` в C#). Пространства имён стандартной библиотеки —
корневые (`io`, `fmt`, `strings`, `net`, `net.http`, `log`,
`encoding.json`, `crypto.hash`, `data`, `task`, `reflect`,
`debug`, `os`, `collections`, …), как и корни пакетов (`app`):

| Импорт | Обращение |
|--------|-----------|
| нет импорта | `io.println("hi")`, `net.http.Get(url)`, `app.models.User` |
| `import io` | `println("hi")` |
| `import net.http` | `Get(url)` |
| `import io as out` | `out.println("hi")` |
| `import app.models` | `User` |
| `import app.models.User` | только `User` |

- Полный путь работает всегда, импорт только сокращает его.
- Конфликт коротких имён из двух импортов — ошибка компиляции в месте
  использования (`ambiguous name`); её решают псевдонимом (`as`) или
  полным путём. Имя из импорта скрывает одноимённое корневое пространство
  (`import crypto` даёт `hash` = `crypto.hash`; корень `hash` тогда
  доступен через `import hash.fnv` или псевдоним). Код самой стандартной
  библиотеки такие имена не скрывают.
- Объявление своего пространства имён скрывает одноимённое имя из импорта
  без ошибки (`const ErrNotFound` при `import net`): короткое имя — своё,
  импортированное доступно полным путём (`net.ErrNotFound`). Использование
  такого имени даёт предупреждение-инспекцию `L0010` (`import-shadowed`);
  объявление без использований по короткому имени — нет.
- Импортировать можно и отдельный член: `import app.models.User` — в
  область видимости попадает только `User`.
- Импорт родительского пространства делает дочерние доступными по
  последнему сегменту: `import net` → `http.Get(url)`.
- Относительные ссылки: первый сегмент пути, который не локальное имя, не
  член своего пространства и не импорт, ищется среди дочерних пространств
  объемлющих пространств, от ближайшего к корню: в `app.api` запись
  `model.User` — это `app.model.User` (так же, как из самого `app`), в
  `app.api.v1` — тоже. Корневые пространства (stdlib и пакеты) проверяются
  раньше: в `app.api` при соседнем `app.errors` запись `errors.New` — это
  stdlib `errors`, соседа называют полным путём или импортом.
- Корни стандартной библиотеки зарезервированы: `namespace io` или
  `namespace net.x` (первый сегмент — корень stdlib) — ошибка компиляции
  «namespace `io` belongs to the standard library»; пакет с таким корнем
  (`namespace` в манифесте или имя пакета) отвергается при загрузке
  манифеста. Корня `std` больше нет: `import std.io` — ошибка с
  исправлением `import io`, `namespace std...` зарезервирован.
- Имя встроенной функции (`delete`, `len`, `append`, `panic`, `typeof`,
  `error`) не перекрывается одноимённым членом пространства stdlib,
  импортированного целиком (атрибут `@delete`): вне атрибутов
  оно остаётся встроенной функцией.
- Имя встроенного атрибута (`json`, `yaml`, `toml`, `xml`, `csv`, …) в
  голове составного пути (`json.Value`) при `import encoding.json`
  означает импортированное пространство `encoding.json`, а не структуру
  значения атрибута (у неё нет членов); само имя (`@json(...)`,
  `Attribute<json>()`) остаётся атрибутом.
- Неиспользуемый импорт — ошибка компиляции (`unused import`), как в Go Импорт
  используется и тогда, когда к его пространству обращаются только по
  имени (`import task` + `task.Delay(1)`, `import app.geo` + `geo.Hello()`).
- Точка входа — функция `main`, указанная при сборке (по умолчанию ищется в
  корневом пространстве имён проекта). `main` не принимает параметров и
  возвращает ничего или `void!` (также `async func main() void!`): если она
  вернула ошибку, программа печатает в stderr `error: <сообщение>` и трассу,
  код выхода 1.
- Видимость: имя с заглавной буквы экспортируется (как в Go). Строчная —
  приватно для пространства имён. Исключение — функции стандартной
  библиотеки вроде `println`, которые для краткости экспортируются со
  строчной буквы; правило для пользовательского кода остаётся строгим.

## Объявления переменных

Только `var`. Тип выводится из инициализатора. Явный тип пишется после имени
через пробел, как в Go.

```zell
var x = 123          // int
var name = "zell"   // string
var ratio = 0.5      // float
var list []int = []  // явный тип нужен, если из значения не выводится
var count int        // без инициализатора: нулевое значение
```

- `const` — константы времени компиляции: `const Pi = 3.14159`. Константное
  выражение может задавать длину массива: `var buf [N * 2]byte`.
- Переменные нельзя объявить и не использовать (как в Go).
- Множественное присваивание существующим переменным:
  `a, b = b, a` (сначала вычисляются все значения справа) и
  `(q, r) = DivMod(17, 5)` для кортежного результата (`_` отбрасывает).
- Операторов `++` и `--` нет: пишут `i += 1` / `i -= 1`. `i++` в конце
  инструкции — ошибка «Zell has no ++; write i += 1» с исправлением;
  разбор продолжается, как будто написано `i += 1`, следующая строка
  ошибок не получает.
- Кортежный результат раскладывается в новые переменные:
  `var (q, r) = DivMod(17, 5)` или, как в Go, без скобок
  `var q, r = DivMod(17, 5)` (явный тип не пишется).
- Поиск в map с проверкой наличия (comma-ok, как в Go):
  `var v, ok = m[k]` (или `var (v, ok) = m[k]`, `v, ok = m[k]`) — `ok`
  типа `bool`, при отсутствии ключа `v` — нулевое значение. Простое
  `m[k]` по-прежнему даёт только значение. Оператора `in` для map нет.
  Исключение — значение-кортеж: если тип значения `V` — кортеж из стольких
  же элементов, сколько имён слева (`map[string](int, int)` и
  `var (lo, hi) = m[k]`), имена разбирают само значение (отсутствующий
  ключ — нулевые элементы), а не comma-ok. Comma-ok — только два имени над
  `V`, который не 2-кортеж (`var (t, ok) = m[k]` для `V = (int, int, int)`
  — comma-ok). Наличие ключа у map со значением-N-кортежем даёт N + 1 имя:
  элементы и `ok` (`var lo, hi, ok = m[k]`, так же в присваивании).
  В обобщённом теле форма решается по объявленному типу шаблона, а не по
  экземпляру: если тип значения — параметр типа (`m map[K]V`), два имени
  над `m[k]` — всегда comma-ok, даже когда `V` подставлен 2-кортежем.
  Разбор значения действует только для конкретного кортежа в объявлении
  (`map[K](A, B)`).
- `s[i]` строки — байт (`byte`) по смещению `i`, выход за границы — паника;
  `for i, ch in s` перебирает кодовые точки.

## Типы

| Категория | Типы |
|-----------|------|
| Целые | `int` (64 бит), `int8`, `int16`, `int32`, `int64`, `uint*`, `byte` |
| Дробные | `float` (64 бит), `float32` |
| Прочие примитивы | `bool`, `string`, `char` (Unicode code point) |
| Составные | `[]T` (срез), `[N]T` (массив), `map[K]V`, `*T` (указатель) |
| Пользовательские | `struct`, `interface`, `enum`; обобщённые `List<int>`, `Pair<A, B>` (см. «Generics») |
| Специальные | `void`, `T!` (результат или ошибка), `Task<T>` (асинхронный результат) |

`char` — 32-битная кодовая точка, как `rune` в Go: `char - char` даёт
`int`, `char + n`, `n + char` и `char - n` (`n` — любое целое) дают `char`
(`c += n`, `c -= n` тоже), сравнения `== != < <= > >=`. Прочие операции
(`c + c`, `c * n`) — ошибка, нужен `int(c)`. Арифметика идёт в `int`, а
результат приводится к `char` как `char(n)`: младшие 32 бита, без проверки
на допустимую кодовую точку и без паники (как переполнение `int32` в Go);
недопустимая кодовая точка печатается как U+FFFD.

Строковые литералы: `"..."` с escape-последовательностями и raw-строки в
обратных кавычках `` `...` `` — без обработки escape, многострочные (для
regex, путей Windows, SQL). Строки — неизменяемые, UTF-8. Срезы и map — как в Go (ссылочная семантика
на общий буфер). Подсрез записывается диапазоном: `s[1..3]`, `s[..2]`, `s[2..]`.
Литерал среза там, где ожидается массив `[N]T` (инициализация с типом,
присваивание, аргумент, `return`, поле), — литерал массива: `var a
[3]string = ["a", "b", "c"]`, вложенные `[[1, 2], [3, 4]]` для `[2][2]int`.
Число элементов должно быть ровно `N`, иначе ошибка `array literal has 2
elements, want 3`. Формы `[3]T{...}` и `[...]T{...}` нет: литералы
коллекций в Zell пишутся без типа перед `{` (тип берётся из ожидаемого).

### Псевдонимы типов

`type Name = Type` на верхнем уровне вводит прозрачный псевдоним: новое
имя того же типа, а не новый номинальный тип. `Name` и `Type` взаимозаменяемы
везде — в присваиваниях, сигнатурах (метод с псевдонимом в сигнатуре
реализует интерфейс с исходным типом и наоборот), наборах методов,
литералах (`P{X: 1}` для `type P = Point`; `Inventory{"apple": 3}` для
`type Inventory = map[string]int` и `Ints{1, 2}` для `type Ints = []int`,
где `Name: v` в литерале map — ключ из переменной `Name`, как в Go),
статических методах и
вариантах (`Shade.Green`), преобразованиях (`Celsius(36)` для
`type Celsius = float`); `reflect.TypeOf<Name>()` возвращает исходный тип.

```zell
type Handler = func(Request) Response!
type Ints = []int
type P = geo.Point
```

- Видимость — как у других объявлений (с заглавной буквы — экспорт);
  псевдоним может ссылаться на другой псевдоним, цикл (`type A = []A`,
  `type A = B` + `type B = A`) — ошибка «invalid recursive type alias».
- `type` — контекстное ключевое слово: только в `type Name =` на верхнем
  уровне; в остальных местах это обычное имя (`var type = "x"`).
- Обобщённые псевдонимы (`type Pair<T> = (T, T)`) и локальные (внутри
  функции) не поддерживаются; атрибуты на псевдониме — ошибка (кроме
  `@cfg`). В исходниках stdlib на Zell (`sema/stdlib_src`) псевдонимы
  пока не поддерживаются.

## Функции

Параметр — `имя тип`. Возвращаемый тип — после закрывающей скобки, без
двоеточия. `void` опускается.

```zell
func Add(a int, b int) int { return a + b }
func Add(a, b int) int { return a + b }       // группировка как в Go
func Swap(a, b int) (int, int) { return b, a }
func Log(msg string) { println(msg) }

var (x, y) = Swap(1, 2)
```

- Несколько возвращаемых значений — кортеж. Литерал кортежа с известным
  ожидаемым типом (`return`, присваивание, инициализация с типом,
  аргумент) типизируется поэлементно, так что `nil` получает тип элемента:
  `return (nil, false)` в функции с результатом `(*Order, bool)`.
  Элемент кортежа — `t.0`, `t.1`, … (также `t._0`, имя из рефлексии);
  `t.0.1` — вложенный доступ (число сразу после `.` — всегда индекс, не
  дробь); индекс вне кортежа — ошибка `tuple (int, string) has no element
  2`. `println((3, "x"))` печатает `(3 x)`, вложенные кортежи — рекурсивно
  (`((1 2) z)`), `fmt` `{0}`/`%v` — так же.
- Замыкания: `var f = func(x int) int { return x * 2 }`, короткая форма
  `var f = (x int) => x * 2`.
- У параметров короткой лямбды тип можно опустить, если он следует из
  ожидаемого функционального типа (аргумент вызова, типизированная
  переменная, поле): `var g func(string) bool = (s) => s != ""`,
  `slices.Map(xs, (x) => x * 2)` (в вызове generic-функции — после вывода
  параметров типа из остальных аргументов), `ctx.Users.Where((u) => u.Age >
  18)`. Единственный нетипизированный параметр можно писать без скобок:
  `u => u.Age > 18`, `s => s != ""`, `async u => ...`, `u => { ... }` (то же,
  что `(u) => ...`; `=>` не имеет другого смысла, неоднозначности нет; перенос
  строки после `=>` допустим). Несколько параметров — только в скобках.
  Блочная лямбда без типа результата берёт его из ожидаемого типа
  (`ctx.Transaction(async () => { ...; await ctx.SaveChanges()? })` —
  `void!`). Без ожидаемого типа — ошибка `cannot infer the type of lambda
  parameter u`.
- Лямбда на месте `expr<F>` становится деревом выражения, а не замыканием
  (раздел «Деревья выражений»).
- Функции — значения первого класса, тип `func(int) int`.
- **Переменное число аргументов**, как в Go: последний параметр
  `args ...T` — это `[]T`. Вызов передаёт в него оставшиеся аргументы
  (новым срезом; ни одного — пустой срез) или один срез, развёрнутый
  через `xs...`: `sum(1, 2, 3)`, `sum(xs...)`, `join(", ", parts...)`.
  `...` допустим только у последнего аргумента и только для
  вариативного параметра (ровно после фиксированных: `f(a, xs...)`);
  срез передаётся как есть, без копии (как в Go). Так же разворачиваются
  срезы во встроенных вариативных функциях: `append(xs, ys...)` (все
  элементы `ys`, `append(xs, xs...)` допустим), `fmt.Sprintf(format,
  args...)` с `args []any` (вид каждого аргумента — по его
  динамическому типу), `task.All(ts...)` / `task.Any(ts...)` (то же, что
  `task.All(ts)`). Вариативными бывают обычные функции и методы
  структур и enum; в generic-функциях, лямбдах, методах интерфейсов и
  функциональных типах `...T` нет — значение вариативной функции имеет
  тип `func(..., []T) R`, а её значение-метод принимает срез. Ошибки:
  `cannot use ... in call to non-variadic f`, `can only use ... with the
  final argument`, `not enough arguments in call to f: expected at least
  N`.

## Структуры и методы

Методы объявляются внутри структуры. Приёмник неявный — `this`. Метод
по умолчанию работает с указателем на структуру, как `func (s *S)` в Go.

```zell
struct Point {
    X float
    Y float

    func Length() float {
        return math.Sqrt(this.X * this.X + this.Y * this.Y)
    }

    func Move(dx, dy float) {
        this.X += dx
        this.Y += dy
    }

    static func New(x, y float) Point {
        return Point{X: x, Y: y}
    }
}

var p = Point.New(1, 2)
var q = Point{X: 3, Y: 4}
```

- Конструкторы: литерал `Point{X: 1, Y: 2}` (в литерале двоеточие остаётся,
  как в Go) или `static func`.
- Поля с заглавной буквы — публичные, со строчной — приватные.
- Встраивание (композиция) как в Go: поле без имени `Base` поднимает его
  поля и методы (в том числе generic-методы: `ctx.Raw<User>(...)` при
  встроенном `data.Context`).
- Поле может иметь значение по умолчанию — константу: `Port int = 8080`.
  Оно подставляется в литерал, где поле не указано, и в `var c Config`
  без инициализатора; опущенное поле-структура без своего значения по
  умолчанию получает значения по умолчанию своих полей (рекурсивно:
  `struct C { In L }` при `struct L { N int = 5 }` даёт `C{}.In.N == 5`);
  остальные нулевые значения (`new Config`, элементы массивов,
  отсутствующий ключ map) остаются нулевыми.
- Структуры нельзя сравнивать через `==` (`operator == is not defined
  on ...`): сравнивают поля или пишут метод `Equal`.
- Свободные `func` на уровне пространства имён допустимы для утилит и `main`.
- **Значения-методы**, как в Go: `x.M` без вызова — замыкание типа
  `func(параметры M) результат`, связанное с получателем. Получатель
  вычисляется один раз, там, где написано `x.M`, и удерживается
  замыканием (освобождается вместе с ним). Методы работают с указателем,
  поэтому, как `(&x).M` в Go, переменная-структура связывается по адресу
  (своей ячейкой: метод видит её последующие изменения, а его изменения
  видны в ней); указатель и значение интерфейса (вместе с динамическим
  значением) захватываются как есть; enum и прочие значения (результат
  вызова) копируются. Поле или элемент-структура (`h.c.M`, `xs[i].M`)
  дали бы внутренний указатель, который нельзя удерживать, — ошибка
  `cannot take the method value M of a struct field or element`. Метод
  `async` даёт асинхронное замыкание (`func(...) Task<T>`), метод с `T!` —
  замыкание с `T!`. Работает для методов структур (в том числе
  экземпляров generic-структур и продвинутых через встраивание), enum,
  интерфейсов и ограничений параметров типа; generic-метод с собственными
  параметрами типа по-прежнему нужно вызывать.
- **Выражения-методы**: `T.M` для структуры `T` — функция, принимающая
  получатель `*T` первым параметром: `var f = Counter.Add` имеет тип
  `func(*Counter, int) int`, `Counter.Add(&c, 1)` — вызов с явным
  получателем.

```zell
var c = Counter{}
var inc = c.Inc          // связан с &c
inc()                    // c.n == 1
var add = Counter.Add    // func(*Counter, int) int
add(&c, 2)
```

## Атрибуты

Атрибуты — метаданные на объявлениях, доступные через рефлексию и
компилятору. Пишутся через `@` перед объявлением, пространства имён,
структур, полей, методов, функций, вариантов enum и параметров.

```zell
@json(name: "user_id")
struct User {
    @json(name: "id")       Id    int
    @json(omitEmpty: true)  Email string
    @json(skip: true)       cache string

    @deprecated("use Save")
    func Store() void! { ... }
}
```

- Атрибут — это обычная структура, помеченная `@attribute`; её поля —
  параметры атрибута. Аргументы — константы времени компиляции.
- Встроенные: `@reflect` (принудительно сохранить метаданные типа, в
  том числе методы), `@deprecated`, `@inline`, `@test`, `@attribute`,
  `@embed("путь")`, `@allowCycle` (на структуре или перечислении:
  не выдавать для типа предупреждение W0001), `@acyclic` (обещание, что
  значения типа не образуют циклов: без W0001 и без участия в сборке
  циклов; проверяется `--leak-check`), см. «Циклы», `@required` (на поле
  атрибут-структуры: аргумент обязателен, см. «Свои атрибуты»).
- `@intrinsic` — только в исходниках стандартной библиотеки (в
  пользовательском коде — ошибка `@intrinsic is reserved for the standard
  library`). Помечает объявление-заглушку вызова, который компилятор
  понижает сам, ради документации и IDE: обобщённые методы
  `testing.T.Must<V>(x V!) V` / `MustFail<V>(x V!) error` (вызов
  `t.Must(x)` перехватывается до разрешения метода; любой другой путь к
  заглушке — явные аргументы типа `t.Must<int>(x)` — ошибка компиляции
  `testing.T.Must is a compiler intrinsic: call it directly, without type
  arguments`, тело никогда не генерируется) и структура `task.Task<T>`,
  которая лишь описывает методы встроенного `Task<T>` (`Cancel`): компилятор
  её не регистрирует, `task.Task` — не имя.
- `@embed("путь")` на глобальной `var`/`const` вшивает файл при
  компиляции (путь относительно исходного файла; отсутствующий файл —
  ошибка компиляции): `var X string` (текст UTF-8), `var X []byte`,
  `const X = ""` (значение-заглушка заменяется текстом файла), `var X
  embed.FS` — каталог (все файлы рекурсивно) или шаблон `dir/*.ext`;
  `embed.FS` даёт `ReadFile`/`ReadString`/`Has`/`Names`/`List` по путям
  `dir/имя`. У `var` с `@embed` нет инициализатора.
- Атрибут-структуры могут объявляться и в stdlib на Zell
  (`@binary(endian: "big")` из `encoding.binary`, `@cli.flag(...)` из
  `cli`): они пишутся через пространство имён, как обычные.
- Ключевые слова допустимы как имена аргументов атрибута и полей
  структур (`@cli.flag(default: "8080")`, `@Conf(enum: "a,b")`): аргумент
  `enum:` задаёт поле `enum`. Исключения — `func`, `static`, `async`
  (начинают метод) и `_`. Такое поле читается как обычно (`c.enum`;
  ключевые слова инструкций — `c.for`, `c.var` — только вплотную к точке)
  и инициализируется литералом `Conf{enum: "x"}`.
- Каждый применённый атрибут — константное значение своей структуры
  (аргументы, значения полей по умолчанию, иначе нулевые значения), вшитое в таблицы рефлексии;
  у встроенных это структуры `reflect` (`json`, `deprecated`, ...).
  Читается через `Attribute<A>()` / `Attributes<A>()` (раздел «Рефлексия»).
- Библиотечные: `@json`, `@log(skip: true)` (поле не попадает в `{@X}` логгера), `@xml`, `@db(column: "...")`, `@validate(...)`.
- Неизвестный атрибут — ошибка компиляции (в отличие от строковых тегов Go).
- Видимость атрибута — обычная видимость его структуры: атрибут для других
  пакетов называется с заглавной буквы и пишется через пространство имён
  (`@zconf.Conf(...)`); атрибут со строчной буквы (`@range`) — приватный
  для своего пространства имён. Встроенные и stdlib-атрибуты (`@json`, `@cli.flag`)
  строчные по историческим причинам и доступны везде.

### Свои атрибуты

Атрибут объявляется как структура с `@attribute`. Поля — параметры,
значения по умолчанию допускаются.

```zell
namespace app.validation

import reflect

@attribute(targets: [reflect.Target.Field])
struct range {
    min int
    max int
    message string = "value out of range"
}

@attribute(targets: [reflect.Target.Struct, reflect.Target.Func], repeatable: true)
struct tag {
    name string
}
```

```zell
@tag("entity")
@tag("audited")
struct User {
    @range(min: 0, max: 150)  Age  int
    @range(1, 64)             Name string   // позиционно, по порядку полей
}
```

- Аргументы передаются по имени или позиционно. Опущенный аргумент
  (как именованные аргументы C#) получает значение поля по умолчанию, а
  если его нет — нулевое значение типа (`0`, `""`, `false`, пустой срез,
  первый вариант enum, для вложенной атрибут-структуры — её поля по тем же
  правилам): `@rule(min: 1)` у атрибута с пятью полями без значений по
  умолчанию — корректная запись. Поле, которое обязано быть задано,
  помечается встроенным `@required` (`@required path string`); его
  отсутствие — ошибка «missing argument path for attribute @route (the
  field is @required)». `@required` допустим только на поле
  `@attribute`-структуры (в файле с `import data` ту же роль играет
  `data.required`: признак — имя атрибута). Один параметр — короткая
  форма `@deprecated("why")`.
- `targets` ограничивает места применения: `Namespace`, `Struct`,
  `Interface`, `Enum`, `Variant`, `Field`, `Func`, `Param`. Без указания —
  везде. Нарушение — ошибка компиляции.
- `repeatable: true` разрешает несколько одинаковых атрибутов на одном
  объявлении; иначе повтор — ошибка.
- Допустимые типы параметров: примитивы, `string`, enum, срезы из них и
  другие атрибут-структуры. Значения вычисляются при компиляции.
- Атрибут — только данные. Он не выполняет код при компиляции и не меняет
  генерируемый код; поведение живёт в библиотеке, которая его читает
  (через `f.Attribute<range>()`, `f.Attributes<tag>()` для повторяемых, или
  compile-time `reflect.Fields<T>()`, см. раздел «Рефлексия»).

## Интерфейсы

Структурная типизация, как в Go: структура (или enum с методами) реализует
интерфейс, если имеет все его методы. `implements` — необязательная проверка
на месте объявления (см. ниже).

```zell
interface Shape {
    func Area() float
}

struct Circle {
    R float
    func Area() float { return 3.14159 * this.R * this.R }
}

func Describe(s Shape) {
    println(s.Area())
}
```

### Методы по умолчанию, встраивание и `sealed`

- Интерфейс может содержать методы с телом (методы по умолчанию),
  выраженные через остальные его методы; реализация обязана дать только
  методы без тела. Состояния у интерфейса нет, `this` в таком теле —
  значение интерфейса: его можно передать дальше как интерфейс, вызовы
  через него диспетчеризуются динамически. Метод типа с тем же именем
  переопределяет метод по умолчанию (и при вызове через интерфейс).
  Методы по умолчанию не бывают `static`, `async` или обобщёнными.

  ```zell
  interface Logger {
      func Log(level int, msg string)
      func Info(msg string) { this.Log(1, msg) }   // по умолчанию
  }
  ```

  Метод по умолчанию вызывается и на значении типа, реализующего интерфейс
  (`console.Info("x")`, в том числе в обобщённом теле через ограничение
  `T: Logger`): значение приводится к интерфейсу (переменная-структура —
  по адресу, так что изменения через методы видны в ней самой; `*S`
  удовлетворяет ограничению-интерфейсу, как и `S`). Методы по умолчанию
  могут объявлять и интерфейсы stdlib на Zell (`hash.Hasher.WriteString`
  по умолчанию пишет байты строки через `Write`). Если такой метод дают два
  разных интерфейса, которые тип реализует, вызов — ошибка `ambiguous
  default method` (приведите значение к нужному интерфейсу явно).
  Реализация: метод по умолчанию компилируется один раз как функция от
  значения интерфейса; слот vtable типа, у которого нет своего метода,
  указывает на переходник, собирающий `{data, vtable}` (ABI в
  `compiler/src/codegen/mod.rs`).
- `interface ReadWriter { Reader; Writer }` встраивает интерфейсы: имя
  интерфейса на отдельной строке тела добавляет его методы, в том числе
  методы по умолчанию (одноимённые методы должны совпадать по сигнатуре;
  собственный метод встраивающего интерфейса имеет приоритет). Цикл
  встраивания (`A { B }`, `B { A }`) — ошибка `embeds itself`.
- Значение интерфейса неявно приводится к интерфейсу с подмножеством его
  методов (`var n Named = shape`; отсутствующие методы по умолчанию не
  мешают); `case Mover m:` в `switch` по интерфейсу или `any` проверяет,
  реализует ли динамический тип другой интерфейс.
- `println` значения `any` печатает его динамическое значение.
- `struct Circle implements Shape, fmt.Stringer { ... }` (и `enum E
  implements I { ... }`) — проверка на месте объявления с той же
  формулировкой, что при приведении (`Square does not implement Shape:
  missing method Perimeter`); методы по умолчанию не требуются, не
  интерфейс после `implements` — ошибка `is not an interface`. Семантика
  остаётся структурной: тип без `implements` с теми же методами тоже
  реализует интерфейс.
- `sealed interface Shape { ... }` — реализации только в том же
  пространстве имён (в любом его файле). Реализации — все структуры и enum
  этого пространства имён, имеющие методы интерфейса (`implements` не
  обязателен); тип другого пространства имён не приводится к нему ни явно
  через `implements`, ни неявно: `sealed interface Shape can only be
  implemented in namespace app.shapes`. Статически к `sealed`-интерфейсу
  приводится только `sealed`-интерфейс того же пространства имён.
  `switch` по типу без `default` над таким интерфейсом проверяется на
  полноту (`switch on sealed interface Shape is not exhaustive: missing
  Triangle`); `case T x` и `case *T x` оба покрывают `T`. Полный `switch`
  (как и `switch` по enum, перечисляющий все варианты) — завершающий
  оператор: `return` после него не нужен; если во время выполнения не
  совпал ни один `case` (например, nil-интерфейс), программа паникует.

- **Асинхронные методы.** `async`-метод `async func M(args) R` реализует
  метод интерфейса `func M(args) Task<R>`, а `async func M(args) R!` —
  `func M(args) Task<R!>`: вызов через интерфейс даёт ту же задачу, что
  прямой вызов метода. В самом интерфейсе `async func M(args) R` (без
  тела) — сокращение ровно для `func M(args) Task<R>`: оба написания
  взаимозаменяемы, их реализуют и `async`-метод, и обычный метод,
  возвращающий `Task<R>`, а у вызова тип `Task<R>` (`await r.M()`).
  `async`-метод не реализует метод интерфейса, возвращающий не `Task`
  (`func M() R`): ошибка `method M has type async func() R, want func()
  R: an async method implements an interface method returning Task<R>`.
  Методы по умолчанию `async` не бывают (см. выше).

  ```zell
  interface Repo {
      async func Get(id int) string!     // = func Get(id int) Task<string!>
      func Count() Task<int>
  }

  struct Memory {
      items []string
      async func Get(id int) string! { ... }
      async func Count() int { return len(this.items) }
  }
  ```

  Поведение — как у прямого вызова, сохранённого в `Task<R>`: тело
  начинает работать синхронно в задаче вызывающего до первой
  приостановки; паника в нём — `task.ErrPanic` у ожидающего `Task<R!>` и
  повторная паника у ожидающего `Task<R>`; отмена — через задачу вызова
  (или текущую задачу вызывающего до первой приостановки).
  *Реализация:* слот vtable такого метода — переходник `(data, args) ->
  Task<R>`, который вызывает рампу метода с локальным слотом результата
  (без ожидающего кадра) и возвращает `res.task`, а если вызов ни разу не
  приостановился — завершённую задачу из `res.value`
  (`zell_task_completed`, ABI.md 10.3). Вызов через интерфейс поэтому
  стоит косвенного вызова плюс, при синхронном завершении, одной
  завершённой задачи; связанного ожидания (ABI.md 10.3, «Frame-linked
  await») через интерфейс пока нет.

Наследования классов нет; встраивание структур — композиция без
виртуальной диспетчеризации. Как выражать паттерны: `docs/PATTERNS.md`.

## Перегрузка операторов

Операторы определяются только через фиксированный набор встроенных
интерфейсов; произвольных операторов нет.

| Оператор | Интерфейс | Метод |
|---|---|---|
| `a + b`, `a - b`, `a * b`, `a / b`, `a % b` | `Add`, `Sub`, `Mul`, `Div`, `Rem` | `func Add(other T) T` |
| `-a` | `Neg` | `func Neg() T` |
| `a @ b` | `MatMul` | `func MatMul(other T) T` |
| `a[i]`, `a[i] = v` | `Index`, `IndexSet` | `func Index(i I) V`, `func IndexSet(i I, v V)` |
| `a == b`, `a != b` | `Equatable` | `func Equals(other T) bool` |
| `<`, `<=`, `>`, `>=` | `Ordered` | `func Compare(other T) int` |
| `a += b` и прочие (`-= *= /= %= @=`) | через соответствующий бинарный | — |

```zell
struct Vec {
    X float
    Y float
    func Add(o Vec) Vec { return Vec{X: this.X + o.X, Y: this.Y + o.Y} }
    func Mul(k float) Vec { return Vec{X: this.X * k, Y: this.Y * k} }
    func Neg() Vec { return Vec{X: -this.X, Y: -this.Y} }
}

var v = (a + b) * 0.5 + -c      // a.Add(b).Mul(0.5).Add(c.Neg())
v += a                          // v = v.Add(a)
```

Правила (реализация — `compiler/src/sema/opover.rs`):

- Перегружаются операторы над значениями **структур и enum** (не над
  числами, строками и указателями: `p == q` для `*T` сравнивает адреса);
  индексация — также через указатель на структуру (`p[i]`).
- Метод выбирает **левый операнд**: `a + b` — это `a.Add(b)`. Правый
  операнд проверяется по типу параметра метода (с обычными неявными
  приведениями и нетипизированными константами), поэтому метод может
  принимать и другой тип: `func Mul(k float) Vec` разрешает `v * 2`, но не
  `2 * v` (`mismatched types ... the left operand selects the operator
  method`). Тип результата — тип результата метода: `Time.Sub(Time)
  Duration` даёт `t1 - t0` типа `Duration`; метод с результатом `T!` делает
  выражение ошибочным (`(a / b)?`, `try a / b else ...`, как `big.Decimal`).
- Методы вызываются напрямую (без динамической диспетчеризации), в том
  числе продвинутые через встраивание. Операторные методы не бывают
  `async` и обобщёнными; `Equals` должен возвращать `bool`, `Compare` —
  `int`, `IndexSet` — ничего.
- `==`/`!=` и `< <= > >=` используют `Equals`/`Compare`, только если они
  есть; иначе действуют встроенные правила (простые enum сравниваются по
  тегу, структуры без `Equals` — ошибка с подсказкой `help: declare func
  Equals(other T) bool`). `a != b` — это `!a.Equals(b)`, `a < b` —
  `a.Compare(b) < 0`. Сравнение с `nil` не перегружается.
- `a op= b` — это `a = a op b`, левая часть вычисляется дважды, поэтому она
  должна быть переменной, полем или элементом с простым индексом;
  `a[i] op= v` — `a.IndexSet(i, a.Index(i) op v)`, индекс вычисляется
  один раз.
- Не перегружаются: `&&`, `||`, `!`, `=`, `.`, `&` (и как адрес, и
  побитовое), `|`, `^`, `<<`, `>>`, `*`(deref), `?`, `..` и срезы `a[i..j]`;
  отсутствующий метод — ошибка с именем оператора (`operator / is not
  defined on Money: Money has no method Div`).
- `@` между операндами — `MatMul` с приоритетом `*`; `@` в начале
  объявления (поля, метода, параметра) — атрибут. `@=` — составное
  присваивание.
- **Ограничения generics.** `Add`, `Sub`, `Mul`, `Div`, `Rem`, `Neg`,
  `MatMul` — встроенные ограничения (если в области видимости нет типа с
  таким именем): `T: Add` разрешает `+` (и `+=`) на `T` и выполняется для
  чисел с этим оператором (`Add` — и для `string`, `Rem` — для целых) и для
  типов с методом ровно `func Add(other T) T` (`Neg`: `func Neg() T`).
  `Ordered` выполняется также для типов с `func Compare(other T) int`,
  `Equatable` — для типов с `func Equals(other T) bool` (`Comparable`
  остаётся множеством типов со встроенным `==`, годных в ключи `map`).
  В экземпляре обобщённой функции оператор над `T = Vec` вызывает метод,
  поэтому `Sum<T: Add>`, `Max<T: Ordered>` и обобщённые структуры с
  операторными методами (`struct Vec2<T: Add> { ... func Add(o Vec2<T>)
  Vec2<T> }`) работают и с числами, и с типами-значениями.
- Используется в `math.big` (`Int`, `Rat`, `Decimal`; `Int./` — деление
  с усечением, как у `int`, евклидово — `DivEuclid`; `Decimal./` и `%`
  возвращают `Decimal!`), `time` (`Duration` с `* /` на `int`, `Time +
  Duration`, `Time - Time`), `math.complex`, `collections.BitSet`
  (`b[i]`, `b[i] = true`).

## Перечисления

```zell
enum Color { Red, Green, Blue }

enum Result {
    Ok(value int)
    Fail(code int)
}

var c = Color.Red
switch r {
    case Result.Ok(v):   println(v)
    case Result.Fail(c): println("fail", c)
}
```

После вариантов перечисление может объявлять методы; `this` — само
значение (копия, а не указатель). Статических методов у перечислений нет.

```zell
enum Color {
    Red
    Green

    func IsWarm() bool { return this == Color.Red }
}

println(Color.Green.IsWarm())
```

- Нулевое значение простого перечисления — первый вариант.
- Вариант не может содержать само перечисление по значению (напрямую, через
  структуру, массив или кортеж): `enum E { Num(n int), Neg(e E) }` — ошибка
  `invalid recursive type E: it contains itself by value (use a pointer)`;
  рекурсия — через указатель (`Neg(e *E)`), срез или map, как у структур.
- Повторяющиеся константные `case` (`case 1, 2:` и `case 2:`) — ошибка
  компиляции.

## Generics

Обобщёнными могут быть функции, методы (в том числе методы обычных
структур), структуры и перечисления. Интерфейсы обобщёнными быть не могут
(пока). Реализация — мономорфизация, как в Rust и для структур в C#: каждый
различный набор аргументов типа компилируется в отдельную функцию/структуру,
кодогенерация и рантайм про generics ничего не знают.

```zell
func Max<T: Ordered>(a, b T) T {
    if a > b { return a }
    return b
}

struct Stack<T> {
    items []T
    func Push(x T) { this.items = append(this.items, x) }
    func Pop() T! { ... }
}

enum Option<T> {
    Some(value T)
    None
}

struct Pair<A, B> {
    First A
    Second B
    func Swap() Pair<B, A> { return Pair<B, A>{First: this.Second, Second: this.First} }
}

var m = Max(3, 7)                 // вывод: Max<int>
var f = Max<float>(1, 2)          // явные аргументы; 1 и 2 становятся float
var s = Stack<string>{}           // литерал экземпляра
var o = Option<int>.Some(1)       // вариант экземпляра enum
var g = Max<int>                  // экземпляр как значение func(int, int) int
switch o { case Option.Some(v): println(v) }   // в образце аргументы не пишутся
var t = l.Show<string>("x")       // обобщённый метод
```

**Синтаксис.** Параметры типа — после имени объявления: `<T>`, `<K, V>`,
`<T: Ограничение>`. Аргументы типа — после имени: `List<int>` в типах,
`F<int>(x)`, `S<int>{...}`, `E<int>.V`, `S<int>.Static()` и `F<int>` как
значение в выражениях (как в C#: `<...>` считается аргументами типа, если
за `>` идёт `(`, `{`, `.`, `)`, `]`, `}`, `,` или конец оператора). Строка,
заканчивающаяся на `>` или `>>`, завершает оператор (`var x List<List<int>>`).
Внутри обобщённого кода экземпляры пишутся явно: `Pair<B, A>{...}`; без
аргументов литерал допустим, только если ожидаемый тип — экземпляр того же
шаблона.

**Ограничения.**

| Ограничение | Допускает | Операции над `T` в теле |
|---|---|---|
| нет | любой тип | присваивание, передача, возврат, `var z T` (нулевое значение) |
| `Ordered` (встроенное) | целые, дробные, `string`, `char`, типы с `func Compare(other T) int` | также `< <= > >= == != +` |
| `Comparable` (встроенное) | числа, `bool`, `char`, `string`, указатели, простые enum | также `== !=`, ключ `map[T]V` |
| `Equatable` (встроенное) | `Comparable` и типы с `func Equals(other T) bool` | также `== !=` |
| `Add`, `Sub`, `Mul`, `Div`, `Rem`, `Neg`, `MatMul` (встроенные) | числа с этим оператором (`Add`: и `string`; `Rem`: целые), типы с операторным методом `func Add(other T) T` | также этот оператор (и `op=`), см. «Перегрузка операторов» |
| интерфейс `I` | тип с методами `I` (структурно) | также методы `I`, преобразование в `I` |

Тело обобщённой декларации проверяется **один раз** против ограничений (как в
Go): `a + b` для `T` без `Ordered` — ошибка в самой декларации, даже без
экземпляров. Затем каждый экземпляр проверяется с конкретными типами
(например, `println(x)` для `T = Point` даёт ошибку с пометкой
`in instantiation of Show<Point>`). Нарушение ограничения в месте
использования: `type Point does not satisfy constraint Ordered` /
`type Sq does not satisfy constraint Shape: missing method Area`; неверное
число аргументов: `wrong number of type arguments for Id: expected 1, got 2`.

**Вывод аргументов типа** (если `<...>` не написаны): объявленные типы
параметров сопоставляются с типами аргументов структурно (`[]T` с `[]int`,
`func(T) U` с `func(int) string`, `Pair<A, B>` с экземпляром `Pair`,
`map[K]V`, `*T`, `T!`, кортежи). Нетипизированные константы обрабатываются
последними: если параметр — ровно `T`, уже выведенный из другого аргумента,
константа получает этот тип (`Max(x, 1)` при `x float`), иначе — тип по
умолчанию (`Max(1, 2)` — `Max<int>`). Параметр, который встречается только в результате, выводится из
ожидаемого типа вызова (`return Empty()` при `func Empty<T>() []T` в
функции с результатом `[]User!` даёт `Empty<User>`; `!` ожидаемого типа
снимается, если результат шаблона не `T!`). Разные типы для одного параметра
(`conflicting types for type parameter T`) и невыводимый параметр
(`cannot infer type parameter T`, например `Id(nil)`) — ошибки. Лямбды
всегда имеют типы параметров, поэтому выводятся по своему типу.

**Мономорфизация.** Экземпляр `(шаблон, аргументы)` создаётся один раз и
кэшируется; его имя читаемое (`Max<int>`, `Pair<string, int>.Swap`), символ —
`zell_<ns>__Max__int` (видно в `zell check --dump-hir`). Методы обобщённой
структуры инстанцируются вместе с ней; обобщённые методы — при вызове.
Рекурсия в обобщённом коде допустима; бесконечное разрастание
(`F<T>` вызывает `F<[]T>`) обрывается ошибкой после 48 уровней вложенности.
Значения экземпляров освобождаются как обычные значения своих типов
(`Drop` экземпляра работает).

**`collections`** написана на Zell (обобщённые структуры поверх срезов и
`map`, встроены в компилятор):

| Тип | Методы |
|---|---|
| `List<T>` | `New()`, `Add(x)`, `Len()`, `Get(i)`, `Set(i, x)`, `Insert(i, x)`, `Remove(i)`, `Contains(x)` и `IndexOf(x)` (требуют `T: Comparable` в месте вызова), `Clear()`, `Items() []T` (копия) |
| `Map<K: Comparable, V>` | `New()`, `Set(k, v)`, `Get(k) V` (нулевое значение, если нет), `Has(k)`, `Remove(k)`, `Len()`, `Clear()`, `Keys() []K`, `Values() []V` — в порядке вставки |
| `Set<T: Comparable>` | `New()`, `Add(x)` (идемпотентно), `Has(x)`, `Remove(x)`, `Len()`, `Clear()`, `Items() []T` — в порядке вставки |
| `Queue<T>` / `Stack<T>` | `New()`, `Push(x)`, `Pop() T!` и `Peek() T!` (ошибка на пустой), `Len()` |

`for x in list`, `for i, x in list`, `for x in set`, `for k, v in m` (и
`for k in m`) обходят элементы в этом порядке. Пустое значение (`List<int>{}`,
`var m Map<string, int>`) готово к использованию.

## Указатели

Как в Go: `&x` берёт адрес, `*p` разыменовывает, доступ к полям через
указатель автоматически (`p.X`). Арифметики указателей нет. Нулевое
значение — `nil`.

```zell
var p = Point{X: 1, Y: 2}
var ptr = &p
ptr.X = 10
var copy = *ptr
```

Структуры — значения; передаются копированием, если не брать указатель.
Выделение в куче — `new Point{...}` возвращает `*Point`. Переменная, адрес
которой берётся, переносится в кучу. Указатели управляемые (подсчёт
ссылок); указатель внутрь объекта (`&s.f`, `&a[i]`) можно только
разыменовать или передать параметру, который его не сохраняет — см.
«Память → Указатели и владение». `weak *T` — слабый указатель.

## Ошибки

Ошибки — значения, как в Go. Исключений нет. Отличие от Go в том, что язык
даёт три коротких конструкции вместо `if err != nil`.

### 1. Объявление: тип `T!`

Функция, которая может завершиться ошибкой, добавляет `!` к возвращаемому
типу. `void!` — функция без результата, но с возможной ошибкой.

```zell
func ParseInt(s string) int! {
    if s == "" {
        return error("empty string")
    }
    ...
    return n
}

func Save(path string, data []byte) void! { ... }
```

`error(msg)` создаёт ошибку. `return` в такой функции принимает либо значение
`T`, либо ошибку; компилятор различает их по типу.

### 2. Проброс наверх: оператор `?`

`expr?` возвращает значение, если ошибки нет, и немедленно выходит из текущей
функции с этой ошибкой, если она есть. Это замена `if err != nil { return err }`.
Работает только внутри функции с типом `T!` (или внутри блочного `try`,
см. ниже).

```zell
func ReadConfig(path string) Config! {
    var text = io.ReadFile(path)?
    var cfg = ParseConfig(text)?
    return cfg
}
```

Чтобы добавить контекст при пробросе: `io.ReadFile(path)?("reading config")`
оборачивает ошибку сообщением.

### 3. Обработка на месте: `try`

```zell
// Обработать и выйти / продолжить
var cfg = try ReadConfig("app.toml") catch err {
    println("config:", err)
    return
}

// Значение по умолчанию
var port = try ParseInt(env.Get("PORT")) else 8080

// Проверка без значения
try Save("out.txt", data) catch err {
    println("save failed:", err)
}
```

- Блок `catch` обязан либо завершить функцию (`return`, `panic`), либо не
  использовать значение `try`. Так переменная после `try ... catch` всегда
  инициализирована.
- `try ... else` подставляет значение по умолчанию и отбрасывает ошибку.

### Блочная форма `try`

Когда нужно обработать ошибку для нескольких операций разом, `try` берёт
блок. Внутри него `?` переходит в `catch` этого блока, а не возвращает из
функции:

```zell
try {
    var text = io.ReadFile(path)?
    var cfg = ParseConfig(text)?
    Apply(cfg)?
} catch err {
    println("config:", err)
    return
}
```

- Ошибки внутри блока всё так же помечаются `?`; неявного проброса нет.
- Чтобы пробросить дальше, в `catch` пишут `return err` (в функции с `T!`).
- Переменные блока видны только в нём; результат выносят через переменную,
  объявленную до `try`.
- `catch` блочной формы не обязан завершать функцию: после него выполнение
  продолжается. `else` у блочной формы нет.
- Блоки вкладываются; `?` идёт в ближайший `catch`. `?` внутри самого
  `catch` или внутри лямбды, объявленной в блоке, к этому `try` не
  относится (идёт во внешний `try` или возвращает из функции).
- Блочный `try` разрешает `?` в любой функции, даже без `T!`.
- При переходе в `catch` освобождаются временные значения и переменные
  блока (как при `break`); `defer` функции не выполняются — функция
  продолжается.
- Если из многострочного кода нужно значение, идиоматично вынести его в
  функцию с типом `T!` и использовать `?` или `try f() catch`.

### Игнорирование и обязательность

Значение типа `T!` нельзя использовать, не обработав: `var x = ParseInt(s)`
без `?` или `try` — ошибка компиляции. Явно отбросить результат и ошибку
можно через `_ = f()`. Передать необработанный `T!` аргументом тоже нельзя
(`g(f())`); единственное исключение — тестовые `t.Must(f())` и
`t.MustFail(f())` (см. «Компилятор и инструменты», «Тесты с ошибками»).

### Тип ошибки

`error` — встроенный интерфейс:

```zell
interface error {
    func Message() string
}
```

Любая структура с методом `Message()` может быть ошибкой. Это позволяет
делать типизированные ошибки и разбирать их через `switch` по типу:

```zell
struct NotFound {
    Path string
    func Message() string { return "not found: " + this.Path }
}

func Open(path string) File! {
    if !fs.Exists(path) {
        return NotFound{Path: path}
    }
    ...
}

var f = try Open("a.txt") catch err {
    switch err {
        case NotFound e: println("no such file:", e.Path)
        default:         println("open failed:", err)
    }
    return
}
```

### Проверка через цепочку обёрток

Если ошибку обернули контекстом (`?("loading config")` или `errors.Wrap`),
исходная ошибка сохраняется внутри. Для проверки по цепочке служат
`errors.Is` и `errors.As`:

```zell
// Ошибки-значения объявляются как константы и сравниваются через Is
const ErrNotFound = error("not found")
const ErrTimeout  = error("timeout")

var cfg = try ReadConfig("app.toml") catch err {
    if errors.Is(err, fs.ErrNotFound) {
        cfg = DefaultConfig()           // нет файла: это нормально
    } else {
        return err                      // пробросить дальше
    }
}

// Достать типизированную ошибку из цепочки
var nf NotFound
if errors.As(err, &nf) {
    println(nf.Path)
}

// Несколько условий в одном месте
try Connect(addr) catch err {
    switch {
        case errors.Is(err, net.ErrTimeout): retry()
        case errors.Is(err, net.ErrRefused): return err
        default:                             panic(err)
    }
}
```

- `errors.Wrap(err, "context")` оборачивает, `errors.Unwrap(err)` достаёт
  исходную ошибку.
- `errors.Is(err, target)` — есть ли `target` в цепочке (сравнение по
  значению).
- `errors.As(err, &target)` — есть ли в цепочке ошибка типа `target`;
  если да, записывает её.
- Пользовательская ошибка с методом `Unwrap() error` — тоже звено
  цепочки (как в Go): `Is`/`As`/`Unwrap` идут к её причине. `Unwrap()`
  вызывается один раз, когда значение становится `error`; текст
  ошибки — только её `Message()` (причина к нему не дописывается).
- `panic(msg)` — для невосстановимых ситуаций (баг, нарушение инварианта);
  не используется для ожидаемых ошибок.

### Трасса ошибки

Каждая ошибка хранит, где она создана и через какие `?` прошла. Это
**трасса возврата** (как error return trace в Zig), а не стектрейс через
раскрутку стека, поэтому стоит почти ничего:

- `error(...)`, `return SomeError{...}`, `errors.Wrap`, `?("ctx")` записывают
  в ошибку указатель на статическую запись `{файл, строка, функция}`,
  которую компилятор кладёт в секцию только для чтения. Ни раскрутки
  стека, ни аллокаций, ни символизации.
- Каждый `?` дописывает свою запись в небольшой встроенный массив внутри
  объекта ошибки (переполнение уходит в цепочку в куче, что редкость).
  Стоимость одного уровня проброса — запись одного указателя.
- Если на ошибку есть другие ссылки (константа-sentinel `const ErrX =
  error(...)`, значение, сохранённое где-то ещё), сама ошибка не меняется и
  не копируется при пробросе: её трасса накапливается в небольшой
  **отложенной записи** текущего потока, по одной на проброс, а `?` только
  дописывает туда указатель. Запись привязывается к ошибке там, где проброс
  заканчивается: `try ... catch err` делает копию ошибки с трассой
  (copy-on-write, `errors.Is` по-прежнему узнаёт в копии оригинал), если
  обработчик может увидеть трассу — то есть использует `err` иначе, чем
  `err.Message()` и `errors.Is(err, ...)`; иначе запись просто отбрасывается,
  и проброс sentinel-ошибки не аллоцирует вовсе. `?("ctx")` переносит
  запись в обёртку, `try ... else` отбрасывает её, результат `async`-функции
  забирает её с собой перед публикацией задачи. Чужая трасса не меняется
  никогда.
- `errors.Trace` печатает файл записи относительно текущего рабочего
  каталога, если он под ним (абсолютные пути зависимостей, сборка из
  другого каталога), иначе — как его видел компилятор.

```zell
try ReadConfig("app.toml") catch err {
    println(err)                  // config: open app.toml: not found
    println(errors.Trace(err))
}
```

```
config: open app.toml: not found
  created at   app/fs.zl:42      Open
  returned via app/config.zl:17  ReadConfig  ?("config")
  returned via app/main.zl:9     main
```

- `println(err)` печатает только сообщение; трасса показывается явно через
  `errors.Trace(err)` (строка) или `errors.Frames(err)` (срез записей
  `errors.Frame { File string; Line int; Func string; Context string }`,
  по одной на строку трассы; `Context` — текст из `?("...")` или `""`).
- Формат `errors.Trace` точный: только строки трассы (без сообщения),
  через `\n`, без завершающего перевода строки. Первая строка
  `  created at   <файл>:<строка>  <функция>`, затем по одной
  `  returned via <файл>:<строка>  <функция>[  ?("<контекст>")]` на каждый
  `?`, от старых к новым, и последняя — для `try ... catch`, который ошибку
  поймал (`main` в примере выше — такое место). Колонка места выравнивается
  по самому длинному, имя функции — по самому длинному, если за ним идёт
  контекст; колонки разделены двумя пробелами, хвостовые пробелы срезаются.
  Файл — путь в том виде, в каком его получил компилятор; функция — имя
  без пространства имён (`Open`, `Cache.Get`, `main$lambda1`).
- Место создания: `error(...)`, `errors.New`, `errors.Wrap` (начинает
  новую трассу, старая остаётся у обёрнутой ошибки), структура,
  превращённая в `error` (`return Timeout{...}`), вызов функции stdlib,
  вернувшей ошибку, и `return err` для ошибки, у которой места ещё нет
  (так у ошибки-константы `const ErrX = error(...)` местом создания
  становится `return ErrX`). `?` внутри блочного `try` тоже добавляет
  строку `returned via` — это и есть место, где ошибку поймали.
- Кадры внутри стандартной библиотеки в трассу не пишутся (как и в трассе
  паники, где у кода stdlib нет строк): для функции stdlib, написанной на
  Zell, местом создания становится её вызов из пользовательского кода
  (прямой вызов или `await` прямого вызова), так же как для функции
  рантайма; место, которое у ошибки уже есть (пользовательская ошибка,
  прошедшая через код stdlib), сохраняется.
- Копия при записи сохраняет идентичность: `errors.Is(err, ErrX)` верно и
  для копии константы.
- Полный нативный стектрейс по-прежнему снимается при `panic`. Для ошибок
  его планируется включать в отладке (`zell run --debug-errors` или
  `ZELL_ERROR_BACKTRACE=1`: при создании ошибки сохраняются сырые адреса
  кадров, символизация лениво при печати); в 0.1 это не реализовано.
- В release трасса включена; `--no-error-trace` отключает запись для
  случаев, когда ошибки используются как управление потоком в горячем цикле
  (места не генерируются, вызовы опускаются, `errors.Trace` возвращает `""`).

### Как это выглядит вместе

```zell
func LoadUsers(path string) []User! {
    var text = io.ReadFile(path)?("loading users")
    var lines = strings.Split(text, "\n")
    var users []User = []
    for line in lines {
        var u = try ParseUser(line) else continue
        users = append(users, u)
    }
    return users
}
```

Три строки вместо примерно десяти в Go, при той же явности: по `?` и `try`
видно каждое место, где может произойти ошибка.

## Паника

Паника — это ошибка программиста, а не ожидаемая ошибка: `panic(...)`,
разыменование `nil`, выход за границы, деление на ноль, неудачное
приведение, несовпавший исчерпывающий `switch`, нехватка памяти. Ошибки,
которые вызывающий должен обработать, — это `T!` (раздел «Ошибки»).

1. **Паника завершает задачу, в которой произошла.** Нет `recover`, нет
   `try`/`catch` для паник, продолжить выполнение этой задачи нельзя.
   Задача — единица планировщика: тело `async`-функции с момента её
   первой приостановки (до неё функция выполняется в задаче
   вызывающего, раздел «Асинхронность»), `task.Go`/`Spawn`.
2. **Раскрутка задачи** проходит её кадры от самого внутреннего наружу —
   кадры `async`-функций и синхронные кадры (обычные `func`, замыкания,
   вызванные из задачи, вперемешку с `async`) — и в каждом выполняет
   отложенные `defer` (последний первым; `defer await` пропускается, см.
   `defer` перед разделом «Асинхронность») и освобождает живые значения:
   временные значения посреди выражения, затем локальные (`Drop` — в
   порядке, обратном объявлению, как при обычном выходе). Мьютекс,
   отпускаемый в `defer`, освобождается, счётчики ссылок сходятся
   (`--leak-check` чист); двойного освобождения не бывает. Паника внутри
   `defer` или `Drop`, выполняемых при раскрутке, завершает процесс:
   печатаются обе паники, код выхода 2. Цена для кода без паники
   (runtime/ABI.md 8.1): функция, у которой при вызове, способном
   запаниковать, есть что освобождать, ставит свой кадр в цепочку
   потока перед первым таким вызовом и снимает на выходе (несколько
   записей в память, без вызовов и без setjmp на x86-64); то, что
   освобождает раскрутка, хранится в памяти, а не только в регистрах.
   Паника внутри `Drop`, вызванного обычным освобождением (не
   раскруткой), не раскручивает кадр, который это освобождение делал:
   его `defer` не выполняются, его значения утекают.
3. **Владелец задачи узнаёт о панике:**
   - `Task<T!>` (async-функция с ошибкой): `await` даёт ошибку, в цепочке
     которой есть сигнальная `task.ErrPanic`; её `Message()` —
     `panic: <сообщение>`. Проверка — `errors.Is(err, task.ErrPanic)`,
     сообщение и трасса — `task.PanicMessage(err)`, `task.PanicTrace(err)`.
     Выбран сигнальный вид, а не тип-структура: так панику узнаёт
     `errors.Is`, как `task.ErrCancelled`, и её можно обернуть `?("ctx")`.
   - `Task<T>` без `!`: панику нельзя проглотить — `await` паникует снова
     в ожидающей задаче с сообщением `panic in awaited task: <сообщение>`
     и исходной трассой (вложенные ожидания не повторяют префикс).
     Режима «вернуть нулевое значение» нет.
   - Задача, которую никто не ждёт (`task.Go`, таймеры): паника печатается в stderr (сообщение и
     трасса, в обычном формате), когда задачу отпускают; процесс
     продолжает работу. `WaitGroup` (через `defer wg.Done()`), `select` и
     каналы видят такую задачу завершённой.
4. **`main`** (синхронный или `async`) и синхронный код вне задач
   планировщика: процесс завершается с кодом 2 и трассой, как раньше.
   Паника в задаче `async main` после её первой приостановки
   раскручивает задачу, затем главный поток печатает панику и
   завершает процесс с кодом 2.
5. **`zell test`**: паника в тесте — провал этого теста (сообщение и
   трасса в отчёте), прогон продолжается со следующего теста (каждый
   тест — отдельный процесс).
6. **Отладчик** (`zell debug`) останавливается на панике до раскрутки.

Так на всех платформах (Linux, macOS, Windows).

**Трасса паники** печатается как в Go: после `panic: <сообщение>` (первая
строка неизменна) пустая строка, `backtrace (most recent call first):` и
по строке на кадр — `  <файл>:<строка> <функция>`, файл и функция как в
трассе ошибки (путь относительно рабочего каталога, если файл в нём; имя
без пространства имён):

```
panic: runtime error: index out of range [5] with length 3

backtrace (most recent call first):
  examples/bounds.zl:6 inner
  examples/bounds.zl:10 main
```

Строки берутся из компактной таблицы `zell_lines` — обычных данных
исполняемого файла, которые компилятор строит из DWARF объектных файлов
и линкует отдельным объектом (runtime/ABI.md 8.2), поэтому работают и в
`--release` без символов, одинаково на Linux, macOS и Windows; кадры не
из Zell-кода (рантайм, libc) печатаются как `модуль(символ+0xсмещение)`.
Встроенные (inlined) вызовы своего кадра не имеют. Тот же текст — у
`PanicTrace` паники задачи. Внутренние точки входа паник рантайма
(`zell_panic_nil` и т. п.) в трассе не показываются: первая строка — кадр,
где случилась паника.

**Аварийный сигнал** — настоящий сбой, а не проверка, вставленная
компилятором: чтение по плохому адресу через `unsafe`, переполнение стека,
ошибка в C-коде. Это не паника: задача его не изолирует, `defer` не
выполняются. Как в Go, рантайм сбрасывает буфер stdout (уже напечатанное
не теряется), печатает в stderr `fatal error: unexpected signal SIGSEGV`,
строку `[signal SIGSEGV: <что> addr=0x… pc=0x…]` и трассу в том же
формате, затем завершает процесс с кодом 2:

```
fatal error: unexpected signal SIGSEGV
[signal SIGSEGV: stack overflow addr=0x7ffd2e3cafd0 pc=0x401229]

backtrace (most recent call first):
  examples/rec.zl:5 down
  ...
```

Ловятся `SIGSEGV`, `SIGBUS`, `SIGILL`, `SIGFPE` (обработчик на
альтернативном стеке сигналов, поэтому работает и при переполнении
стека); на Windows — те же сбои через векторный обработчик исключений,
под именами POSIX-сигналов (runtime/ABI.md 8.3). `ZELL_NO_FATAL_HANDLER`
отключает обработчик (тогда — действие ОС по умолчанию, например core
dump).

## Управление потоком

Как в Go, без скобок вокруг условий, с обязательными фигурными скобками.

```zell
if x > 0 {
    ...
} else if x < 0 {
    ...
} else {
    ...
}

for i in 0..10 { ... }          // диапазон [0, 10)
for item in list { ... }
for i, item in list { ... }
for cond { ... }                // как while
for { ... }                     // бесконечный
```

`in` — контекстное ключевое слово: ключевое только между переменными
цикла и итерируемым значением в `for … in …`, в остальных местах — обычное
имя (`var in = 1`, параметр `in io.Reader`, `for x in in`).

**Протокол итерации.** `for x in v` обходит срезы, массивы, строки (по
code point), `map`, коллекции `collections` и любой тип, который
следует протоколу (реализация — `compiler/src/sema/iterate.rs`):

1. у `v` есть `func Iter() It` — цикл вызывает его один раз и обходит
   итератор `It`;
2. иначе `v` сам итератор, если у него есть `Next()`;
3. иначе у `v` есть `func Items() []T` — цикл обходит этот срез.

Итератор — значение (структура, указатель на структуру, интерфейс) с
методом встроенного интерфейса `Iterator<T> { func Next() (T, bool) }`
(сопоставляется структурно; обобщённых интерфейсов нет, поэтому
`Iterator<T>` не пишется как тип): `false` завершает цикл. Также
допускаются `func Next() (K, V, bool)` — две переменные цикла, ключ и
значение (`for k, v in orderedMap`; с одной переменной — ошибка) — и
`func Next() *T`, где `nil` завершает цикл (`for m in re.Iter(s)`).
`async func Next()` (или `func Next() Task<(T, bool)>`, как асинхронный
метод интерфейса) ожидается (`await`) на каждом шаге, поэтому такой
цикл допустим только в async-функции: `for v in ch` по `task.Channel<T>`
получает значения, пока канал не закрыт и не опустошён. С одним
значением `for i, x in v` нумерует элементы с 0. `break`/`continue`
работают как обычно; `Iter()` вызывается один раз, `Next()` — перед каждой
итерацией. Так обходятся `LinkedList`, `OrderedMap`, `LRU` (через
`Iter()`), `Deque`, `Ring`, `Heap`, `BitSet` (через `Items()`),
`regex.Iter` и `Channel`.

```zell
struct Countdown {
    From int
    func Iter() countIter { return countIter{n: this.From} }
}

struct countIter {
    n int
    func Next() (int, bool) {
        if this.n == 0 { return (0, false) }
        this.n -= 1
        return (this.n + 1, true)
    }
}

for x in (Countdown{From: 3}) { print(x) }   // 321
```

### switch

`switch` — единственная конструкция ветвления по значению. Без `fallthrough`,
без `break` в конце каждого `case`. Поддерживает значения, диапазоны,
несколько вариантов, деструктуризацию enum и проверку типа.

```zell
switch n {
    case 1, 2:       println("small")
    case 3..10:      println("medium")
    case n > 100:    println("huge")     // условие
    default:         println("other")
}

switch shape {
    case Circle c:    println("circle", c.R)
    case Rect r:      println("rect", r.W, r.H)
}

switch res {
    case Result.Ok(v):   println(v)
    case Result.Fail(c): println("fail", c)
}
```

- Проверка типа (`case T x:`) работает над интерфейсом, `any` и `error`.
  Для структуры `T` динамический тип должен совпасть точно; для
  интерфейса `I` — реализовать `I` (привязка `x` — значение `I`). Над
  `error` проверяется тип самой ошибки (структуры, упакованной в `error`),
  а не цепочки обёрток (для неё — `errors.As`): `case ExitCoder e:`
  срабатывает для любой структуры-ошибки с методом `ExitCode() int`.
  Выбирается первый подходящий `case`.
- `switch` по enum без `default`, перечисляющий все варианты, и полный
  `switch` по типу над `sealed`-интерфейсом — завершающие операторы
  (`return` после них не нужен), как в `Eval` из `docs/PATTERNS.md`.
  Неполный `switch` по enum допустим (ничего не делает для остальных
  вариантов); неполный по `sealed`-интерфейсу без `default` — ошибка.
- `break`, `continue`, `return`. `break` внутри `case` выходит из
  `switch` (как в Go), `continue` продолжает объемлющий цикл.
- **Метки** — как в Go: `имя:` на строке перед `for` или `switch` (или
  перед ними на той же строке) помечает инструкцию; `break имя` выходит
  из неё, `continue имя` переходит к следующей итерации помеченного цикла
  (так из `case` выходят из цикла). Метка пишется на той же строке, что
  `break`/`continue`. После `:` точка с запятой не вставляется, поэтому
  `outer:` на отдельной строке относится к следующей инструкции. Метки
  видны во всём теле функции (не в лямбдах внутри него). Ошибки
  компиляции: `break label not defined: L` (метки нет в функции),
  `invalid break label L` / `invalid continue label L` (метка не на
  объемлющей инструкции), `continue` к метке `switch`, метка не перед
  `for`/`switch`, повторная метка и неиспользуемая метка (`label L
  defined and not used`, как в Go). Выход по метке освобождает значения
  и выполняет очистку всех покидаемых областей, как обычный `break`;
  в коде — простые переходы.

```zell
outer:
for i, row in grid {
    for j, cell in row {
        switch cell {
            case want:
                (r, c) = (i, j)
                break outer
            case "":
                continue outer
        }
    }
}
```
- `defer` — выполнить при выходе из функции, как в Go. Аргументы
  вычисляются сразу. Отложенный вызов функции с `T!` — ошибка компиляции
  (результат нужно обработать): ошибку обрабатывают в отложенном замыкании,
  `defer func() { try Close() catch err { ... } }()`. Получатель-поле (`defer this.mu.Unlock()` у значения
  `task.Mutex` в поле): сохраняется указатель `this`, адрес поля берётся
  при вызове — тот же адрес, что вычислил бы Go, без внутреннего указателя.
- `defer await f(args)` — только в `async`-функции (методе, лямбде); в
  синхронной — ошибка компиляции. Получатель и аргументы вычисляются сразу,
  как у `defer`; `await` выполняется при выходе из функции в общем порядке
  LIFO с обычными `defer` на любом пути выхода (конец тела, `return`, `?`,
  выход из помеченного цикла), результат отбрасывается. Ожидаемый `T!`
  (`Close() Task<void!>`) — ошибка компиляции, как у `defer`: ошибку
  обрабатывает отложенное асинхронное замыкание
  ```zell
  defer await async func() {
      try await rows.Close() catch err { log.Warn("close", err) }
  }()
  ```
  Нужна вызываемая форма: `defer await t` (готовая задача) запрещён.
  `defer await` не ставится в цикл и не больше восьми `defer` в функции
  (он существует только в open-coded виде, раздел «Память»). **Паника:**
  раскрутка кадра пропускает отложенные `await` (разрушаемый кадр не может
  приостановиться) — выполняются только обычные `defer`, вычисленные
  получатель и аргументы освобождаются. **Отмена** их не пропускает: отмена
  кооперативная, тело выходит обычным путём, и отложенный `await`
  выполняется; ожидания внутри него видят отмену по общим правилам
  (`Delay` просыпается сразу, `Recv` и сеть дают `task.ErrCancelled`).
  Асинхронный `Drop` отложен.

## Асинхронность

Модель — задачи (tasks) на пуле потоков, как в C#/Tokio, с
языковым `async`/`await`.

```zell
async func Fetch(url string) string! {
    var resp = await http.Get(url)?
    return await resp.Text()?
}

async func main() {
    var a = Fetch("https://a")      // Task<string!>, запущена сразу
    var b = Fetch("https://b")
    var (ra, rb) = await task.All(a, b)?
    println(ra, rb)
}
```

- `async func` возвращает `Task<T>`; вызов запускает задачу, `await`
  дожидается результата. Тело выполняется синхронно на потоке
  вызывающего до первой реальной приостановки (как в C#); объект задачи
  создаётся только при ней, поэтому вызов, который завершился, ни разу не
  приостановившись (буферизованное чтение, свободный мьютекс, кэш),
  стоит как обычный вызов: `await f()` получает результат напрямую, без
  задачи (и без кадра корутины, если в теле нет точек приостановки).
  До первой приостановки тело работает в составе текущей задачи
  вызывающего (наследует её отмену; `task.CurrentContext()` внутри — её
  контекст); сохранённый `Task<T>` такого вызова — уже завершённая задача.
  `await f()` прямо внутри `async`-функции не создаёт задачу для `f`, даже
  если она приостанавливается: её кадр связывается с кадром ожидающего
  (ABI.md 10.3, «Frame-linked await»), и вся цепочка таких вызовов
  работает в задаче своего корня. Наблюдаемое поведение то же, что у
  задачи: результат, паника (`panic in awaited task` для `Task<T>`,
  `task.ErrPanic` для `Task<T!>`), отмена через текущую задачу; отладчик
  показывает только задачу корня.
  *Оптимизация (поведение не меняется):* `async`-функция, которая
  никогда не приостанавливается, компилируется как обычная функция с тем
  же ABI (ABI.md 10.3, «Never-suspending functions»): без кадра корутины,
  без задачи и без звена в цепочке кадров. «Никогда» решает анализ всей
  программы после мономорфизации: функция может приостановиться, если
  ждёт что-то кроме прямого вызова `async`-функции, которая сама никогда
  не приостанавливается (`task.Delay`, `Yield`, каналы, мьютексы,
  ввод-вывод, `Task` из переменной, поля, `All`/`Any`, замыкания,
  метода интерфейса или значения-функции); рекурсия, которая ждёт только
  себя, остаётся неприостанавливаемой (наибольшая неподвижная точка).
  Наблюдаемое поведение то же, потому что `async`-функция и так работает
  в задаче вызывающего до первой приостановки, а паника раскручивает
  такой кадр как синхронный (`defer`, `Drop`, освобождение, см.
  «Паника»). `zell check --dump-hir`
  помечает такие функции `async(plain)`, `--emit=llvm-ir` — атрибутом
  `"zell-plain-async"`.
- `await` допустим только внутри `async`.
- `?` и `await` комбинируются: `await f()?`.
- Планировщик — часть рантайма: пул потоков по числу ядер, кооперативное
  переключение в точках `await`. Блокирующий ввод-вывод в стандартной
  библиотеке асинхронный.
- Примитивы: `task.All`, `task.Any`, `task.Delay`, `Channel<T>`, `Mutex`.
  `await task.Any(t1, ..., tn)` (все `Task<T>` одного типа) даёт результат
  первой завершившейся задачи; остальные продолжают работать.
  Число задач, известное только во время выполнения: `task.All(ts)` над
  срезом `[]Task<T>` (или `task.All(ts...)`, или литерал `task.All([a,
  b])`) — `Task<[]T>` с результатами в порядке среза; над `[]Task<T!>` —
  `Task<([]T)!>`: как у формы с перечислением. Первая задача, завершившаяся
  ошибкой (или паникой), отменяет остальные ещё не завершённые (тем же
  `zell_task_cancel`, что и проигравших `task.Any`); результат —
  ошибка именно этой задачи (первой по времени завершения, а не по
  порядку в списке или срезе), а когда отменённые задачи завершились
  (их `defer` выполнены), `task.All` завершается. При успехе значения идут в
  порядке аргументов. Паника в задаче с `T!` приходит как `task.ErrPanic`, без
  `!` — повторяется у ждущего, как и раньше. Над
  `[]Task<void>` / `[]Task<void!>` — `Task<void>` / `Task<void!>`. Пустой
  срез даёт пустой результат. В отличие от формы с перечислением, такой
  `task.All` — обычная задача, её можно сохранить и дождаться позже.
  `task.Any(ts)` над срезом — как `task.Any(t1, ..., tn)`; пустой срез —
  паника `task.Any called with no tasks`.
  `task.Channel<int>(n)` создаёт канал с буфером на `n` значений (0 —
  небуферизованный: `Send` ждёт своего `Recv`); копии канала разделяют его;
  `await ch.Recv()` имеет тип `T!` и падает, когда канал закрыт и пуст;
  `Send` в закрытый канал — паника. Нулевое значение `task.Mutex` и
  `task.WaitGroup` готово к работе. `task.Mutex` следует правилам
  `sync.Mutex` из Go. Обычный режим: `Unlock` освобождает мьютекс и будит
  старейшего ожидающего, но владение не передаёт — работающая задача может
  взять свободный мьютекс раньше него (перехват); разбуженный, проигравший
  гонку, возвращается в **голову** очереди и остаётся старейшим. `Lock`
  занятого мьютекса сначала коротко крутится (до ~100 попыток CAS с
  `pause`, только когда есть свободные воркеры; при `ZELL_WORKERS=1` не
  крутится), затем встаёт в очередь. Режим голодания: ожидающий, который
  ждал дольше 1 мс, переключает мьютекс на передачу по FIFO — `Unlock`
  передаёт владение старейшему ожидающему, новые `Lock` и `TryLock` не
  перехватывают и встают в хвост; режим кончается, когда очередь пуста или
  получивший мьютекс ждал меньше 1 мс. Порядок захвата поэтому не
  гарантирован, гарантированы взаимное исключение и отсутствие голодания
  (ожидание сверх ~1 мс плюс задержка планировщика); `TryLock` берёт
  свободный мьютекс вне режима голодания. `task.Spawn(f)` запускает `f` на воркере,
  `task.Yield()` уступает поток, `await task.Timeout(t, ms)` — `true`, если
  `t` завершилась за `ms` мс (иначе `false`, `t` продолжает работать).
- Контекст задачи (значения и отмена) — см. «Отмена и структурированная
  конкурентность» и «Значения в контексте задачи» ниже. Реализация v1:
  `task.Spawn(f)` требует результата (`Spawn<void>` невыразим), для
  `func() Task<void>` есть `task.Go(f)`; явный контекст —
  `task.SpawnWith(ctx, f)` (перегрузки нет); ключи — `var K = task.Key<T>()`
  (не `const`: вызов не константное выражение). Отменённое ожидание с
  результатом `T!` (`Recv`, сеть) возвращает `task.ErrCancelled`; `Delay` и
  `Send` просыпаются сразу, но ошибку вернуть не могут — проверка
  `task.CheckCancelled()?`; `Mutex.Lock` не отменяется; `await` чужой задачи
  ждёт её завершения (runtime/ABI.md §10.11).
- Асинхронный метод интерфейса — `func X() Task<T>` или сокращение
  `async func X() T`; его реализует `async`-метод `async func X() T`
  (или обычный метод, возвращающий `Task<T>`), см. «Интерфейсы»,
  «Асинхронные методы».
- Асинхронные лямбды: `async func(n int) int { ... }` и
  `async (n int) => ...`; вызов возвращает `Task<T>`.
- Реализация в LLVM: через LLVM coroutines (`llvm.coro.*`), каждая `async`
  функция превращается в конечный автомат с выделенным фреймом.

## Рефлексия

Цель: удобнее, чем в Go (типизированные атрибуты, методы, enum,
создание значений, generics-дружественный API) и быстрее, чем в C#
(никакого JIT, никаких `MethodInfo.Invoke` через boxing: метаданные —
статические таблицы в бинарнике, доступ к полям по смещению, вызов
методов через указатель на функцию).

### Устройство

- Для каждого типа компилятор генерирует **статическую таблицу**
  `TypeInfo` в секции только для чтения: имя, полный путь, размер,
  выравнивание, вид (`reflect.Kind`), поля (имя, тип, смещение,
  атрибуты), методы (имя, сигнатура, указатель на функцию), варианты enum,
  тип элемента/ключа (`Elem`, `Key`, `Len`), атрибуты типа. Таблицы
  ссылаются друг на друга указателями, поэтому обход графа типов — обычное
  чтение памяти без аллокаций и без поиска по строкам.
- Атрибуты хранятся как готовые значения своих структур, а не как строки:
  `field.Attribute<json>()` возвращает `*json` или `nil` за O(1) по
  количеству атрибутов поля.
- Значения `any`, интерфейсов и ошибок несут указатель на `TypeInfo`: это
  тот же указатель, что тип бокса и `vtable[0]`, поэтому `typeof(x)` —
  одно чтение, а `switch x { case User u: }` — одно сравнение указателей.
- **Урезание**: если программа не использует `reflect` (ни прямо, ни
  через `typeof`, `json` или тип атрибута), таблиц нет вовсе — у типов
  остаётся минимальный заголовок `{name, size, drop}`. Иначе таблица
  создаётся только для типов, на которые ссылается код или другая таблица;
  методы перечисляются только у «полных» типов (названных в
  `reflect.TypeOf<T>()`, в статическом `typeof(x)`, в
  `reflect.Fields<T>()`, помеченных `@reflect` или попавших в
  `reflect.TypesWith<A>()`). Неиспользуемые таблицы
  удаляет `globaldce`.
- Раскладка таблиц (общая для компилятора и рантайма) — `runtime/ABI.md`,
  раздел 17: таблица — неуничтожимый объект `{-1, null, TypeInfo}`, первые
  три слова `TypeInfo` — заголовок `zell_type_info` рантайма; поля,
  методы, варианты и значения атрибутов — тоже неуничтожимые объекты,
  срезы таблиц без `backing` (подсчёт ссылок на них ничего не делает).

### API (`reflect`)

```zell
var t = reflect.TypeOf<User>()         // статически, без значения
var t2 = typeof(u)                     // по значению, встроенная функция

t.Name                                 // "User"
t.FullName                             // "app.models.User"
t.Kind                                 // reflect.Kind.Struct
for f in t.Fields {
    println(f.Name, f.Type.Name, f.Offset)
    var tag = f.Attribute<json>()      // *json или nil
    if tag != nil && tag.skip { continue }
}

var v = reflect.ValueOf(&u)            // reflect.Value: {владелец, адрес, *TypeInfo}
v.Field("Email").Set("a@b.c")          // проверка типа во время выполнения
var email = v.Field("Email").Get<string>()

var m = t.Method("Store")              // *MethodInfo или nil
var res = m.Call(&u)?                  // вызов через указатель на функцию
var fresh = t.New()                    // новое нулевое значение в куче, *User как any

for variant in reflect.TypeOf<Color>().Variants { println(variant.Name) }
```

- `reflect.TypeOf<T>()` и `typeof(x)` возвращают `*reflect.TypeInfo`;
  таблица у типа одна, поэтому `==` сравнивает типы. `typeof(x)` от
  значения статического типа — таблица этого типа (операнд не
  вычисляется, как `sizeof`), от `any`, интерфейса или `error` —
  динамический тип (`nil` для `nil`; у ошибки без структуры — `error`).
- `TypeInfo`: `Name` (короткое имя в написании Go: `User`, `*User`, `int`,
  `[]int`, `map[string]int`), `FullName`, `Kind`, `Size`, `Align`,
  `Fields []*FieldInfo` (в порядке объявления, `Offset` — раскладка C с
  естественным выравниванием), `Methods []*MethodInfo`,
  `Variants []*VariantInfo` (`Name`, `Index`, `Fields`), `Elem`, `Key`,
  `Len`; методы `Field(name)`, `Method(name)`, `Variant(name)` (`nil`,
  если нет), `Attribute<A>() *A`, `Attributes<A>() []*A` (порядок в
  исходнике), `New() any` (держит `*T`; только у полных типов, иначе
  паника), `Same(other)`. `FieldInfo`: `Name`, `Type`, `Offset`, `Index`,
  `Embedded`, `Exported`, `Attribute<A>()`, `Attributes<A>()`.
  `TypeInfo.Package` — путь пространства имён, где объявлен тип
  (`app.jobs`; пусто у встроенных и составных типов). `MethodInfo`:
  `Name`, `Type`, `Static`, `Params []*ParamInfo` (без приёмника),
  `Attribute<A>()`, `Attributes<A>()`, `Call`, `Invoke`. `ParamInfo`:
  `Name`, `Type`, `Index`, `Attribute<A>()`, `Attributes<A>()` (атрибуты
  параметра, `@attribute(targets: [reflect.Target.Param])`).
  `reflect.Kind`: `Bool`, `Int` (`int`/`int64`), `Int8`…`Int32`, `Uint`,
  `Uint8` (`byte`)…`Uint32`, `Float`, `Float32`, `Char`, `String`, `Error`,
  `Any`, `Interface`, `Struct`, `Enum`, `Pointer`, `Weak`, `Slice`,
  `Array`, `Map`, `Tuple`, `Func`, `Fallible`, `Task`, `Void`, `Invalid`.
  У кортежа `Fields` — его элементы `_0`, `_1`, … (со смещениями).
  Поле, тип которого записан синонимом (`int64`, `uint`, `uint8`,
  `float64`), показывает это написание в `f.Type.Name`.
- `reflect.Value` — `{владелец any, адрес, *TypeInfo}`: владелец держит
  память живой, чтение поля — сложение смещения. `ValueOf(x any)`,
  `Field(name) Value` (сквозь указатель на структуру; паника, если поля
  нет), `Get<T>() T` и `Set<T>(v T)` проверяют тип и паникуют при
  несовпадении (сообщение называет поле), `IsValid()`, поле `Type`.
- `m.Call(recv, args...)` — универсальная форма: аргументы упаковываются в
  `[]any`, приёмник — `*S` (или `S`: метод работает с копией), результат —
  `any!` (ошибка метода или проверки типов `reflect: S.M: ...`).
  Типизированная форма `m.Call<func(*User) void!>()` возвращает обычную
  функцию (первый параметр — приёмник) и вызывает её напрямую, без
  накладных расходов; несовпадение сигнатуры — паника.
- `any` — пустой интерфейс (`interface {}`); значения в нём несут
  `TypeInfo`, поэтому `switch x { case User u: }` работает за одно сравнение
  указателей.
- Встроенные атрибуты со значениями — структуры `reflect`: `json`
  (`name string`, `omitEmpty bool`, `skip bool`), `deprecated`
  (`message string`), `inline`, `test`, `log` (`skip bool`); имя атрибута можно писать как тип
  (`f.Attribute<json>()`), а поля этих структур читаются из любого
  пространства имён. `@attribute` и `@reflect` в списках атрибутов не
  появляются.

### Статическая рефлексия (нулевая стоимость)

Для сериализаторов и ORM обычная рефлексия всё же обходит таблицы во
время выполнения. Вторая половина механизма — **compile-time рефлексия**
в generic-коде: компилятор раскрывает обход полей на этапе компиляции,
когда тип известен (мономорфизация).

```zell
func ToJson<T>(value T) string {
    var b = strings.Builder{}
    b.Write("{")
    for f in reflect.Fields<T>() {       // разворачивается при компиляции
        var tag = f.Attribute<json>()
        if tag != nil && tag.skip { continue }
        var name = f.Name
        if tag != nil && tag.name != "" { name = tag.name }
        b.Write(fmt.Format("\"{0}\":", name))
        b.Write(Scalar(f.Get(value)))   // прямой доступ к полю, без reflect.Value
    }
    b.Write("}")
    return b.String()
}
```

`reflect.Fields<T>()` в generic-функции — не вызов, а инструкция
компилятору: тело цикла проверяется и генерируется отдельно для каждого
поля структуры `T` (у кортежа — для каждого элемента: `_0`, `_1`, …) (`f` — `*FieldInfo` этого поля), а `f.Get(value)` —
прямое обращение `value.Id`, `value.Email` и т. д. со статическим типом
поля, а `f.Set(&value, x)` — присваивание этого поля (см. ниже). Копии выбираются счётчиком цикла, поэтому `continue` и `break`
значат то же, что в обычном цикле. Результат — скорость ручного кода (как
у `serde` в Rust или source generators в C#), без генерации исходников и
без отдельного шага сборки. Вне generic-функции (кроме копии развёрнутого
цикла по дескрипторам, где `reflect.Fields<t>()` известен) и для `T`, не
являющегося структурой, — ошибка компиляции; при проверке generic-тела с абстрактным
`T` тело проверяется один раз, а `f.Get(v)` не имеет типа.

Вторая инструкция — **статический `if`**: условие из проверок вида
`reflect.TypeOf<T>().Kind == reflect.Kind.Struct` (в том числе через
`.Elem` и `.Key`) или `reflect.TypeOf<A>() == reflect.TypeOf<B>()`,
соединённых `!`, `&&`, `||`, вычисляется при компиляции; ветка, которая не
выполнится, не проверяется. Так generic-код выбирает обработку по виду
типа (`json.Format<T>` для структур, срезов, map, чисел...).

Достижимость считается после свёртки: если выбранная ветка статического
`if` (или статического `switch`, см. ниже) завершается — `return`,
`break`, `continue`, `panic`, `reflect.Error` или другая завершающая
инструкция, — то инструкции после него в том же блоке в этой
инстанциации недостижимы и не проверяются, как отброшенная ветка:

```zell
func Name<T>(x T) string {
    if reflect.TypeOf<T>().Kind == reflect.Kind.Struct {
        return reflect.TypeOf<T>().Name
    }
    reflect.Error("Name needs a struct")   // только для T, не являющихся структурой
}
```

То же для развёрнутого цикла `for f in reflect.Fields<T>()`: если копия
тела для поля k после свёртки всегда выполняет `return` (или `panic`,
`reflect.Error`), поля после k не разворачиваются, а если ни одна более
ранняя копия не содержит `break` этого цикла, недостижимы и инструкции
после цикла. Так проверяется «есть ли у типа поле с условием»:

```zell
func requireKey<E>() {
    for g in reflect.Fields<E>() {
        if g.Name == "Id" {
            return
        }
        if g.Name == reflect.TypeOf<E>().Name + "Id" {
            return
        }
    }
    reflect.Error("data: " + reflect.TypeOf<E>().Name + " has no key")
}
```

Сравнение `==`/`!=` свёрнутой строки (`f.Name`) с константным именем
типа (`reflect.TypeOf<E>().Name`, `FullName`, их конкатенации с
литералами) в инстанциации тоже константа.

Цепочки `else if` сворачиваются по очереди. Поскольку код инстанциации
может быть отброшен, «неиспользуемая переменная» в generic-функции
сообщается только абстрактной проверкой тела (она видит все ветки).

**Константы развёрнутого цикла.** В копии тела `for f in
reflect.Fields<T>()` для конкретного поля константами времени
компиляции являются:

- `f.Name`, `f.Index`, `f.Exported`, `f.Embedded`;
- `f.Attribute<A>()` — указатель на неуничтожимое значение атрибута или
  `nil`; поэтому `f.Attribute<A>() != nil` и `== nil` — константы, а поля
  атрибута (`tag.min`) — константы аргумента (или значения по умолчанию,
  или нулевого значения);
- `f.Type` как операнд проверки типа: `f.Type.Kind == reflect.Kind.X`
  (в том числе через `.Elem`/`.Key`: `f.Type.Elem.Kind`),
  `f.Type == reflect.TypeOf<U>()`, и наравне с ним
  `reflect.TypeOf<T>()`; а также `f.Type.Name`, `f.Type.FullName`,
  `f.Type.Kind` как значения;
- локальная переменная, инициализированная такой константой
  (`var tag = f.Attribute<A>()`), если в остатке блока ей ничего не
  присваивается и её адрес не берётся;
- сравнения `==`/`!=` (и `<`… для целых) двух констант, `!` константы,
  `&&`/`||`, у которых левая сторона — такая константа и решает результат
  (правая сторона тогда не проверяется).

`if`, условие которого через эти правила стало константой, —
статический: проверяется и генерируется только выбранная ветка
(`if f.Type.Kind == reflect.Kind.String { n += len(f.Get(v)) }` для поля
`int` не проверяется), и `reflect.Error` в нём отвергает неверное
применение атрибута (`@range` на поле `bool`). Условие, зависящее от
значений во время выполнения (`if n > 0 && f.Attribute<A>() != nil`), —
обычный `if`. При абстрактной проверке тела (поле неизвестно) обе ветки
такого `if` проверяются с подавленной диагностикой.

**Статический `switch`.** В generic-функции `switch` по значению
известного статического типа, все шаблоны которого — типовые
(`case string s:`), выбирает при компиляции первую ветку, тип которой
совпадает с типом значения (или интерфейс, который тип реализует;
привязка получает значение), иначе `default`; остальные ветки не
проверяются, несовпадающий шаблон — не ошибка:

```zell
for f in reflect.Fields<T>() {
    switch f.Get(v) {
    case string s: b.Write(s)
    case int n:    b.Write(fmt.Format("{0}", n))
    default:       b.Write("?")
    }
}
```

`switch` по константе развёрнутого цикла (`switch f.Type.Kind`,
`switch f.Name`) выбирает ветку с равной константой; значения в его
`case` обязаны быть константами (ошибка «a case of a static switch ...
must be a constant»). После статического `switch`, чья выбранная ветка
завершается, остаток блока недостижим (как после статического `if`).

**Адрес поля.** `f.Addr(p)` (`p` — `*T`) — адрес поля в `*p`
(`&p.<поле>`, внутренний указатель со статическим типом поля): декодер
пишет прямо в поле (`sql.convertInto(f.Addr(p), v, name)`), без копии.

**Запись поля.** `f.Set(p, value)` — инструкция (не значение): прямое
присваивание `p.<поле> = value`, где `p` — `*T` (тип из
`reflect.Fields<T>()`), а `value` приводится к статическому типу поля
(«cannot use string as int for field A»); `f.Set(v, x)` со значением
вместо указателя — ошибка «f.Set needs a *T ...». Пара `f.Get`/`f.Set`
копирует или заполняет структуру без `reflect.Value`.

### Типы с атрибутом и ошибки из библиотек

Две функции позволяют писать фреймворки (маршруты `web`, реестры задач,
DI) обычными пакетами, без хуков в компиляторе.

```zell
@attribute(targets: [reflect.Target.Struct])
struct job {
    name string
}

@job(name: "hello")
struct Hello {
    static func Run() string { return "hi" }   // сигнатура фиксирована: func() string
}

func main() {
    for t in reflect.TypesWith<job>() {          // []*TypeInfo, новый срез
        var run = t.Method("Run").Call<func() string>()
        println(t.Attribute<job>().name, run())
    }
}
```

- **`reflect.TypesWith<A>() []*TypeInfo`** — все типы *всей программы*
  (пакет бинарника и все его зависимости, включая stdlib), в объявлении
  которых есть атрибут `A`: структуры, enum и интерфейсы. `A` обязан быть
  типом атрибута (`@attribute`-структура или встроенный атрибут со
  значением), иначе ошибка компиляции. Список вычисляет компилятор в
  итоговой единице сборки (как `main`), поэтому функцию можно вызывать и
  из библиотеки: `web.Run(app)` в пакете `web` видит контроллеры
  приложения. Порядок стабилен: пакет (по имени), затем файл (по пути),
  затем порядок объявлений — таблицы маршрутов и OpenAPI детерминированы.
  Generic-тип даёт по элементу на каждую инстанциацию, реально
  использованную в программе (`Box<int>`, `Box<string>`); сам шаблон —
  нет. Сами таблицы — константы (неуничтожимые, как значения атрибутов),
  а результат — новый срез в куче при каждом вызове (одна аллокация):
  его можно сортировать (`slices.SortBy`) и менять, следующий вызов
  вернёт исходный порядок. Стоимость O(типов с `A`):
  полные таблицы (с методами и `ptrTo`) получают только помеченные типы;
  программа, которая не вызывает `TypesWith`, не платит ничего.
  Анализ в IDE идёт по единицам (пространствам имён), поэтому LSP может
  видеть неполный список; для типов это не важно (результат всегда
  `[]*TypeInfo`), а значение существует только в итоговой сборке, где
  видна вся программа.
- **`reflect.Error(msg string)`** — ошибка компиляции в месте вызова,
  если вызов достижим после свёртки констант: в ветке, отброшенной
  статическим `if`, ошибки нет. `msg` — константная строка (литералы,
  константы, их конкатенация, `f.Name` поля из `reflect.Fields<T>()`,
  `reflect.TypeOf<T>().Name`/`FullName`/`Package`, строковые поля
  атрибута, полученного через `f.Attribute<A>()`); иначе ошибка
  «reflect.Error needs a constant string message». Диагностика —
  `error: <msg>` с позицией вызова и заметкой `raised by <функция>`
  (для generic-функции — инстанциация, `Check<int>`) и заметками
  `instantiated here (файл:строка:столбец)` — вызов, создавший
  инстанциацию, затем вызовы внешних инстанциаций. `reflect.Error(...)` —
  завершающая инструкция (как `panic`): `return` после неё не нужен. При абстрактной
  проверке generic-тела (тип-параметр ещё не известен) ошибка не
  выдаётся — только в инстанциациях. В методе generic-структуры (все её
  методы проверяются вместе с инстанциацией) ошибка выдаётся, только
  если метод используется: вызов, значение-метод или преобразование
  структуры к интерфейсу, в котором (или в любом другом интерфейсе
  программы) есть метод с этим именем — только такой метод достижим
  через таблицу методов; так библиотека объявляет «запрещённый» метод
  (`Where` после `Select`). `TypeOf<T>().Name` и `f.Type.Name` в
  сообщении — короткие имена, как во время выполнения (`User`, `[]*Order`).
  Это библиотечный `static_assert`.
- Развёртывание этого цикла при компиляции — в следующем разделе.

### Развёртывание типов, методов и параметров

`for t in reflect.TypesWith<A>()` — та же инструкция компилятору, что
`reflect.Fields<T>()`, но в любой функции (список типов известен при
компиляции): тело проверяется и генерируется отдельно для каждого типа
(в порядке `TypesWith`), `t` в копии — дескриптор этого типа. Внутри такой
копии `for m in t.Methods` развёртывается по методам структуры (порядок
объявления, статические и `async` тоже; у enum и интерфейсов методов нет),
а внутри копии метода `for p in m.Params` — по параметрам (без
приёмника). `continue`/`break` значат то же, что в обычном цикле.

```zell
async func Dispatch(path string, q map[string]string, body string) string! {
    for t in reflect.TypesWith<controller>() {
        var c t                                   // t — тип
        for m in t.Methods {
            var g = m.Attribute<get>()
            if g == nil { continue }              // статический if
            if t.Attribute<controller>().prefix + g.path != path { continue }
            var args m.Args                       // поле на каждый параметр
            for p in m.Params {
                var qa = p.Attribute<query>()
                if qa != nil {
                    switch p.Type.Kind {          // статический switch
                    case reflect.Kind.Int:    p.Set(&args, strconv.Atoi(q[qa.name])?)
                    case reflect.Kind.String: p.Set(&args, q[qa.name])
                    default: reflect.Error("unsupported parameter type " + p.Type.Name)
                    }
                } else {
                    p.Set(&args, json.Parse<p.Type>(body)?)
                }
            }
            if m.IsAsync { return render(await m.Apply(&c, args)) }
            return render(m.Apply(&c, args))      // прямой вызов, без []any
        }
    }
    return error("404 " + path)
}
```

**Когда цикл развёртывается.** Цикл по `TypesWith<A>()` развёртывается,
только если телу нужен дескриптор времени компиляции: `t` (или
дескриптор, полученный из него вложенными `for m in t.Methods`,
`for p in m.Params`, `for f in reflect.Fields<t>()`) стоит на месте типа,
на нём вызываются `CallOn`/`Apply`/`Get`/`Set`, или тело вызывает
`reflect.Error`. Иначе это обычный цикл по срезу во время выполнения
(`for i, t in TypesWith<A>()`, `t.Method("Run").Call<F>()`, `return t` —
как раньше). Правило синтаксическое и не зависит от остального тела.
Generic-тип, помеченный `A`, в развёрнутой форме — ошибка компиляции (его
инстанциации известны только после анализа всей программы); во время
выполнения он перечисляется как обычно. При абстрактной проверке
generic-тела с `A` — параметром типа тело проверяется один раз с
подавленной диагностикой.

**Константы.** Наравне с константами полей (выше) в копии константами
являются: `t.Name`, `t.FullName`, `t.Package`, `t.Kind` (и через
`.Elem`/`.Key`), `t == reflect.TypeOf<U>()`, `t.Attribute<B>()`;
`m.Name`, `m.Static`, `m.IsAsync` (только при компиляции: в таблицах
времени выполнения `async`-методов нет), `len(m.Params)`,
`m.Attribute<B>()`, `m.Result.Kind`; `p.Name`, `p.Index`,
`p.Attribute<B>()`, `p.Type.Kind`/`.Name`/`== TypeOf<U>()`. На них
работают статические `if`/`switch`, `reflect.Error` и правило
достижимости. Переменная копии, все использования которой свернулись,
равна `nil` (таблицы не читаются и для типа не создаются); иначе это
запись таблицы (`TypeOf<t>()`, `.Methods[k]`, `.Params[j]`), у
`async`-метода такой записи нет — ошибка компиляции.

**Дескриптор как тип.** В копии развёрнутого цикла на месте типа (`var x
T`, аргумент типа `F<T>()`, литерал `T{...}`, `new T{...}`; не внутри
лямбды) можно писать:

| запись | тип |
|---|---|
| `t` | сам тип из `TypesWith<A>()` |
| `f.Type` | тип поля из `reflect.Fields<T>()` (в том числе в generic-функции) |
| `f.Type.Elem`, `f.Type.Key`, `p.Type.Elem`, … | тип элемента среза, указателя, map (ключа map) — цепочкой |
| `p.Type` | тип параметра |
| `m.Result` | объявленный результат метода (`T`, `T!`; у `async` — результат задачи) |
| `m.Args` | структура аргументов метода: по полю на параметр, имя и тип как у параметра |

Грамматика не меняется (это `path` в позиции типа). Дескриптор, не
являющийся константой развёрнутого цикла (параметр функции типа
`*reflect.ParamInfo`, переменная цикла времени выполнения), на месте типа —
ошибка «p.Type is a run-time descriptor here: a descriptor can be used as a
type only inside a loop unrolled at compile time».

**Типизированный вызов.** `m.CallOn(recv, args...)` — прямой вызов метода
`m` у получателя `recv` (`*S` или `S`, где `S` — `t`; у статического
метода получателя нет): аргументы проверяются по типам параметров как в
обычном вызове («cannot use string as int in argument 1 of Counter.Add»),
результат — результат метода (`Task<T>` у `async`, его ждут `await`).
`m.Apply(recv, args)` — тот же вызов с аргументами из переменной типа
`m.Args`. Аргументы набираются по одному: `p.Set(&args, v)` — инструкция,
присваивание поля параметра `p` с проверкой типа (та же ошибка, номер
аргумента — `p.Index + 1`), `p.Get(args)` — его значение. `m.Call<F>()` и
`m.Invoke` остаются (для не-`async` методов, через запись таблицы).

Диагностика кода, не зависящего от дескриптора, выдаётся один раз (а не в
каждой копии); переменная в копиях не используется, только если она не
используется ни в одной копии.

### Реализовано

- `reflect` целиком в описанном объёме (кроме списка реализуемых
  интерфейсов и методов у таблиц интерфейсов); исходник на Zell —
  `compiler/src/sema/reflect_src/reflect.zl`, тела нескольких внутренних
  функций генерирует компилятор (`codegen/reflect.rs`).
- `encoding.json`: `Parse<T>(text) T!` и `Format<T>(v T) string` (с отступами — `FormatIndent<T>(v, prefix, indent)`, раскладка Go `MarshalIndent`)
  через compile-time рефлексию (структуры с `@json(name:, omitEmpty:,
  skip:)`, вложенные структуры, срезы, массивы, `map` со строковыми
  ключами — при выводе отсортированы, указатели, `nil` → `null`, строки,
  числа, `bool`, простые enum по имени варианта, `json.Value`, `any`),
  ошибки с путём (`users[2].id: expected int, found string`);
  `ParseValue(text) Value!` — динамическое дерево (`Type`, `IsNull`,
  `Bool`, `Float`, `Int`, `String`, `Len`, `Index`, `Get`, `Has`, `Keys`,
  `Items`, `Format`; `IsObject`/`IsArray` — общие имена контейнеров у
  `json.Value`, `yaml.Value` (там же родные `IsMap`/`IsSeq`) и
  `toml.Value` (`IsTable`/`IsArray`)), конструкторы `NewNull`/`NewBool`/`NewNumber`/
  `NewString`/`NewArray`/`NewObject`, `Decode<T>(v)`, `Quote(s)`.
  Разбор — C (`runtime/src/std_json.c`): текст за один проход
  превращается в документ-арену узлов, `Value` — узел такого документа
  (документ живёт, пока жив хотя бы один его `Value`), `Parse<T>` обходит
  узлы напрямую, `Format<T>` пишет в C-буфер; строки Zell создаются
  только для строковых полей результата. Вложенность глубже 512
  контейнеров отвергается (`json: nesting too deep`). Пустой массив
  `[]` разбирается в пустой (не nil) срез и форматируется обратно как
  `[]`; nil-срез, map и указатель — `null` (как в Go). Нет
  `Reader`/`Writer`, `Options{Indent}`, `Schema<T>`, конвертеров.
- `strings.Builder` (`Write`, `String`, `Len`, `Reset`).
- Те же `Fields<T>()`-обходы дают `Parse<T>`/`Format<T>` для
  `encoding.csv` (`@csv(name:, index:, skip:, omitEmpty:)`),
  `xml` (`@xml(name:, attr:, text:, ns:, omitEmpty:, skip:)`), `yaml`
  (`@yaml(name:, omitEmpty:, skip:, flow:)`) и `toml` (`@toml(name:,
  omitEmpty:, skip:, inline:)`); `@serde(name:, omitEmpty:, skip:)` —
  общий атрибут, который читают все форматы. Типизированные шаблоны
  `text.template.Parse<T>` проверяют поля `T` через `reflect.TypeInfo`
  во время выполнения, а для строкового литерала — ещё и при компиляции
  (`sema/litcheck.rs`, вместе с `regex.Pattern("...")`).
- Библиотеки на Zell загружаются при первом обращении к их именам,
  поэтому программы без рефлексии не платят ничего.

| | Go | C# | Zell |
|---|---|---|---|

### Отмена и структурированная конкурентность

Отмена живёт в контексте задачи и распространяется по дереву задач сама,
как в Kotlin и Swift; явного токена в сигнатурах нет.

- У каждой задачи есть родитель; контекст (отмена, дедлайн, значения)
  наследуется детьми. `task.Spawn` без явного контекста берёт текущий.
- Отмена кооперативная: срабатывает в точках `await`. Отменённый `await`
  возвращает ошибку `task.ErrCancelled`, которая идёт наверх через `?`.
  Ожидания ввода-вывода, `Delay`, `Channel.Recv`, `Mutex.Lock` просыпаются
  сразу с этой ошибкой.
- Отмена родителя отменяет детей. Внутри `task.Scope` ошибка одного ребёнка
  отменяет остальных, а scope не завершается, пока живы его дети: задачи не
  утекают.
- `task.WithTimeout(ms, fn)` и `task.WithDeadline(at, fn)` — scope с дедлайном.
- `task.NewCancel()` даёт ручку `{Context, Cancel()}` для отмены снаружи
  (кнопка «Стоп», shutdown сервера).
- `t.Cancel()` у `Task<T>` отменяет саму задачу `t` и её потомков тем же
  `zell_task_cancel`, что отменяет проигравших `task.Any`: ожидания, которые
  она начала (и до первой приостановки), просыпаются с `task.ErrCancelled`,
  `Delay` — сразу; `await t` у `Task<T!>` получает ту ошибку, которую вернёт
  тело (обычно `task.ErrCancelled` через `?`), у `Task<T>` — значение,
  которое вернёт тело (правило ожиданий без `!` выше). Повторный `Cancel`
  ничего не делает; у завершённой задачи результат не меняется (отменяются
  только оставленные ею работающие потомки, как при отмене scope). Задачи, которые тело начало
  до своей первой приостановки, принадлежат вызывающему (runtime/ABI.md
  10.11) и этой отменой не задеваются; отменить всё дерево вызова —
  `task.NewCancel()` + `task.RunWith`.
- `task.CheckCancelled() void!` — явная проверка в длинном синхронном цикле.
- `task.OnCancel(fn)` — обратный вызов при отмене (обычно с `defer`).
- `task.Any` отменяет проигравшие задачи (до того, как вернёт результат);
  `task.All` при первой ошибке отменяет остальные. Ожидания, которые
  проигравшая задача начала, отменяются вместе с ней, даже если начаты до
  её первой приостановки: отменённый `Recv` уходит из очереди канала, и
  следующий `Send` достаётся живому получателю. Отменённый `task.Delay`
  (проигравший `Any`) завершается сразу и снимает свой
  таймер, а не держит задачу до срока.

```zell
async func Search(query string) []Result! {
    return await task.WithTimeout(5000, async () => {
        return await task.Scope(async (s *task.Scope) => {
            var a = s.Spawn(SearchDb(query))
            var b = s.Spawn(SearchIndex(query))
            return await task.Any(a, b)?        // проигравший отменяется
        })?
    })?
}
```

### Значения в контексте задачи

Аналог `AsyncLocal<T>` и `context.WithValue`, но с типизированными ключами и
без параметра `ctx` в сигнатурах:

```zell
const CurrentSpan = task.Key<SpanInfo>()      // уникальный типизированный ключ

await task.With(CurrentSpan, span, async () => {   // действует на время fn
    await next(ctx)?                               // и на всех детей
})?

var span = task.Get(CurrentSpan)              // *SpanInfo или nil, в любой глубине
```

- `task.Key<T>()` — ключ; `task.Get(key) *T`; `task.With(key, value, fn)`
  устанавливает значение на время `fn` и восстанавливает прежнее после.
- Значения наследуются дочерними задачами на момент их запуска; изменения
  ребёнка родителю не видны.
- `task.CurrentContext()` возвращает контекст как значение для явной
  передачи (`task.Spawn(ctx, fn)`, колбэки из C, пулы).
- Реализация: неизменяемый список кадров; `With` — один кадр, `Get` — проход
  по списку, наследование — копия указателя.
- Значения, установленные внутри `async`-функции (`task.With`, span'ы
  `diag.StartSpan`, `log.Context.Push`), не видны вызывающему после
  первой приостановки или завершения функции (в том числе синхронного,
  без задачи): рантайм возвращает контекст вызывающего (runtime/ABI.md,
  10.3 и 10.8).
- Используется `zell.diag` (текущий span), `zell.log` (`Enrich.FromContext`),
  `http.Client` и `sql` (автоматический `traceparent`).

## Деревья выражений

Лямбда, переданная туда, где ожидается **`expr<F>`** (`F` — функциональный
тип), становится не замыканием, а значением-деревом (аналог
`Expression<Func<>>` в C#): библиотека читает тело лямбды как данные и
переводит его, например, в SQL, без хуков в компиляторе.

```zell
func Where(p expr<func(*User) bool>) Query { ... }

var minAge = 18
var q = Where(u => u.Age >= minAge && strings.HasPrefix(u.Name, "A"))
var p expr<func(*User) bool> = u => u.Address.City == "Paris"
var keep = p.Compile()                  // func(*User) bool, обычная функция
```

- **Тип.** `expr<F>` — встроенная форма типа (импорт не нужен, грамматика
  та же: `path typeargs`); это структура `expr.Expr<F>` пакета `expr`.
  `F` обязан быть функциональным типом (`expr<int>` — ошибка «the type
  argument of expr must be a function type»). Лямбда становится деревом
  везде, где известен ожидаемый тип: аргумент, типизированная переменная,
  поле, `return`. Сначала она проверяется как обычная лямбда типа `F`
  (типы параметров выводятся так же, в том числе у `u => ...`; в вызове
  generic-функции `Where<T>(p expr<func(*T) bool>)` — после вывода `T` из
  других аргументов или явных `Where<User>(...)`). Параметры типа в
  результате `F` выводятся из тела лямбды: `Select<R>(f expr<func(*T) R>)`
  с `u => (u.Name, u.Age)` даёт `R = (string, int)` (и у generic-метода
  generic-структуры). Если результат `F` — интерфейс (`any`), а тело
  другого типа, который его реализует, значение приводится (узел
  `Convert`): `OrderBy(k expr<func(*T) any>)` принимает `u => u.Name` и
  `u => (u.A, u.B)`. Без ожидаемого типа —
  обычная ошибка `cannot infer the type of lambda parameter u`. Деревом
  становится только литерал лямбды: значение типа `F` на месте `expr<F>` —
  ошибка «only a lambda literal becomes an expression tree».
- **Узлы.** Параметр; доступ к полю, в том числе вложенный
  (`u.Address.City`, сквозь указатели); константа; захваченное значение;
  `== != < <= > >=`, `+ - * / %` (и `+` строк), `&& || !`, унарный `-`;
  операторы типов с методами `Compare`/`Equals` (`u.Joined < t` у
  `time.Time`) — те же узлы `Binary`; `x == nil` / `x != nil`;
  преобразование `float(u.Age)` (и неявное к интерфейсу) — `Convert`;
  индексация `u.Tags[0]` — `Index`; вызовы из белого списка (одна таблица
  в компиляторе, `sema/exprtree.rs` `TREE_CALLS`): `strings.HasPrefix`,
  `HasSuffix`, `Contains`, `ToLower`, `ToUpper`, `Trim`, `len`,
  `slices.Contains`, `math.Abs`, — и функции и методы, помеченные
  атрибутом **`@expr.call`** (библиотека объявляет, что переводит их:
  `data.Any(u.Orders, o => ...)`, `g.Count()` у группы); узел `Call`
  называет функцию полным именем без аргументов типа (`data.Group.Count`),
  приёмник метода — первый аргумент. Лямбда — аргумент такого вызова —
  узел `Lambda`: её параметры продолжают нумерацию внешних
  (`Param(1)` у `o` в `u => data.Any(u.Orders, o => o.Total > u.Limit)`),
  тело — поддерево; она читает параметры внешних лямбд и слоты. Кортеж
  `(a, b)` и литерал структуры `T{A: x}` — результаты проекций
  (`expr<func(*User) (int, string)>`, `expr<func(*User) UserDto>`).
- **Запрещено** (ошибка компиляции на месте подвыражения): блочное тело
  (`u => { ... }`, а значит и присваивания), `await` и `async`-лямбда,
  вложенная лямбда не в аргументе вызова (`a nested lambda is only allowed
  as an argument of a call in an expression tree`), `?` и `try`, вызовы с
  параметром вне списка и без `@expr.call` (`call of app.f is not allowed
  in an expression tree (allowed: ...)`, `method call User.IsAdult ...`),
  вызовы значений-функций, побитовые операторы и сдвиги, литералы срезов и
  map, `&`, индексация map и срезы `a[i:j]`.
- **Захват — значениями, при построении дерева** (как в C#). Каждое
  максимальное подвыражение без параметров лямбды — *слот*: литерал
  остаётся константой, всё остальное (переменная, путь полей `req.MinAge`,
  глобальная переменная, любой вызов, индексация, преобразование от них:
  `time.Now()`, `ids[0]`, `cutoff()`) вычисляется один раз,
  когда вычисляется сама лямбда, и хранится в дереве как значение. Поэтому
  `for n in names { ps = append(ps, u => u.Name == n) }` даёт каждому
  дереву своё `n`, а присваивание переменной после построения не меняет ни
  дерево, ни `Compile()`. Вызов функции с `@expr.call` (и выражение,
  которое его содержит) слотом не бывает, даже без параметров: он
  остаётся узлом `Call` с аргументами-слотами (`data.Exists(q)`,
  `data.Over()` — библиотека переводит их сама, а в памяти их значение
  могло бы и не вычисляться). Повторное упоминание того же значения
  (`u.Age > n && len(u.Name) > n`) использует один слот. Переменные
  создающей функции при этом не переезжают в ячейки.
- **`Compile()`** возвращает лямбду как обычную функцию `F` бесплатно:
  дерево несёт и замыкание (оно читает те же слоты).
- **Комбинаторы** (`expr`): `And(a, b)`, `Or(a, b)`, `AndAll(ps)`,
  `OrAll(ps)` (срез; generic-функции не бывают вариативными), `Not(p)` —
  над предикатами `expr<func(T) bool>` одного `T`; результат —
  `expr<func(T) bool>` с узлом `Binary`/`Unary` над корнями частей, его
  `Compile()` вычисляет части с сокращённым вычислением. Пустой `AndAll` —
  константа `true`, пустой `OrAll` — `false`.
- **Представление и стоимость.** Структура узлов каждого места лямбды —
  константа `expr.Site` (неуничтожимый объект в секции только для чтения:
  узлы в префиксном порядке, их строки, число параметров). Значение
  `expr<F>` — `{site, (замыкание F, значения слотов, типы узлов)}`: три
  замыкания над *одним* окружением, кортежем захваченных значений в одном
  heap-боксе (`hir::Function::value_env`, `ExprKind::EnvClosures`).
  Построение дерева без захватов не выделяет память, с захватами — один
  бокс. Вложенная лямбда получает своё окружение-значение (нужные ей слоты
  и параметры внешних лямбд), которое строит внешняя лямбда при вызове. Узлы декодируются только по `Root()` (каждый вызов — новое
  дерево); константы и значения слотов упаковываются в `any` в этот же
  момент.
- **Пакет `expr`.** `p.Root() *expr.Node`, `p.Params() []*reflect.TypeInfo`,
  `p.ParamNames()`, `p.Compile()`, `p.String()` (`u => u.Age > 18`;
  `println(p)` печатает так же); для кэша переводчика: `p.Site()` —
  указатель на константу места (один у всех вычислений одной лямбды, `nil`
  у дерева из комбинатора), `p.Slots()` — слот каждого узла `Const` и
  `Captured` в порядке `Walk`, `p.Value(k)` — значение слота `k` в этом
  вычислении (перевод кэшируется по месту, параметры берутся из слотов без
  разбора дерева). `expr.Node` — enum с данными:
  `Param(index, t)`, `Field(base, name, index, t, owner)`,
  `Const(value any, t)`, `Captured(index, name, value any, t)`,
  `Binary(op, left, right, t)`, `Unary(op, operand, t)`,
  `Call(fn, args, t)` (`fn` — полное имя из списка), `IsNil(operand,
  negated)`, `Tuple(elems, t)`, `Struct(t, fields []FieldInit)`,
  `Convert(operand, t)`, `Index(base, index, t)`, `Lambda(first, names,
  body, t)`; `t` —
  `*reflect.TypeInfo` статического типа узла, `owner` — структура поля.
  `expr.Op`: `Add Sub Mul Div Rem Eq Ne Lt Le Gt Ge And Or Not Neg`
  (`op.Symbol()`). Функции: `TypeOf(n)`, `FieldOf(n) *reflect.FieldInfo`
  (дескриптор поля: имя, индекс, тип, атрибуты — так библиотека находит
  колонку через `f.Attribute<column>()` или по `f.Index` в
  `reflect.Fields<T>()`), `Children(n)`, `Walk(n, f)` (сначала родитель;
  `false` из `f` пропускает детей), `Values(n) []any` (константы и
  захваченные значения в порядке обхода), `Format(n, names)`.
- **Только параметры.** Константы и захваченные значения остаются
  значениями (`any`) и никогда не превращаются в текст: переводчик
  передаёт их как параметры запроса (`?`/`$1`), а не подставляет в SQL.

## Память

Трассирующего сборщика мусора нет и не планируется. Модель — подсчёт
ссылок (ARC) с оптимизациями компилятора, как в Swift и Koka (Perceus);
единственная форма сборки — ограниченный сборщик циклов (см. «Циклы»),
который просматривает только объекты циклических типов.

### Что где живёт

- Значения (структуры, массивы фиксированной длины, примитивы, кортежи) —
  на стеке, копируются при присваивании.
- `new T{}`, срезы, map, строки, замыкания, фреймы корутин, ошибки,
  значения в интерфейсах — в куче, со счётчиком ссылок в заголовке.
- Строки неизменяемы, поэтому подстрока (`s[a..b]`, `strings.Split`,
  `Fields`, `TrimSpace`, `Cut`, тексты совпадений regex) может быть
  *видом* — делить байты исходной строки без копии, как в Go; вид
  удерживает байты родителя, пока жив сам (короткие куски дешевле
  скопировать, и они копируются). Представление — `runtime/ABI.md` §4.1.
- `&local`: переменная, адрес которой берётся, живёт в heap-ячейке со
  счётчиком, если адрес может убежать. **Анализ убегания** оставляет на
  стеке переменную, чей адрес только читается или передаётся неубегающим
  параметрам (не сохраняется, не возвращается, не захватывается, не
  уходит в рантайм, `defer`, интерфейс или `weak`, от неё не берутся
  срезы и сохраняемые внутренние указатели), и так же — объект
  `var p = new T{...}`, если `p` не переприсваивается и не убегает: тогда
  объект лежит в кадре функции, а выход из области видимости `p`
  освобождает его поля (с `Drop`), как освободил бы последний `release`.
  Такой стековый объект несёт неумирающий заголовок, поэтому `*T` на него
  выглядит как обычный. В `async`-функциях анализ не применяется.

### Указатели и владение

`*T` — управляемая ссылка: ненулевой `*T` всегда указывает на целый объект
в куче (`new T{}`, `&x` переменной — её ячейка, `&T{...}`) и владеет одной
ссылкой на него. Копирование указателя — `retain`, перезапись и выход из
области видимости — `release`. Структуры-значения с полями `*T` (и любыми
другими управляемыми полями) копируются и освобождаются поле за полем —
на стеке, в срезах, map, интерфейсах и замыканиях.

**Внутренние указатели** — `&s.f`, `&a[i]`, `&slice[i]`, `&global` — не
имеют собственного объекта, поэтому их нельзя удерживать. Правило:

- внутренний указатель можно разыменовать, сравнить, использовать для
  доступа к полю и передать как аргумент (в том числе как получатель
  метода, `s.inner.Method()`) параметру, который **не убегает**;
- его можно сохранить в **локальную переменную** (`var p = &xs[1]`, как
  в Go): такая переменная — *внутренний указатель в локальной* — держит
  скрытую сильную ссылку на владельца (*pin*): на массив среза для
  `&slice[i]` (поэтому `xs = append(xs, ...)` или `xs = nil` не делают `p`
  висячим — он продолжает указывать в старый массив), на объект для
  `&p.f`, на ячейку переменной для `&s.f`, на pins другой такой переменной
  для `&q.f`. Владелец должен вычисляться без вызовов (путь из
  переменных, полей, разыменований и индексов); `&f()[i]` — ошибка.
  Переменную можно разыменовывать, сравнивать, переприсваивать (`p =
  &ys[0]`, `p = q`, `p = nil`; старые pins освобождаются вместе с
  переменной) и передавать неубегающим параметрам; pins освобождаются в
  конце её блока. Её нельзя скопировать в другую переменную (`var q = p`),
  поле, элемент, map, интерфейс или `weak`, вернуть, захватить замыканием
  или взять её адрес (`&p`);
- в остальном его нельзя сохранить в поле, элемент, map, замыкание,
  интерфейс или `weak`, вернуть из функции или передать параметру,
  который убегает — это ошибка компиляции «cannot keep an interior
  pointer» / «cannot pass an interior pointer to parameter ...» /
  «cannot keep interior pointer variable ...»;
- параметр **убегает**, если функция его сохраняет (куда угодно, включая
  локальную переменную), возвращает, переприсваивает, берёт его адрес,
  захватывает замыканием, превращает в интерфейс или `weak`, передаёт
  убегающему параметру или неизвестной функции (замыкание, метод
  интерфейса); параметры `async`-функций и лямбд убегают всегда. Анализ
  межпроцедурный (наибольшая неподвижная точка по графу вызовов);
- вызывающая сторона держит владельца живым на время вызова (указатель,
  через который взят адрес, или срез — `retain` до конца вызова);
- метод, продвинутый из встроенной структуры, вызывается через интерфейс
  с указателем в середину внешней структуры, поэтому преобразование в
  интерфейс запрещено, если такой метод даёт `this` убежать;
- то же для срезов массивов: `a[i..j]` локального массива владеет его
  ячейкой, глобального — указывает в статическую память, а срез массива,
  доступного через указатель, — внутренний и подчиняется тому же правилу.

Так любой сохранённый в куче `*T` указывает на заголовок объекта
(payload − 16), и `retain`/`release` всегда корректны, а внутренние
указатели живут не дольше вызова, на время которого их владелец
удерживается, или не дольше локальной переменной, которая держит владельца
(сама такая переменная не считает ссылок).

**Заимствованные локальные** (оптимизация, на семантику не влияет;
`compiler/src/hir/borrow.rs`). Функция *не трогает кучу* (heap-pure),
если она не `async` и не лямбда, в ней нет `defer`, она присваивает только
обычным локальным переменным (не захваченным и без взятого адреса),
вызывает только такие же функции и рантайм-функции из фиксированного
списка читающих (строки, `strconv`, `math`, `unicode` — без колбэков,
указателей, интерфейсов и структур в параметрах), не вызывает методы
интерфейсов и замыкания, не делает `append`, `delete`, `errors.As`,
`await`, не форматирует ошибки и структуры и не работает со значениями,
которые могут владеть объектом с `Drop`, который сам трогает кучу
(наибольшая неподвижная точка по графу вызовов). В такой функции
локальная переменная типа `*T`, `string` или `[]T` (не циклического типа,
определённая один раз, не переприсваиваемая, не захваченная, без взятого
адреса) не берёт своей ссылки, если её значение — элемент `for x in s` по
срезу (цикл держит массив среза) или `var x = путь`, где путь — поля,
разыменования и элементы срезов/массивов (индекс — переменная или
константа) от *корня*: параметра, который не переприсваивается, или
переменной, определённой один раз и не переприсваиваемой. Корень держит
ссылку (параметр — вызывающая сторона) всё время жизни `x`, каждое звено
пути — ссылка, хранящаяся в куче, а такая функция ни одну из них не
перезаписывает, поэтому значение `x` живо и без собственного счётчика.
Сохранение, возврат или передача `x` во владеющий параметр берут ссылку
как обычно. Так чтение общих объектов в цикле не делает `retain`/`release`
(в многопоточной программе это атомарные операции над чужими строками
кэша). Гонка данных — запись в общий слот из другого потока без
синхронизации — и без этой оптимизации не определена. `ZELL_NO_BORROW=1`
при компиляции её отключает. Спецификационный тест —
`tests/spec/memory2/borrowed_locals.zl`.

**Заимствованные временные** (оптимизация, на семантику не влияет;
`hir::borrow::borrow_returning`). Функция *возвращает заимствованное*,
если она не `async` и не лямбда, без `defer`, присваивает только обычным
локальным (не параметрам), все её параметры — заимствованные (не
захвачены, без взятого адреса), результат — `*T`, `string`, `[]T` или
структура нециклического типа, и каждый `return e` возвращает параметр,
путь по встроенным полям структур от параметра или от разыменования
параметра-указателя (`this`, `this.d`) либо литерал структуры, все
ссылочные поля которого — такие пути (`Value{d: this.d, n: ...}`). Ссылки
в результате — копии ссылок, которые держат значения аргументов
вызывающей стороны, поэтому тело такой функции их не берёт, а прямой
вызов получает результат заимствованным до конца оператора: аргументы
живут до его конца (владеющие временные удерживаются, места стабильны), а
для параметра, через который результат *читается* (`(*this).d`),
аргументом должен быть адрес стабильного места — локальной переменной (не
ячейки), её встроенного поля или временного значения другого такого
вызова (`it.Get("id").Int()`). Иначе — через vtable, значение-функцию,
рефлексию или с нестабильным аргументом — вызывается обёртка, которая
берёт ссылку как обычно. Сохранение или возврат такого временного берут
ссылку. Спецификационный тест — `tests/spec/memory2/borrowed_temporaries.zl`.

### Деструкторы

Метод `func Drop()` (не статический, без параметров и результата) —
деструктор. Он вызывается ровно один раз, когда значение исчезает:

- для объекта в куче (`new`, ячейка переменной, коробка интерфейса,
  ячейка замыкания) — когда уходит последняя сильная ссылка;
- для значения на стеке — в конце его блока; переменные блока
  освобождаются в обратном порядке объявления, на каждой итерации цикла,
  а также при `break`/`continue`, `return`, `?` и `try ... else`;
- при `return` сначала выполняются отложенные (`defer`) вызовы, затем
  освобождаются переменные функции (последняя объявленная — первой);
- глобальные переменные освобождаются после `main`, в порядке, обратном
  инициализации;
- у структуры с полями-деструкторами сначала выполняется её `Drop` (если
  есть), затем поля освобождаются в порядке объявления.

Этот порядок не зависит от глубины структуры: освобождение длинной цепочки
(список из миллионов узлов, глубокое дерево) не рекурсирует без границы —
глубже 64 вложенных освобождений рантайм ставит умершие объекты в очередь
и освобождает их итеративно, в том же порядке, что и рекурсия («deferred
drop», `runtime/ABI.md` 3.2); стек программы при этом не растёт.

Значение с деструктором (или содержащее его по значению) **только
перемещается**: его создают на месте (литерал, результат функции,
`T!`-результат через `?`/`try`) и передают по значению — это передача
владения (параметр забирает значение, деструктор вызовется в вызываемой
функции). Скопировать такое значение из переменной, поля или элемента
(`var b = a`, `f(a)`, `return a`, `*p`, `for x in arr`) — ошибка
компиляции; делить его можно только по указателю (`&x`, `new T{...}`).
Такие значения нельзя хранить в срезах, map, кортежах, полезной нагрузке
перечислений и результатах `async`-функций (используйте `[]*T`).
`Drop` нельзя вызвать явно, а `this` в `Drop` не должен убегать
(во время `Drop` объект уже освобождается). Неиспользуемая переменная с
деструктором не считается ошибкой: её «использует» деструктор.

### Подсчёт ссылок без накладных расходов там, где он не нужен

Компилятор выводит владение статически и убирает большинство операций
со счётчиком:

- параметры по умолчанию **заимствованы**: функция не делает `retain` при
  входе и `release` при выходе; вызывающая сторона гарантирует, что
  значение живо (собственные локальные переменные и временные значения —
  бесплатно, значения, прочитанные из кучи, глобальных переменных или
  ячеек, удерживаются на время вызова). Параметр становится владеющим,
  только если функция его переприсваивает или она `async`; значение с
  деструктором перемещается;
- `s += x`, `s = s + x` и `xs = append(xs, x)` передают старое значение
  переменной в операцию по владению: если на строку или буфер среза ровно
  одна ссылка, они растут на месте (геометрически), без копии и без
  `retain`/`release` элементов;
- временные значения, живые в момент раннего выхода (`?`,
  `try ... else return/break/continue`), освобождаются на этом пути.

Объекты, не убегающие из функции, живут на стеке без счётчика (см. «Что
где живёт»). Планируется: общий перенос владения при последнем
использовании переменной.

Счётчик реально меняется только там, где объект действительно разделяется
между несколькими владельцами. Задачи выполняются на нескольких потоках,
поэтому счётчик потокобезопасен, но атомарные инструкции нужны лишь там,
где объект действительно трогают разные потоки:

- пока в процессе один поток (планировщик запускается при первой задаче),
  счётчик меняется без атомарных инструкций (`zell_threaded`);
- в многопоточном процессе работает **смещённый подсчёт ссылок** (biased
  reference counting, как в Swift и CPython без GIL): объект, который
  удерживает поток-воркер (или главный поток), «принадлежит» ему — слово
  счётчика делится на часть владельца B, которую он меняет обычной 16-битной
  записью, и общую часть S, которую остальные потоки меняют атомарно;
  счётчик равен B + S. Если чужое освобождение уводит S в минус, объект
  ставится в очередь владельца, и тот (или любой поток, пока владелец спит
  или уже завершился) сводит части и освобождает объект, когда сумма
  стала нулём. Задачи и объекты циклических типов не смещаются никогда;
  объекты завершившегося потока остаются в общем («ничьём») состоянии с
  атомарными операциями. Точный протокол — `runtime/ABI.md` §3.1;
- быстрые пути `retain`/`release` (один поток или свой смещённый
  счётчик) компилятор вставляет прямо в код на любом уровне `-O`
  (`ZELL_NO_INLINE_RC=1` при сборке возвращает вызовы рантайма).
- `defer` без выделения памяти (open-coded, как в Go): если ни один
  `defer` функции не стоит в цикле и их не больше восьми, приёмник и
  аргументы вычисляются в момент `defer` в слоты кадра, а сам вызов
  компилятор вставляет в точку выхода (обычный `return`, `?`, конец
  тела) под флагом «выполнен ли `defer`», в обратном порядке; иначе
  отложенные вызовы по-прежнему хранятся замыканиями в массиве кадра.
  Семантика та же (`ZELL_NO_OPEN_DEFER=1` при сборке отключает, кроме
  функций с `defer await`: у него нет формы в массиве).

### Возврат памяти системе

Освобождённая память возвращается ОС (`runtime/ABI.md` §3.2): маленькие
объекты живут в страницах по 64 КБ, принадлежащих потокам; страница без
живых объектов уходит в общий пул, большие объекты получают собственное
отображение. Свободная память остаётся резервом, пока занятое плюс резерв
не превышают недавнего пика (повторное построение данных не вызывает новых
страничных отказов), и фоновый поток-уборщик отдаёт системе
(`MADV_DONTNEED` / `MADV_FREE` / `DiscardVirtualMemory`) всё, что
пролежало без дела 0,3 с, сверх 16 МБ: после освобождения 500 МБ RSS
падает меньше чем за секунду. `runtime.FreeOSMemory()` отдаёт всё
сразу; `diag.Runtime()` показывает `HeapInUse`, `HeapRetained`,
`HeapReleased`.

### Циклы

Единственная слабость ARC — циклические ссылки. Модель: циклы разрывают
`weak`-ссылками; компилятор предупреждает о типах, которые могут
образовать цикл; диагностика показывает утечки в продакшене; а то, что
всё-таки утекло, освобождает **ограниченный сборщик циклов**. Это не
трассирующий GC (см. ниже).

- `weak *T` — слабая ссылка, не удерживает объект. `weak` — контекстное
  ключевое слово перед `*` в типе. `*T` (и `nil`) неявно превращается в
  `weak *T`; чтение `weak *T` даёт `*T` (удержанный) или `nil`, если
  объект уже освобождён (`var p = c.parent` имеет тип `*T`,
  `c.parent.name` разыменовывает). Слабые ссылки обнуляются до вызова
  деструктора. Используется для обратных ссылок (родитель ↔ ребёнок,
  наблюдатели, кэши). Слабую ссылку можно взять только на целый объект.
- Циклы через замыкания и фреймы корутин — та же модель: захват по
  ссылке удерживает объект, `weak` разрывает.

**(а) Предупреждение при компиляции.** Sema строит граф ссылок между
типами: `*T → T` (у `weak *T` ребра нет), структура → типы полей, данные
перечисления → типы полей вариантов, `[]T`, `[N]T`, `T!`, `Task<T>` →
`T`, `map[K]V` → `K`, `V`, кортеж → элементы, `func(...)` → типы
переменных, захваченных лямбдами этого типа (отложенные `defer`-замыкания
не значения и не считаются), интерфейс и `any` → все типы, которые
где-либо в программе в них преобразуются (программа целиком, поэтому
точнее, чем «любой тип»); у `error` рёбер нет (значения ошибок —
объекты рантайма, сборщик в них не заходит). Тип **может образовать
цикл** (*циклический тип*), если лежит в сильно связной компоненте с
ребром (два и больше типа или ребро в себя). Для каждой пользовательской
структуры (и перечисления) такой компоненты компилятор один раз выдаёт

```
warning: W0001 type Node can form a reference cycle through field Parent (*Node); consider weak *Node or a Drop that breaks the cycle
```

с первым полем, лежащим на цикле (для `[]*T` — «weak *T elements», для
`func` — «capturing a weak *T»). Предупреждения нет: у типов stdlib; у
типа с атрибутом `@allowCycle` (на структуре или перечислении); у
компоненты, где какой-то тип уже держит `weak`-ссылку внутрь неё
(дерево со слабым `Parent`, список наблюдателей — направление владения
задано). `--deny-warnings` (`zell build/run/check`) превращает все
предупреждения в ошибки. Атрибут `@acyclic` на структуре или
перечислении — **обещание** программиста, что значения типа никогда не
лежат на цикле (дерево, список): у типа нет исходящих рёбер в графе, он
не выдаёт W0001, его объекты не помечаются, не записываются кандидатами и
не просматриваются сборщиком (обычный путь ARC без затрат). Выполнение
обещания — ответственность программиста; `--leak-check` в отладочной
сборке проверяет его при выходе: утёкший объект такого типа на цикле даёт
строку `type Node is @acyclic but was found in a cycle`. Предупреждение — подсказка, а не запрет: такие
типы по-прежнему компилируются, и их циклы освобождает сборщик.

**(б) Диагностика в продакшене.** `zell run --leak-check` (и `zell
build --leak-check`): при выходе программа печатает в stderr `leak: N
objects`, (в отладочной сборке) строки `K x Тип` для ещё живых объектов
и `cycle through Type.Field` — поле `*T`, замыкающее цикл, — и
завершается с кодом 66. Неумирающие литералы и sentinel-ошибки не
считаются. В режиме `ZELL_CYCLES=auto` перед отчётом выполняется
последняя сборка циклов (утечкой остаётся только то, что сборщик
освободить не может); в режиме `manual` отчёт добавляет строку `M of
them in unreachable reference cycles the cycle collector can free` —
сколько из утёкших объектов лежат в недостижимых циклах, а остальное —
настоящие утечки (объект удерживает что-то вне кучи: глобальная
переменная, зависшая задача). Без `--leak-check`: `ZELL_DIAG_HEAP=1`
включает дешёвые счётчики живых объектов по типам (`diag.HeapByType`,
обработчик `/debug/heap` с приростом с прошлого запроса,
docs/FRAMEWORK.md §5), а метрики `zell_cycles_collected_total`,
`zell_cycle_collections_total`, `zell_cycle_candidates` попадают в
`diag.PrometheusText`; `runtime.CycleStats()` даёт то же из кода.

**(в) Ограниченный сборщик циклов.** Синхронное пробное удаление (trial
deletion) Бэкона–Раджана поверх счётчиков ссылок, **только для объектов
циклических типов**:

- Объект циклического типа (`new T` — и ячейки, коробки, окружения
  замыканий, массивы срезов и map, через которые может пройти цикл)
  создаётся с флагом в заголовке. Остальные объекты — строки, срезы
  простых данных, всё, что не может лежать на цикле, — в сборке **никогда
  не участвуют**: их не просматривают, их счётчики не трогают, их
  retain/release не меняются.
- *Возможный корень*: когда счётчик помеченного объекта уменьшается, но
  не до нуля, объект один раз записывается в буфер кандидатов своего
  потока. Если объект затем умирает обычным образом, деструктор
  вызывается сразу, как и без сборщика. Исключение — освобождение
  *закрепления* (временной ссылки, которую компилятор берёт на время
  вызова или доступа к полю, `f(n.Left)`): оно кандидата не записывает,
  если за это время не было сборки (эпоха сборок не изменилась), — пара
  retain/release, между которыми ссылка никуда не сохранялась, не может
  оставить новый мусорный цикл.
- *Сборка* просматривает только множество, достижимое от кандидатов по
  ссылкам на помеченные объекты: вычитает внутренние ссылки из
  счётчиков; объект, у которого что-то осталось, держат снаружи — он и
  всё, что от него достижимо, живы; остальное — мусор. Куча целиком,
  стеки и глобальные переменные **никогда не сканируются**, мир не
  останавливается: остальные потоки работают, а объект, счётчик которого
  поменялся во время сборки, считается живым (проверка перед
  освобождением; инвариант — `runtime/ABI.md` 3.8). Размер просматриваемого
  множества ограничен (`ZELL_CYCLES_MAX_SCAN`, по умолчанию 4M объектов;
  больше — сборка отменяется).
- Освобождение мусорного цикла: сначала обнуляются слабые ссылки на его
  объекты, затем вызываются **все** их `Drop` (в порядке записи
  кандидатов; поля всех объектов цикла ещё целы), затем освобождаются
  поля и память. Если `Drop` сохранил объект цикла куда-то наружу, этот
  объект и то, что он достигает, остаются жить (и считаются утечкой), а
  `Drop` никогда не вызывается дважды.
- Когда: `ZELL_CYCLES=auto` (по умолчанию) — после записи N кандидатов
  (N адаптивно: 4096 вначале, от 1024 до 4M — удваивается, если сборки
  находят мало мусора; `ZELL_CYCLES_THRESHOLD=N` фиксирует), при
  ближайшем создании объекта циклического типа в потоке, который это
  заметил; `manual` — только `runtime.CollectCycles()` (возвращает
  число освобождённых объектов); `off` — сборщика нет: флаги не ставятся,
  кандидаты не пишутся, поведение как у чистого ARC. В режиме auto после
  `main` с `--leak-check` выполняется последняя сборка.
- Не собираются циклы через значения `error`, через задачи (`Task<T>`,
  фреймы корутин) и — пока в процессе больше одного потока — через map
  (их таблицы могут перестраиваться параллельно); объекты арен (`-2`) и
  стековые объекты в сборке не участвуют.

Это **не трассирующий GC**: обычные объекты никогда не просматриваются,
нет фазы пометки от корней, нет барьеров записи, освобождение всего, что
не лежит на цикле, остаётся детерминированным. Сборщик — страховка для
циклов, которые программа не разорвала `weak`; цена — запись кандидатов
для объектов циклических типов (benchmarks/README.md).

### Арены

Для серверов, парсеров и других задач с чётким жизненным циклом есть
библиотечные арены (`arena`) — дополнение к ARC, а не замена:

```zell
func Handle(words []string) int {
    var a = arena.New()
    defer a.Free()                  // идиома: одна арена на запрос
    var t = a.New<Token>()          // *Token в арене, обнулённый
    var buf = a.Alloc<int>(64)      // []int из 64 нулей в арене
    t.Text = a.String(words[0])     // копия строки в арене
    ...
}
```

- `a.New<T>() *T`, `a.Alloc<T>(n) []T`, `a.String(s) string` размещают
  значения в арене; `a.Free()` освобождает всё разом (арена остаётся
  пригодной), `a.Len()` — число объектов в ней. Когда исчезает последняя
  копия значения `Arena`, всё освобождается и без `Free`.
- У объектов арены нет подсчёта ссылок: retain/release для них — пустые
  операции (счётчик `-2`, `runtime/ABI.md` 3.6). При `Free` выполняются
  их деструкторы, так что строки, срезы и указатели на обычную кучу,
  хранящиеся в полях, освобождаются.
- Строки и срезы, созданные обычным кодом «внутри» арены, в арену не
  попадают — только через `a.String`/`a.Alloc`; `append` сверх ёмкости
  среза арены копирует его в обычную кучу.
- Указатели в арену после `Free` недействительны; в v1 это не проверяется.
  Освобождать их (переменная или срез таких указателей выходит из
  области видимости после `defer a.Free()` или после `Free` в конце тела
  цикла) безопасно, пока арена не выделила память снова. Арена не
  потокобезопасна.

### Гарантии

- Детерминированное освобождение: деструктор (метод `Drop()`) вызывается
  сразу, когда счётчик обнулился (или в конце блока для значения на
  стеке); файлы и сокеты закрываются вовремя. Исключение — объекты
  недостижимого цикла: их `Drop` вызывает сборщик циклов, когда до них
  доходит (или никогда, если `ZELL_CYCLES=off`).
- Нет фонового потока и барьеров записи, маленький рантайм. Пауза
  сборщика циклов — только у потока, который его запустил, и длится
  столько, сколько занимает просмотр множества кандидатов; остальные
  потоки не останавливаются.
- Нет UB при обращении к `nil` (паника с трассировкой), нет use-after-free
  (ссылка удерживает объект, внутренние указатели не переживают вызов),
  нет арифметики указателей. Паника завершает свою задачу и раскручивает
  её кадры, `async` и синхронные (`defer`, `Drop`, освобождение, раздел
  «Паника»); паника в `main` завершает процесс.

### Почему не иначе

- Rust-подобное владение даёт нулевую стоимость, но противоречит цели
  «простота Go»: lifetimes и borrow checker — не для этого языка.
- Трассирующий GC решает циклы, но приносит паузы, большой рантайм,
  сложный FFI и неопределённое время освобождения ресурсов. Сборщик
  циклов решает только циклы и только для циклических типов, сохраняя
  детерминизм всего остального.

    `IsClosed()`; таймауты — `SetTimeout(ms)` (на каждое ожидание),

    `SetKeepAlive(idle, interval, count)`, `SetReadBuffer`,
    `SetWriteBuffer`, `SetLinger(sec)` (0 — RST при закрытии); `LocalAddr()`/
    `RemoteAddr()` (строки), `Local()`/`Remote()` (`Addr`), `Fd()`.

    `ErrAddrInUse`.
  - **UDP**: `ListenUDP(addr) UDPConn!`, `DialUDP(addr) Task<UDPConn!>`

    `RecvFrom(n) Task<Packet!>` (`Packet{Data, Addr}`), `SendTo(b, addr)`,
    `ReadFrom(buf) Task<Datagram!>` (`Datagram{N, From Addr, Truncated}`:
    длинная датаграмма обрезается и это видно), `WriteTo(b, Addr)`;
    `SetBroadcast`, `JoinGroup/LeaveGroup(group, ifname)`,
    `SetMulticastInterface`, `SetMulticastLoopback`, `SetMulticastTTL`,
    буферы, таймауты и дедлайны как у `Conn`.
  - **Буферизация**: `NewBufferedReader(c, size) BufferedReader`

### Фреймворк

Поверх стандартной библиотеки строится фреймворк уровня ASP.NET Core:
`zell.data` (ORM уровня EF Core с переводом лямбд-деревьев выражений в SQL и
миграциями; реализован как `data`, см. ниже), `zell.log` (структурированный логгер уровня Serilog с sinks и
enrichers), `zell.diag` (профилировщик CPU/памяти/задач в формате pprof,
метрики, OpenTelemetry, `zell tool pprof`). Подробно: `docs/FRAMEWORK.md`.

Атрибутный веб-фреймворк (маршруты через атрибуты, DI, middleware,
OpenAPI) жил в stdlib как `web` и раскрывался компилятором; до появления
`reflect.TypesWith<A>()` его нет в дереве (исходники — тег git
`web-in-tree`, последний тулчейн с ним — `v0.1.0-rc.3`), он вернётся
пакетом `zell-lang/web` (docs/FRAMEWORK.md, «План»). Корень `web` не
зарезервирован за stdlib.

**Перевод лямбд в SQL (`data`).** `zell.data` живёт в stdlib как `data` и
написан как обычная библиотека — без хуков в компиляторе, поэтому его можно
вынести пакетом (`docs/EXTRACTION.md`). Операторы запросов принимают
деревья выражений: `Where(p expr<func(*T) bool>)`, `OrderBy(k
expr<func(*T) any>)`, `Select<R>(f expr<func(*T) R>)`, `GroupBy<K>`,
`Join`, `Sum<N>`, ... у `data.Set<T>`/`data.Query<T>` (раздел «Деревья
выражений»). Библиотека (`data_sql.zl`) обходит дерево, где параметр
означает строку таблицы (`t0`), и строит фрагмент SQL сразу для обоих
диалектов (PostgreSQL и SQLite): поля — столбцы по модели (атрибуты
`@table/@key/@column/...`, соглашения, `Configure`), операторы,
`&&`/`||`/`!`, `nil`-проверки, `strings.HasPrefix/HasSuffix/Contains/
ToUpper/ToLower/Trim`, `len`, `slices.Contains` (`IN`), навигации
(`data.Any(u.Orders, o => ...)`, `len(u.Orders)` — `EXISTS` и скалярные
подзапросы; функции помечены `@expr.call`). Константы и захваченные
значения — всегда параметры запроса. Перевод кэшируется по месту лямбды
(`expr.Expr.SiteId()`) в модели контекста: повторный запрос берёт SQL из
кэша и читает только значения слотов. Модель сущности строится при первом
`data.Open<C>()` из таблиц рефлексии и `Configure`, а доступ к полям
(чтение строки, значения столбцов) развёрнут по `reflect.Fields<T>()` без
рефлексии во время выполнения. При компиляции проверяются типы: лямбда
проверяется как обычная (неизвестное поле, несовпадение типов, вызов вне
списка — ошибки компиляции), а неотображаемый тип поля, `Select` коллекции,
`Where` после `Select` — ошибки `reflect.Error` в библиотеке. То, что
зависит от модели (поле `@ignore` в лямбде, отношение без внешнего
ключа), — ошибка запроса или `data.Open` во время выполнения.

## Платформы

Linux, macOS и Windows на amd64 и arm64 — tier 1 с CI и релизными
бинарниками; кросс-компиляция `zell build --target windows-amd64` с
любой машины через LLVM и вшитый `lld`. Платформозависимый код рантайма
изолирован в `runtime/src/platform/`. Подробно: `docs/PLATFORMS.md`.

Условная компиляция:

- `@cfg(условие)` на любом объявлении (функция, структура, поле, метод,
  интерфейс, enum, вариант, `var`, `const`) и перед `namespace` (весь
  файл). Условия: `os: "linux"` (`linux`, `macos`, `windows`, `freebsd`,
  `android`, `ios`, `wasi`), `arch: "amd64"` (`amd64`, `arm64`, `wasm32`),
  `feature: "tls"` (features пакета из манифеста, `docs/PACKAGES.md`),
  `not(у)`, `any(у, ...)`, `all(у, ...)`; несколько аргументов одного
  `@cfg` должны выполняться все. Неизвестный ключ, ОС или архитектура —
  ошибка компиляции.
- Исключённое объявление не проверяется типами, его имени нет
  (использование — `unknown identifier`), поэтому два варианта одной
  функции или структуры под разные платформы сосуществуют.
- Суффиксы файлов, как в Go: `x_linux.zl`, `x_windows.zl`, `x_macos.zl`,
  `x_amd64.zl`, `x_arm64.zl`, `x_linux_arm64.zl` — файл каталога или пакета
  компилируется только для этой цели (файл, указанный явно, берётся
  всегда).
- Константы `os.Name`, `os.Arch`, `os.PathSeparator`, `os.LineSeparator` —
  строки времени компиляции (годятся в `const`).
- Цель — хост или `--target <triple|alias>` (`linux-amd64`,
  `aarch64-apple-darwin`); пока генерация кода только для хоста, а
  `zell check --target windows-amd64` проверяет код под другую цель.

## Компилятор и инструменты

- Реализация компилятора: **Rust** (крейт `inkwell` для LLVM API) — безопасно,
  быстро, хорошие библиотеки для парсинга.
- Дистрибутив для пользователя — один бинарник `zell`: LLVM и `lld`
  линкуются статически, рантайм и стандартная библиотека лежат рядом.
  Пользователю не нужно ставить LLVM, clang или системный линковщик.
- Пайплайн: лексер → парсер (AST) → разрешение имён и типов → проверка
  ошибок (`!`/`?`/`try`) → понижение в LLVM IR → `llc`/`clang` для линковки
  с рантаймом.
- Рантайм (`runtime/`): на C или Rust — аллокатор, подсчёт ссылок,
  планировщик задач, строки, срезы, map, паника.
- CLI:

```
zell build ./src -o app      # собрать
zell run main.zl             # собрать и запустить
zell fmt ./src               # форматировать
zell test ./src              # тесты (@test func TestX(t *testing.T)): --filter, --json, --bench, -v
```

- `zell test [path]` находит функции `@test` (`func TestX(t *testing.T)`,
  `func X()` без параметров, они же `async` — `func(*testing.T) Task<void>`,
  раннер их ожидает (`testing.Case.RunAsync`); бенчмарки
  `func BenchX(b *testing.B)` — с `--bench`), генерирует драйвер, вызывающий `testing.Main`, и
  запускает его; собственные `main` переименовываются в памяти. Каждый
  тест выполняется в отдельном процессе (тестовый бинарник перезапускает
  себя с `--run-one`), поэтому `t.Fatal`, `t.Skip` и паника завершают только
  его; `t.Run` — подтесты в процессе родителя. Вывод как у `go test`
  (`--- FAIL: Name (0.00s)`, `PASS`/`FAIL`, итог `ok`), `--json` — события
  `{"Action": ...}`, `--filter` — подстроки через `|` с якорями `^`/`$`,
  `--parallel N`; код выхода 1 при падении.
- **Тесты с ошибками.** Тест может быть объявлен с результатом `void!`
  (`@test func TestX(t *testing.T) void!`, без параметров и `async` —
  так же) и пробрасывать ошибки через `?`. Ошибка, вернувшаяся из теста,
  проваливает его, как `t.Fatal`: в лог теста пишутся `error: <Message()>` и
  трасса ошибки — то же, что печатает непойманная ошибка в `main`
  (`testing.Case.RunErr`/`RunAsyncErr`/`PlainErr`/`PlainAsyncErr`).
- **`t.Must(x)` и `t.MustFail(x)`** — встроенные (intrinsic) вызовы на
  `*testing.T` (или `testing.T`); единственное исключение из правила
  «Игнорирование и обязательность»: их аргумент — необработанное выражение
  `T!` (в том числе `await g()` в async-тесте). Другие функции и методы
  `T!` по-прежнему не принимают.
  - `t.Must(f())` возвращает значение `T` (для `void!` — ничего, пишется
    оператором). При ошибке тест завершается как `t.Fatal`, в лог пишутся
    `файл:строка: <Message()>` (место вызова `Must`, путь относительно
    текущего каталога компиляции) и трасса ошибки.
  - `t.MustFail(f())` возвращает `error`. Если `f` завершилась успешно
    (значение освобождается), тест завершается с `файл:строка: expected
    an error`.
  - Аргумент не типа `T!` — ошибка компиляции (`t.Must needs a fallible
    (T!) argument`). Получатель `Must` вычисляется только при ошибке.
  - Реализация: компилятор понижает `t.Must(x)` в
    `try x catch err { t.mustError(err, "файл:строка"); panic(...) }`, а
    `t.MustFail(x)` — в вызов `testing.mustFail<T>(t, x, "файл:строка")`;
    `x` вычисляется в самой тестовой функции.

  ```zell
  @test
  func TestParse(t *testing.T) void! {
      var n = t.Must(strconv.Atoi("42"))       // int
      testing.Equal(t, n, 42)
      var err = t.MustFail(strconv.Atoi("x"))  // error
      testing.Contains(t, err.Message(), "invalid syntax")
      var m = strconv.Atoi("7")?               // ошибка провалит тест
      testing.Equal(t, m, 7)
  }
  ```
- Расширение файлов: `.zl`.
- В сообщениях об ошибках типы текущего пространства имён пишутся коротко
  (`Point`), остальные — полным путём (`app.models.User`, `task.Mutex`).
- Компилятор — библиотека; LSP-сервер, форматтер, отладчик и IDE-плагины
  строятся на ней. Подробно: `docs/TOOLING.md`. Каноническая грамматика
  для IDE: `grammar/zell.bnf`; подсветка VS Code: `editors/vscode/`.
- Проект описывается файлом `zell.toml` (имя, версия, зависимости, точка
  входа). Менеджер пакетов встроен в `zell`: `docs/PACKAGES.md`.

## Пример программы

```zell
namespace app

import io

struct Counter {
    count int

    func Inc() { this.count += 1 }
    func Value() int { return this.count }
}

struct Parser {
    static func ParseInt(s string) int! {
        if s == "" {
            return error("empty string")
        }
        return strings.ToInt(s)?
    }
}

async func Load(path string) []string! {
    var text = await io.ReadFileAsync(path)?
    return strings.Split(text, "\n")
}

async func main() {
    var lines = try await Load("numbers.txt") catch err {
        println("cannot load:", err)
        return
    }

    var c = Counter{}
    for line in lines {
        var n = try Parser.ParseInt(line) else 0
        if n > 0 {
            c.Inc()
        }
    }
    println("positive numbers:", c.Value())
}
```

## Грамматика (упрощённо, EBNF)

```
file        = { attribute } "namespace" path { import } { decl } ;   (* @cfg(...) here excludes the file *)
import      = "import" path [ "as" ident ] ;
decl        = { attribute } ( struct | interface | enum | func | externfunc | var | const | typealias ) ;
typealias   = "type" ident "=" type ;         (* transparent alias; "type" is contextual *)
attribute   = "@" path [ "(" [ attrarg { "," attrarg } ] ")" ] ;
attrarg     = [ name ":" ] expr ;            (* in attribute arguments a call takes attrargs: @cfg(not(os: "windows")) *)
name        = ident | keyword ;              (* field and attribute argument names: @Conf(enum: "a") *)
cfg         = "@cfg" "(" cond { "," cond } ")" ;
cond        = ( "os" | "arch" | "feature" ) ":" string | ( "not" | "any" | "all" ) "(" cond { "," cond } ")" ;
struct      = "struct" ident [ generics ] [ "implements" type { "," type } ] "{" { field | method } "}" ;
generics    = "<" tparam { "," tparam } ">" ;
tparam      = ident [ ":" type ] ;            (* type: interface, or builtin Ordered, Comparable, Equatable, Add, Sub, Mul, Div, Rem, Neg, MatMul *)
interface   = [ "sealed" ] "interface" ident "{" { type | ifacemethod } "}" ;   (* type: embedded interface *)
ifacemethod = { attribute } [ "async" ] "func" ident "(" [ params ] ")" [ type ] [ block ] ;  (* block: default method *)
enum        = "enum" ident [ generics ] [ "implements" type { "," type } ] "{" variant { ( "," | newline ) variant } { method } "}" ;
variant     = { attribute } ident [ "(" params ")" ] ;
field       = { attribute } name { "," name } type [ "=" expr ] ;   (* name: not "func", "static", "async" *)
method      = [ "static" ] func ;
func        = [ "async" ] "func" ident [ generics ] "(" [ params ] ")" [ type ] block ;
externfunc  = "extern" "func" ident "(" [ params ] ")" [ type ] ;   (* только в std/**/*_extern.zl *)
params      = param { "," param } ;
param       = ident { "," ident } type | ident "..." type ;   (* variadic: last parameter, a []T *)
type        = path [ typeargs ] [ "!" ] | "*" type | "weak" "*" type | "[" [ constexpr ] "]" type
            | "map" "[" type "]" type | "func" "(" [ types ] ")" [ type ]
            | "(" types ")" ;           (* path may start at a compile-time descriptor: t, p.Type, f.Type, m.Result, m.Args;
                                           expr<F> (an expression tree) is a path with typeargs *)
block       = "{" { stmt } "}" ;
stmt        = var | const | if | for | switch | trystmt | "return" [ exprs ]
            | "break" [ ident ] | "continue" [ ident ] | "defer" expr | exprs [ assignop exprs ]
            | ident ":" ( for | switch ) ;      (* label; no ";" is inserted after ":" *)
assignop    = "=" | "+=" | "-=" | "*=" | "/=" | "%=" | "@=" | "&=" | "|=" | "^=" | "<<=" | ">>=" ;
                                              (* a, b = b, a ; (q, r) = f() *)
var         = "var" ( ident { "," ident } | "(" ident { "," ident } ")" ) [ type ] [ "=" expr ] ;
                                              (* several names: tuple destructuring; var v, ok = m[k] is the comma-ok lookup *)
if          = "if" expr block [ "else" ( if | block ) ] ;
for         = "for" [ ident [ "," ident ] "in" ( expr | range ) | expr ] block ;
                                              (* "in" is contextual: an ordinary name elsewhere *)
switch      = "switch" expr "{" { "case" pattern { "," pattern } ":" stmts }
              [ "default" ":" stmts ] "}" ;
pattern     = expr | expr ".." expr | path "(" [ idents ] ")" | type ident ;
expr        = unary { binop unary } ;
binop       = "||" | "&&" | "==" | "!=" | "<" | "<=" | ">" | ">="
            | "+" | "-" | "|" | "^" | "*" | "/" | "%" | "@" | "<<" | ">>" | "&" ;
                                              (* "@" between operands: MatMul; an "@" starting a decl is an attribute *)
unary       = ( "-" | "!" | "&" | "*" | "await" ) unary | tryexpr | postfix ;
tryexpr     = "try" expr ( "catch" ident block | "else" expr ) ;
trystmt     = "try" block "catch" ident block ;
postfix     = primary { "." ( ident | int ) | "(" [ exprs [ "..." ] ] ")" | "[" ( expr | range ) "]"
            | "?" [ "(" expr ")" ] | typeargs } ;
typeargs    = "<" type { "," type } ">" ;     (* only before ( { . ) ] } , or end of statement *)
range       = [ expr ] ".." [ expr ] ;
primary     = literal | ident | path [ typeargs ] "{" [ fields ] "}" | "new" primary
            | "(" expr ")" | "(" exprs ")" | lambda ;
lambda      = [ "async" ] "func" "(" [ params ] ")" [ type ] block
            | [ "async" ] "(" [ params | idents ] ")" "=>" ( block | expr )
            | [ "async" ] ident "=>" ( block | expr ) ;
                                              (* untyped "(u) =>" and "u =>": types from the expected func type *)
```

## Этапы реализации

1. **Лексер и парсер** — полный синтаксис, AST, сообщения об ошибках с
   позициями.
2. **Семантика** — пространства имён и импорты, разрешение имён, вывод типов,
   проверка `!`/`?`/`try`, структурные интерфейсы.
3. **Кодогенерация** — LLVM IR для структур, функций, указателей, срезов,
   строк, `switch`, ошибок; линковка с рантаймом на C.
4. **Рантайм** — аллокатор с подсчётом ссылок, строки, срезы, map, паника.
5. **Async** — LLVM coroutines, планировщик, `task`.
6. **Стандартная библиотека (ядро) и инструменты** — `io`, `strings`,
   `fmt`, `fs`, `os`, `time`, `zell fmt`, `zell test`.
7. **Generics** — `List<T>`, ограничения через интерфейсы (мономорфизация). ✓
   (без обобщённых интерфейсов; см. «Generics»).
8. **Сеть и криптография** — `net`, `net.http`, `crypto.*` через
   BoringSSL/libsodium, `encoding.json`.
9. **Остальная стандартная библиотека** — форматы, сжатие, regex, SQL, log.
10. **Рефлексия** — атрибуты, таблицы `TypeInfo`, `reflect`, compile-time
    `Fields<T>()`; `encoding.json` поверх неё. ✓ (см. «Рефлексия»,
    «Реализовано»).
11. **Инструменты** — `zell lsp`, `zell fmt`, DWARF и DAP, плагины для
    VS Code и IDEA (`docs/TOOLING.md`).
